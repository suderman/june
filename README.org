#+TITLE: June

June is Jon's personal assistant: one persistent daemon on Pi Durable that he talks to from Kitty and Telegram. She reads Org for tasks and knowledge and Herdr for live agent sessions, and does quick checks and small edits herself with a shell and file tools on the daemon host. She does not replace either, and she still hands larger work to coding agents through the dispatcher. Design and rationale are in [[file:docs/architecture.org][docs/architecture.org]].

* Commands

#+begin_src sh
june                 # terminal client attached to the primary conversation
june ask "What are my agents doing?"
june ask --json "..."    # {"requestId","status","text","reason"}
echo "..." | june ask -
june status [--json] # daemon, model, and conversation state; no model call
june doctor          # configuration and dependency checks
june serve           # the daemon
#+end_src

Exit codes: 0 answered, 1 unanswered or failed, 2 usage, 3 daemon not running. In the client, Enter sends (as a steer while June is working), Alt+Enter queues a follow-up, Esc runs =/stop=, Ctrl+D detaches.

The terminal client, =june ask=, and Telegram share these slash commands, with the same meanings and replies:

| Command                  | Effect                                                         |
|--------------------------+----------------------------------------------------------------|
| =/new=                   | Stop the run, drop queued messages, start a fresh context. History stays in storage. |
| =/stop=                  | Stop the current run; queued messages continue.                |
| =/compact [instructions]= | Compact the context now.                                      |
| =/status=                | Model, state, queue, context use, and spend.                   |
| =/help=                  | List the commands.                                             |

The terminal client and =june ask "/reload"= also support =/reload=. It rescans the configured skill directories and finds and rereads =SOUL.org=, =MEMORY.org=, and =AGENTS.md= without a model call, chat reset, or daemon restart. New, changed, and removed skills apply on the next model turn. A running model call and queued messages are left alone. Code, =config.json=, provider, and environment changes still need a daemon restart. Telegram does not support =/reload= yet because its channel library has no custom-command hook.

There is one conversation, so =/new= and =/compact= from any surface affect all of them. Command replies are not part of the conversation; in the terminal they disappear on reconnect, as Telegram's replies sit only in the chat. Detaching or losing the connection never stops work, and the client reconnects by itself. From another host, run =ssh -t kit june= or =ssh kit june ask "..."=.

* Files

This repository holds code only. June reads configuration and identity in place from the directories in =JUNE_CONFIG_PATH=, colon-separated, least specific first. Without it she reads only =$XDG_CONFIG_HOME/june/=. Jon's NixOS module sets three layers:

| Layer     | Directory                 | Kept in                  | Holds                                         |
|-----------+---------------------------+--------------------------+-----------------------------------------------|
| Harness   | =~/.agents/june/=          | Git (suderman/agents)    | =config.json= defaults, =AGENTS.md= conventions |
| Personal  | =~/profile/june/=          | Syncthing                | =SOUL.org=, =MEMORY.org=, =JOURNAL.org=, =config.json= with =daemonHost= |
| Machine   | =$XDG_CONFIG_HOME/june/=   | this host only           | optional =config.json= overrides                |

=config.json= files merge in path order: objects key by key, arrays and values replaced. =SOUL.org= and =AGENTS.md= come from the most specific directory that has them, and =MEMORY.org= and =JOURNAL.org= are the files beside that =SOUL.org=, which June creates when she first writes to them. =SOUL.md= is no longer read, and =june doctor= fails while one remains. Skill directories are configuration too (=skillDirs=); none are built in.

Runtime files stay on the daemon host and are never synced:

| What                 | Where                                |
|----------------------+--------------------------------------|
| Durable state        | =$XDG_STATE_HOME/june/june.sqlite=    |
| Telegram attachments | =$XDG_STATE_HOME/june/files/inbox/=   |
| Socket               | =$XDG_RUNTIME_DIR/june/june.sock=     |

=JUNE_STATE_DIR=, =JUNE_RUNTIME_DIR=, and =JUNE_SOCKET= override these, which is how a development daemon runs beside the real one. Never put the state directory in Syncthing: copying a live SQLite database with its WAL corrupts it.

* Configuration

Keys, with the defaults that apply when no layer sets them:

#+begin_src json
{
  "model": {
    "chat": { "provider": "(required)", "modelId": "(required)", "thinkingLevel": "medium" },
    "focus": null,
    "patter": null
  },
  "providersFile": "~/.pi/agent/models.json",
  "envFiles": [],
  "contextCap": 200000,
  "daemonHost": null,
  "skillDirs": [],
  "org": { "root": "~/org" },
  "dispatch": { "hosts": [] },
  "herdr": { "session": "default", "host": "<hostname>", "hosts": {}, "allowPrompt": false },
  "telegram": { "tokenEnv": "TELEGRAM_BOT_TOKEN", "allowedUserIds": [] }
}
#+end_src

- =model.chat= is June's everyday model and where every conversation starts. Its =provider= names a provider in =providersFile=, Pi's own =models.json=, whose =apiKey= must be a =$VARIABLE=.
- =model.focus= is the model June uses when she focuses, such as ={"modelId": "gpt-6.1-sol"}=; =provider= and =thinkingLevel= default to chat's. Without it she has no =focus= tool.
- =model.patter= is the cheap model that keeps the user company during long waits, such as ={"modelId": "gpt-6-luna"}=; =provider= comes from chat and =thinkingLevel= defaults to =medium=, which keeps its planning out of the line at no cost in speed. Without it there is no patter.
- =envFiles= are dotenv files read for keys at startup, for development. The service gets keys from its =EnvironmentFile=.
- =daemonHost= is the machine that runs June. Keep it in a layer every host has, such as a synced one. On any other machine, =june=, =june ask=, and =june status= run there over SSH when no local daemon answers. =JUNE_LOCAL=1= disables that.
- =skillDirs= are read in place; =skill_read= only reads inside a listed skill's directory.
- =herdr.hosts= lists other machines June may inspect read-only over SSH, such as ={"cog": {}, "lux": {}}=; ={"ssh": "target"}= overrides the SSH destination.
- =dispatch.hosts= are the machines June may queue AUTO tasks for; the first is the default. Empty, the default, leaves out =org_create_project=, =org_queue_task=, =org_resume_task=, =org_complete_task=, and =org_dispatch_now=.
- =herdr.allowPrompt= enables =herdr_prompt_agent=, which types a follow-up into an existing agent on this host.
- =telegram= turns the channel on. Leave it out to run without Telegram. The allowed user id is personal, so it belongs in =~/profile/june/config.json=.

* Shell and files

June has Pi Durable's =bash=, =read=, =edit=, and =write= tools. They run on the daemon host, kit, whichever client Jon uses, as his user; other hosts are reached with =ssh=. Commands start in the home directory and stop after 120 seconds unless the call passes a longer =timeout=. Output keeps the last 2000 lines or 50 KB, with the full output spilled to a temporary file. =/stop= kills a running command. None of these tools is replay-safe: a call a restart interrupts comes back to the model as interrupted rather than running again. =edit= fails when the text it replaces has changed, so concurrent edits from Emacs or Syncthing are not overwritten silently. The tools grant capability, not permission: when to delegate, and what needs Jon's approval, are set by =AGENTS.md=. The shell can read provider keys in the service environment and =~/.pi/agent/.env=; =AGENTS.md= forbids printing them.

* Chat, focus, and patter

June has three modes, all hers to manage: chat (=model.chat=) for everyday talk, focus (=model.focus=) for careful work, and patter (=model.patter=) to keep the user company while real work runs.


June has her own working context for work she does herself. The =work= tool hands a self-contained brief to a background task that owns a child conversation, with her tools and identity but without =work= itself, the task-queueing tools, Telegram, the journal, or the memory review. The call returns at once and June says she is on it, so the user can keep talking to her while the brief runs; the status bar shows "working in the background". Only the final report comes back, as a =[work]= follow-up she relays, so shell output, file contents, and dead ends stay out of the main thread and its compactions. The child cannot ask the user anything; a decision or approval it needs comes back in the report. After a restart the task finds the same child and the same submitted brief, so nothing runs twice, and the report is sent once. =/stop= (or Esc) stops the main thread's run if there is one, and otherwise stops the background work. =june ask= returns June's first answer, so a brief's report comes later in the conversation, not in that reply.

Focus is hers to manage, like tying her hair up for heads-down work. The =focus= tool switches the main conversation to =model.focus= or back from its next model request, and a prompt section tells her which she is in and to relax when the careful work is done. A brief can run focused on its own with =work= and =focus: true=, leaving the main thread relaxed. There is no command or setting for it; ask her to focus or relax. A restart and =/new= always start relaxed.

Patter is how June stays present during a long wait, the way someone beside you would banter through a slow build rather than sit like a statue. A wait begins when a run has been busy for eight seconds, at once when she is focused, or as soon as a =work= brief is running in the background. When the user breaks in during background work, patter pauses, June hears what it said, and once she has answered patter picks the same bit back up. Patter opens with a quip, then speaks about every 25 seconds, spacing out as a wait drags on (up to three minutes between lines) and stopping when the answer lands. Patter is June at her most playful, carrying one running bit through the wait. Every line hears her identity and the local date and time; the opener also hears the last few exchanges of the conversation, the user's latest message, and the brief; each later line hears only the tool calls since its last line, what is still running and its latest output, and the wait in rough words such as "a few minutes". Its earlier lines come back as its own turns, so it builds on them, and when nothing new has happened it talks about the topic, the user, or the wait instead of restating the status. Tool results stay out, since the answer is June's to give. Its rules forbid claiming results, guessing how long is left, promising, or deciding anything. A line is a display-only entry: the terminal client shows it in italics after a kangaroo, and no model context or memory review ever contains it. The next chat or focus request gets a hidden prompt section listing that wait's lines, marked as performance rather than information. Patter is best effort: a request slower than ten seconds or failing is dropped and logged, and a line that finishes after the answer is discarded. It runs as an in-memory loop, so a restart mid-wait simply starts it again. While the user's latest message came from Telegram, the lines also grow one message in his chat: the first line sends it and each later line edits it, so the phone buzzes once per wait and the message shows June is still at it. After June answers mid-wait, later lines start a new message below her answer. While a brief runs, the chat also shows her typing.

* Personal memory

=SOUL.org= is June's identity. =MEMORY.org= preserves how her understanding of Jon develops, including formative corrections, shared realizations, and explanations of why something matters. A useful lesson records what happened, what changed in her understanding, and how she should act differently, with dates and source references where available. Jon's words and June's interpretations stay distinct. Both are ordinary Org files in the personal layer, shared by Syncthing and read into the system prompt. Changed files apply on the next model turn; =/reload= also finds files added or moved since startup. June can maintain them during ordinary conversation with her file tools. Jon's Org records remain authoritative for tasks, schedules, and project facts.

=JOURNAL.org= is June's own journal: a dated record of Jon, their days together, and what she notices about him, in her own voice. It is an Org date tree (year, month, day, then a timed entry), like Jon's =~/org/journal.org=, which is his and not hers. She writes it on her own judgment with the =journal= tool, which files an entry under today's date and time, and searches it like any file when she needs their past to make sense of the present. Compaction adds entries for anything in the old context she missed. Her working context has no journal tool. The journal is not part of her prompt.

Before manual or automatic compaction, one model request produces both the working summary and a review against existing memory. Useful learning is saved before the summary replaces old context. An unchanged memory is a successful review; no lesson is required. The review reconciles corrections without duplicating lessons or discarding unrelated history. It never rewrites =SOUL.org=, prunes Jon's records, or grants new authority. No nightly job is involved.

A failed review or save skips compaction and keeps old context. Terminal =/compact= reports the cause. Telegram's library still gives its generic decline reply, "Nothing to compact." Failure details enter June's next model prompt on either channel. A request may still proceed if it fits, but overflow recovery cannot proceed without successful compaction. Resolve the cause before retrying. Malformed or truncated output, a two-minute timeout, concurrent edits, a changed personal layer, non-regular memory files, and Syncthing conflict copies all prevent replacement. The combined output is capped at 8192 tokens, so an oversized memory can also stop compaction; there is no automatic pruning.

The save uses a flushed temporary file and atomic rename, with checks against the reviewed text before replacement. This prevents June's own callbacks from interleaving but is not a cross-host lock: an external editor or Syncthing can still race the final check and rename. A saved proposal is reused after restart, and a changed context range refuses the old summary. A provider request interrupted before its response is recorded may be repeated. Memory content stays in Org; replay receipts and failure status live in the existing unsynced SQLite state.

* Filing new tasks

June honors an explicit destination. Otherwise she uses =org_projects= to find an existing project under =~/org/work= by its preamble and repository links before choosing a new path. For a new GitHub repo project, owner/repo guides =work/<owner>/<repo>/<repo>.org=. Unmatched work and clear one-offs go under =work/june/<name>/<name>.org=, not the June software project's file.

=org_create_project= creates the title, category, and optional local and GitHub repository links without overwriting an existing file. It refreshes the dispatcher's agenda with a read-only scan and confirms the file is listed before June queues work there. A failed discovery leaves only the metadata record for retry; it does not write an AUTO task or bypass the agenda check. =org_queue_task= then writes and follows the task as usual. Without a local repository link or a =dir= override, the dispatcher uses the new project directory as the working directory. Review stays on unless Jon explicitly waives it, including for read-only lookups. The worker leaves EVAL; June then reads the outcome and verification evidence. For a task she created, she uses =org_complete_task= to mark it DONE when the request is satisfied and no Jon decision, approval, or review remains, then reports the reviewed result. Tasks needing Jon's review or with incomplete evidence stay EVAL. Resuming Jon's task does not make it hers to close. Completion uses =org-edit= with an EVAL expected-state check; an already DONE task is unchanged on replay. Normal Org archiving handles finished tasks.

* Resuming existing tasks

When the user explicitly asks to start or resume an existing TODO, EVAL, or HOLD task, June can use =org_resume_task=. It uses the shared =org-edit= command with an expected-state check and a replay key, records the user's instruction in Dialog, selects one host, sets review on and deploy off, and preserves the task ID, scope, history, other properties, and schedule. A missing ID is created. A working or blocked linked agent prevents the change. June starts this host's dispatcher, and a new follow watches this run even if a previous run already reached EVAL. Other hosts use their dispatcher timer; existing SCHEDULED dates still apply.

This needs the =org-edit= resume options from =suderman/agents=. Coding workers still must not set AUTO. That distinction is an instruction rule, not a security boundary.

* Telegram setup

1. Create a new bot with @BotFather. Do not reuse the Hermes bot: two processes polling one token fail with 409 Conflict.
2. Put =TELEGRAM_BOT_TOKEN=<token>= in an agenix secret, or an env file for development.
3. Find Jon's numeric user id (for example from @userinfobot) and set ="telegram": {"allowedUserIds": [<id>]}=.
4. Restart June. =june status= shows =telegram polling=, and a message to the bot appears in the terminal client too.

Only allowed users reach the model. Private chats share the primary conversation; Telegram's =/new= resets it for every surface.

What June hears on her own initiative, a =[work]= report or a =[follow]= update on a task she queued, goes where Jon last spoke to her: if his latest message came from Telegram, it goes through the channel's delivery, so her answer reaches the chat, and the terminal shows it as one short =work= or =follow= line; otherwise it stays in the terminal. Patter follows him to the phone as one growing message (see Patter).

June answers terminal messages in Org markup, which the terminal renders through a small Org-to-Markdown pass (=src/org.ts=), and Telegram messages in Markdown, the only rich text Telegram renders.

* Development

#+begin_src sh
nix develop           # node 22 and ripgrep
npm ci
npm run typecheck
npm test              # also: nix flake check
JUNE_STATE_DIR=/tmp/june-dev JUNE_RUNTIME_DIR=$XDG_RUNTIME_DIR/june-dev bin/june serve
JUNE_STATE_DIR=/tmp/june-dev JUNE_RUNTIME_DIR=$XDG_RUNTIME_DIR/june-dev bin/june
#+end_src

On kit, the =june= command from Jon's NixOS module runs this checkout instead of the pinned package whenever =src/cli.ts= and =node_modules= exist here, the service included. Edit, then =systemctl --user restart june= for daemon changes, or rerun the client; =june status= shows the code path in use. =JUNE_SOURCE=none= forces the package, and =JUNE_SOURCE=<dir>= picks another checkout. Remove =node_modules= or set =JUNE_SOURCE=none= in the service before leaving a half-finished change, since a daemon that cannot start leaves June down. Configuration, =SOUL.org=, =MEMORY.org=, =AGENTS.md=, and skills are read live in either case.

Unix socket paths are limited to 108 bytes, so keep =JUNE_RUNTIME_DIR= short. Tests use pi-ai's faux model and a fake Telegram port; they never call a provider or Telegram. =nix build= typechecks and produces =result/bin/june=. After changing dependencies, update =npmDepsHash= in =nix/package.nix=.

* Deployment

The flake exports =packages.<system>.default=. The Home Manager module lives in [[https://github.com/suderman/nixos][suderman/nixos]] as =programs.june=, following that repository's conventions: =programs.june.enable= puts =june= on PATH, and =programs.june.daemon.enable= on kit runs =june serve= as a user service, persists =~/.local/state/june=, and reads provider keys from Pi's agenix-generated =~/.pi/agent/.env=. Logs go to the journal as =level event key=value= lines with secrets redacted: =journalctl --user -u june=. June and the Hermes June can run side by side until Jon cuts over.

* Roadmap

Short technical list until this moves into the Org project.

1. Telegram with a real bot token on kit.
2. Safe Org writes through =org-edit=: capture to the inbox, add a note to a task, change state, schedule. Idempotency keys, a check of the current state before retrying, and refusal of =asana.org= and conflict copies.
3. Herdr follow-up prompts on by default once tested, with a confirmation rule for agents that are blocked on an approval.
4. A bounded supervision check from a systemd timer: deterministic Herdr and Org scans, silence when nothing changed, a small ledger of notified and acknowledged events, and a separate background conversation for judgment.
5. Upgrade to Pi Durable 1.4 when pi-durable-telegram does.
6. Later: notmuch, calendar, Home Assistant, voice.

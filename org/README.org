* Org agent system

Org files assign work to agents, and June runs that system: she queues and follows tasks with her own tools (=src/tools/org.ts=, =dispatch.ts=, =follow.ts=), and this directory holds the commands and prompts underneath.

#+begin_src text
org/
├── dispatch/org-dispatch.el   dispatcher, run by Emacs in batch
├── dispatch/org-dispatch      command-line wrapper
├── edit/org-edit              TODO states and dates set by Org for agents
├── prompts/                   task.org and nudge.org, sent to the agent
├── bin/herdr-link             stamp and follow herdr: links
└── tests/                     batch tests with fixtures
skills/                        project-org-tasks, org-triage, for every agent
#+end_src

** Where each piece runs

June's Home Manager module (=homeModules.default=, see the main README) builds =org-dispatch=, =org-edit=, and =herdr-link= from the same commit as the package, with =ORG_DISPATCH_EL=, =ORG_DISPATCH_PROMPTS=, and =ORG_EDIT_EL= set to that commit, and with =programs.june.dispatch.enable= runs the dispatcher every minute with a systemd user timer. The host provides Herdr and the agents it dispatches, pi or Claude Code. A system flake pins June as an input, so the dispatcher always runs with the prompts from the same commit, and rolling back the system rolls both back. Changing either one needs an input update and a rebuild. To test local changes before pushing, rebuild with =--override-input june path:<checkout>=.

The skills are different. =~/.agents/skills.json= lists them as local entries with two paths, so =agents apply= links =~/.agents/skills/project-org-tasks= and =org-triage= into this checkout when it is there, and edits apply at once; elsewhere it links the pinned copy that =programs.june= places at =~/.config/june/skills=. Every harness finds them in =~/.agents/skills=. Rebuild before publishing skill text that describes a new command.

An Emacs configuration that shows these tasks needs the same TODO keywords, and the =herdr:= link handler if it opens session links. Change both copies of the keywords together.

** The contract

States, set in =org-todo-keywords= here and in the user's Emacs configuration:

| State | Meaning                                                       |
|-------+---------------------------------------------------------------|
| TODO  | the user's task                                               |
| AUTO  | the user asks an agent to do it; its own sequence, never cycled to |
| PROG  | an agent (tagged =:auto:=) or the user is working on it       |
| EVAL  | ready for the user or an agent reviewer                       |
| HOLD  | waiting, usually on the user's answer in =Dialog=             |
| DONE  | finished                                                      |

A task is an AUTO heading in the agenda files. Its property drawer names the machine to run it (=HOST=) and the agent to start (=AGENT=), beside =ID=. When either is missing, the dispatcher fills it from one tag naming a known host or agent, on the heading or else in =#+FILETAGS=, such as =:kit:=, =:pi:cog:=, or =:claude:kit:=, or else from =dispatch.host= and =dispatch.agent= in June's =config.json= (the first known host and pi without them). Only the dispatcher on the resolved host acts, and it writes the values into the drawer when it claims the task, as it does =ID=. From then on the drawer decides and the tags are decoration. A task with two host tags, two agent tags, or an unknown =HOST= or =AGENT= is skipped, with a log line, until that is fixed. The dispatcher starts pi or Claude Code, selected by =AGENT=. A heading the user typed launches once it has stayed unchanged for =dispatch.settle= seconds (120 by default); one June wrote launches at once. =SCHEDULED= delays a task and a repeater makes it recur. While the agent works, the task is =PROG= with an =:auto:= tag, so it stands apart from =PROG= work the user is doing; leaving =PROG= removes the tag, whether through =org-dispatch finish= or =retry=, a hold, =org-edit=, or the user's own change, which the dispatcher notices within a minute. Properties adjust a run:

| Property  | Default          | Effect                                      |
|-----------+------------------+---------------------------------------------|
| REVIEW    | yes              | =no= lets the agent finish DONE             |
| DEPLOY    | no               | =yes= allows deploying                      |
| BRANCH    | current          | push to this branch                         |
| MODEL     | agent's default  | model passed to the selected agent          |
| DIR       | project checkout | working directory                           |
| RETRY     | 0                | times the agent may reschedule a one-off    |
| DEPENDS   | none             | space-separated prerequisite =id:UUID= references |

The dispatcher adds =REPEAT_TO_STATE: AUTO= to repeating tasks so they return to AUTO, not TODO.

Both agents run unattended: pi with =--no-approve=, Claude Code with =--dangerously-skip-permissions=. The task and dispatch prompt set the limits on their work. =MODEL= uses the selected agent's native syntax; =ORG_DISPATCH_MODEL= supplies a default for pi only. Each run has an =auto · HEADING= session name and a =herdr:HOST/AGENT:UUID= link. Resuming reuses a live pane for that host and agent, or starts pi with its session file or Claude with =--resume UUID=; both receive the same task and Dialog prompt. Claude's working directory must already be trusted. A trust or login dialog during startup puts the task on HOLD with the pane ID in Dialog, rather than opening another blocked tab each minute. The dispatcher never answers those dialogs.

Agents end each turn with one of:

#+begin_src sh
org-dispatch finish ID EVAL|HOLD|DONE "note" --headline "your line" # HOLD needs a question
org-dispatch retry ID WHEN "what it waits for" # only when RETRY > 0
#+end_src

=--headline= is optional for older workers. New worker prompts request one line in the worker's own voice, saying only what its Outcome or Dialog records (the finish note for a repeating run). It must be non-empty plain text, without surrounding whitespace or line breaks. =finish= writes it verbatim to the task's =DISPATCH_HEADLINE= property in the same save as the state change, replaces any old value, and removes it when omitted. Claiming a new run clears the property. Nothing in the daemon authors a headline.

On an EVAL, DONE, or HOLD state-change notice, June's existing follow check adds the exact headline to the text she reads and to =june.input.data.follow= as ={title, signal, headline, agent?, session?}=. Agent and session come from the task's latest Herdr link on its followed host, even without a live pane. No headline means unchanged notice text and data. Progress, blocked-agent, and stalled notices do not reuse a headline. A repeating DONE still returns to AUTO through Org and does not create a new terminal follow event. No extra monitor or comic presentation is added.

The dispatcher and prompt are pinned packages: update the June input and activate each launching host to use the new finish option and prompt. Pull the checkout and restart an idle June daemon to use headline-aware follow notices. Checkout-linked skills apply at once, so their new finish instructions are conditional on dispatcher deployment.

The user grants AUTO. June may queue new AUTO tasks and, when the user explicitly asks, resume existing TODO, EVAL, or HOLD tasks under her =AGENTS.md=. They use the same =org-edit= command; instructions define who may grant AUTO. Workers may create new tasks through =plan= only for a plan the user explicitly requested. For an existing task, =retry= is the one worker exception: it returns a task the user allowed to retry to AUTO, lowers =RETRY=, and schedules it for =WHEN=, at least 15 minutes away.

** Dependencies and plans
A task with =:DEPENDS: id:UUID id:UUID= stays AUTO until every prerequisite is DONE. EVAL never unlocks another task, even with a =DEPENDS_ON_STATE= property. Review belongs to the current task: Jon or an authorized agent reviewer accepts it after checking the evidence. Required review still ends at EVAL; with =REVIEW: no=, a worker should use DONE once its checks verify the requested work. Name any remaining human judgment, visual review, or physical check instead of leaving generic testing for Jon.

The dispatcher resolves IDs in the agenda files and their =archive.org= and =archive/= directories, walking parent directories up to the Org root. It skips Syncthing conflict copies. Missing or duplicate IDs, malformed references, HOLD prerequisites, and cycles block the dependent without changing its state. =org-dispatch scan= reports =waiting on HEADING (STATE)= or =blocked on REASON=, including transitive root blockers. A waiting task consumes no agent slot, working-directory slot, or RETRY budget. Run notifies once per dependent and blocker until it clears or changes; scan never sends those notices. Existing SCHEDULED, settling, and concurrency rules still apply after dependencies are satisfied. Launch rechecks readiness before opening a Herdr tab; changing a prerequisite after launch does not cancel work already started.

The task prompt includes each immediate prerequisite's title, file, state, finish note and Outcome. =finish= saves the note in =DISPATCH_FINISH=, and claiming a new run clears it. Older tasks without a finish note still supply their Outcome. Repeating tasks return to AUTO, so a completed iteration is not a permanently satisfied prerequisite. Use a separate one-off acceptance task when that is the intended gate.

When Jon explicitly requests a new plan, June or a coding agent may queue its new tasks with =org-dispatch plan SPEC.json=. This is not permission to resume existing headings or invent autonomous follow-up work. Keep the JSON in local runtime storage, not synced Org. Example:

#+begin_src json
{
  "key": "portal-launch-20261101",
  "title": "Portal launch plan",
  "file": "work/studio/portal/portal.org",
  "tasks": [
    {
      "key": "build",
      "file": "work/studio/portal/portal.org",
      "title": "Build the portal",
      "body": "Queued at Jon's request.\n\n** Scope\nBuild and verify the portal.\n\n** Checklist\n- [ ] Build and run the portal tests."
    },
    {
      "key": "check",
      "file": "work/studio/portal/portal.org",
      "title": "Check the built portal",
      "body": "Queued at Jon's request.\n\n** Scope\nVerify the accepted build against the launch requirements.",
      "depends": ["build", "id:00000000-0000-0000-0000-000000000001"]
    }
  ]
}
#+end_src

The plan's file receives a heading and table linking the generated IDs. All target files must already be writable agenda files without conflict copies. Task keys and the plan key are plain names; titles have no TODO keyword or tags, and body text has no top-level heading or property drawer. =depends= accepts task keys, including forward references, or existing =id:UUID= references, including archived tasks. Optional task settings are =host= and =agent= (June's defaults), =dir= (existing absolute or =~/= directory), and =review= (true by default, false only when Jon waives separate review). No deployment permission is granted.

The command validates the whole graph before publishing, creates AUTO headings, and prints their IDs and files. It starts no dispatcher or agent; the normal timer picks up eligible tasks without settling. Each file is replaced atomically, but the whole plan is not one cross-file transaction. Independent or already-satisfied tasks may launch while another file is still being published. Replay the same key and unchanged spec after an interrupted or partial write: IDs are stable, existing headings and their state are preserved, and missing tasks or the plan table are restored. A changed spec under the same key is refused. Concurrent edits detected before a rename are preserved and require replay; the final comparison and rename are not a cross-process lock.

On an existing live chain, deploy the dependency-aware dispatcher to every host that might launch it before removing prose gates or retry schedules. An older dispatcher ignores DEPENDS and would launch those tasks too soon. Keep RETRY for waits outside Org, not task dependencies. Deployment remains a separate, authorized step.

Runtime state lives in =~/.local/state/org-dispatch= on each host and is not synced. Repeating tasks keep 14 run entries in =:LOGBOOK:=; older ones move to =archive.org= beside the task's file.

** States and dates outside dispatch

Agents write headings and body text directly, but leave TODO states,
=SCHEDULED=, =DEADLINE=, and timestamps to Org, so =CLOSED=, repeaters,
=:LOGBOOK:= entries, and weekdays come out as Emacs makes them:

#+begin_src sh
org-edit todo FILE HEADING STATE [--expect STATE] # workers never grant AUTO
org-edit schedule FILE HEADING WHEN|none
org-edit deadline FILE HEADING WHEN|none
org-edit date WHEN                          # print an active timestamp
#+end_src

=--expect STATE= refuses a stale state before saving. June resumes with =org-edit todo FILE HEADING AUTO --expect HOLD --request KEY --host HOST --note "Chose option A. Resume."=. The expected state must be TODO, EVAL, or HOLD. This saves the state, =HOST=, =AGENT= if missing, ID if missing, =JUNE_REQUEST= key, review on, deploy off, and a June entry in Dialog together. It preserves other properties, schedules, and task history. The request key makes a replay return the existing ID without changing the task, even if work has already finished. This form prints JSON rather than the heading. June checks for active linked agents before calling it. Coding workers must not use it to grant AUTO.

=HEADING= is the title without keyword, priority, or tags. When a title
matches twice, name it by its outline path, matched from the end, such as
=Garden / Spring / Planting=, or by =id:UUID=; a path that still matches twice
is refused. =WHEN= is one date (=2026-10-30=,
=+3d=, =fri=, =today=), an optional time or range (=14:00=, =9:00-10:30=), and
optional cookies (=+1w=, =.+1d=, =-2d=). Words Org would silently read as
today, such as =next tuesday=, are refused.

It runs Emacs in batch with =org-dispatch.el='s keywords, like the
dispatcher, rather than talking to a running daemon. Several Emacs daemons
may visit the file, so the file on disk is the shared truth; Emacs should
auto-save visited Org buffers and revert on change. It refuses =asana.org= and
Syncthing conflict copies. From a checkout, run it as
=bash org/edit/org-edit=.

** Tests

#+begin_src sh
org/tests/test-org-dispatch
org/tests/test-org-edit
#+end_src

The tests need =emacs= on =PATH= and use temporary Org files and state. A
fake =herdr= that always fails keeps the dispatcher test away from any
running server; another that records its calls checks that a run opens in
the Herdr workspace named for its Org file, which is its project for a
=work/<domain>/<project>/<project>.org= file, and that =herdr-link= reopens
a dispatched session there.

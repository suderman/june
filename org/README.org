* Org agent system

Org files assign work to agents, and June runs that system: she queues and follows tasks with her own tools (=src/tools/org.ts=, =dispatch.ts=, =follow.ts=), and this directory holds the commands and prompts underneath.

#+begin_src text
org/
├── dispatch/org-dispatch.el   dispatcher, run by Emacs in batch
├── dispatch/org-dispatch      command-line wrapper
├── edit/org-edit              TODO states and dates set by Org for agents
├── links/june-links.el        file links opened in interactive Emacs
├── prompts/                   task.org and nudge.org, sent to the agent
├── bin/herdr-link             stamp and follow herdr: links
└── tests/                     batch tests with fixtures
skills/                        project-org-tasks, org-triage, org-conflicts, for every agent
#+end_src

** Where each piece runs

June's Home Manager module (=homeModules.default=, see the main README) builds =org-dispatch=, =org-edit=, and =herdr-link= from the same commit as the package, with =ORG_DISPATCH_EL=, =ORG_DISPATCH_PROMPTS=, and =ORG_EDIT_EL= set to that commit, and with =programs.june.dispatch.enable= runs the dispatcher every minute with a systemd user timer. The host provides Herdr and the agents it dispatches, pi or Claude Code. A system flake pins June as an input, so the dispatcher always runs with the prompts from the same commit, and rolling back the system rolls both back. Changing either one needs an input update and a rebuild. To test local changes before pushing, rebuild with =--override-input june path:<checkout>=.

The skills are different. =~/.agents/skills.json= lists them as local entries with two paths, so =agents apply= links =~/.agents/skills/project-org-tasks= and =org-triage= into this checkout when it is there, and edits apply at once; elsewhere it links the pinned copy that =programs.june= places at =~/.config/june/skills=. Every harness finds them in =~/.agents/skills=. Rebuild before publishing skill text that describes a new command.

An Emacs configuration that shows these tasks needs the same TODO keywords, and the =herdr:= link handler if it opens session links. Change both copies of the keywords together.

** File links in interactive Emacs
=links/june-links.el= belongs to June but runs in the user's interactive Emacs, not the batch dispatcher. Load it at startup on the desktop and in the Android Emacs APK. With =use-package=:

#+begin_src emacs-lisp
(use-package june-links
  :vc (:url "https://github.com/suderman/june" :lisp-dir "org/links" :rev :newest)
  :ensure nil
  :demand t
  :custom (june-host "kit"))
#+end_src

=package-vc= fetches June and builds the =org/links= Lisp directory as the package, so the same setup works without a separate June checkout on the desktop or phone. Set =june-host= to the host running June; it defaults to the current machine. Upgrade with =package-vc-upgrade-all= when this integration changes.

The desktop calls =(june-open PATH SEARCH)= through =emacsclient=. The Android app keeps using =org-protocol://june-open?path=…&search=…=; the package registers that handler and loads =org-protocol= at startup in the APK. Files under =~/org= open locally on each device. Other files open on =june-host=, through TRAMP from other devices, including Android. Heading, custom-ID, line and text searches follow Org's file-link rules. Link arguments remain data, never Lisp to evaluate.

Android TRAMP needs working SSH from the Emacs APK. With shared-UID Termux integration, SSH uses Termux's host config and agent. If the key is locked, run =~/bin/ssh-unlock= in Termux and approve the fingerprint before opening a remote link. The current phone setup keeps the key unlocked for one hour. Synced Org links do not need SSH.

** The contract

States, set in =org-todo-keywords= here and in the user's Emacs configuration:

| State | Meaning                                                       |
|-------+---------------------------------------------------------------|
| TODO  | the user's task                                               |
| AUTO  | the user asks an agent to do it; its own sequence, never cycled to |
| PROG  | an agent (tagged =:auto:=) or the user is working on it       |
| EVAL  | ready for the user or an agent reviewer                       |
| HOLD  | waiting, usually on the user's answer in =Dialog=             |
| DONE  | finished                                                      |

A task is an AUTO heading in the agenda files. Its property drawer names the machine to run it (=HOST=) and the agent to start (=AGENT=), beside =ID=. When either is missing, the dispatcher fills it from one tag naming a known host or agent, on the heading or else in =#+FILETAGS=, such as =:kit:=, =:pi:cog:=, or =:claude:kit:=, or else from =dispatch.host= and =dispatch.agent= in June's =config.json= (the first known host and pi without them). Only the dispatcher on the resolved host acts, and it writes the values into the drawer when it claims the task, as it does =ID=. From then on the drawer decides and the tags are decoration. A task with two host tags, two agent tags, or an unknown =HOST= or =AGENT= is skipped, with a log line, until that is fixed. The dispatcher starts pi or Claude Code, selected by =AGENT=. A heading the user typed launches once it has stayed unchanged for =dispatch.settle= seconds (120 by default); one June wrote launches at once. =SCHEDULED= delays a task and a repeater makes it recur. While the agent works, the task is =PROG= with an =:auto:= tag, so it stands apart from =PROG= work the user is doing; leaving =PROG= removes the tag, whether through =org-dispatch finish= or =retry=, a hold, =org-edit=, or the user's own change, which the dispatcher notices within a minute. Properties adjust a run:

| Property  | Default          | Effect                                      |
|-----------+------------------+---------------------------------------------|
| REVIEW    | yes              | =no= lets the agent finish DONE             |
| DEPLOY    | no               | =yes= allows deploying                      |
| LIVE_CONTENT | none          | JSON with approved live content target, actions and limits; separate from code deployment |
| BRANCH    | current          | push to this branch                         |
| MODEL     | agent's default  | model passed to the selected agent          |
| DIR       | project checkout | working directory                           |
| RETRY     | 0                | times the agent may reschedule a one-off    |
| DEPENDS   | none             | space-separated prerequisite =id:UUID= references; =org-edit todo --depends= adds them when June resumes a task |

The dispatcher adds =REPEAT_TO_STATE: AUTO= to repeating tasks so they return to AUTO, not TODO.

Both agents run unattended: pi with =--no-approve=, Claude Code with =--dangerously-skip-permissions=. The task and dispatch prompt set the limits on their work. =MODEL= uses the selected agent's native syntax; =ORG_DISPATCH_MODEL= supplies a default for pi only. Each run has an =auto · HEADING= session name and a =herdr:HOST/AGENT:UUID= link. Resuming reuses a live pane for that host and agent, or starts pi with its session file or Claude with =--resume UUID=; both receive the same task and Dialog prompt. A closed Claude session saved under =~/.claude-NAME= resumes through =claude-NAME=, the account launcher that owns that directory, even when =dispatch.commands= names another such as =claude-auto=. A session elsewhere, or without that launcher, uses the configured command in a fresh session as before. Claude's working directory must already be trusted. A trust or login dialog during startup puts the task on HOLD with the pane ID in Dialog, rather than opening another blocked tab each minute. The dispatcher never answers those dialogs.

Dispatched agents end each turn with one of:

#+begin_src sh
org-dispatch finish ID EVAL|HOLD|DONE "note" --headline "your line" # HOLD needs a question
org-dispatch retry ID WHEN "what it waits for" # only when RETRY > 0
#+end_src

=--headline= is optional for older workers. New worker prompts request one line in the worker's own voice, saying only what its Outcome or Dialog records (the finish note for a repeating run). It must be non-empty plain text, without surrounding whitespace or line breaks. =finish= writes it verbatim to the task's =HEADLINE= property in the same save as the state change, replaces any old value, and removes it when omitted. The same save binds it to the effective finish state in =HEADLINE_STATE= and records Unix seconds in =HEADLINE_AT=. Claiming a new run, or finishing without a headline, clears all three properties. Nothing in the daemon authors a headline. The shared task reader accepts only a state-matching, timestamped headline from the task's own drawer; an old bare =HEADLINE= has no freshness evidence and is omitted without changing the ordinary report.

Manually started workers use =org-edit todo FILE HEADING EVAL --headline "your line"=, choosing EVAL, DONE, or HOLD under their normal review rules. Optional =--expect STATE= refuses a stale write before changing the report. The command uses the same headline validation and state/stamp writer as =finish=, and clears all three report properties when the flag is omitted, including on a trivial same-state write or a resume. A replayed =--request= does not alter a later run's report. Org's repeat behavior and review/deploy properties stay unchanged; no dispatch request or ID is added for manual work. Existing follows read the result without enrolling a task or messaging its worker. The shared skill's Finish and synchronize rule requests a fresh own-voice headline after substantive work; trivial state changes omit it.

The report properties are =HEADLINE=, =HEADLINE_STATE=, and =HEADLINE_AT=. The former =DISPATCH_HEADLINE*= spelling is not read or migrated. Older tasks without a fresh report still produce ordinary state news without a quote.

On an EVAL, DONE, or HOLD state-change notice, June's existing follow check adds the exact headline to the text she reads and to =june.input.data.follow= as ={title, signal, headline, agent?, session?}=. Agent and session come from the task's latest Herdr link on its followed host, even without a live pane. No headline means unchanged notice text and data. Progress, blocked-agent, and stalled notices do not reuse a headline. A repeating DONE still returns to AUTO through Org and does not create a new terminal follow event. No extra monitor or comic presentation is added.

The existing general watch uses that same reader for dispatched tasks June does not explicitly follow. Its batched notice includes each fresh line beside the corresponding task and carries =june.input.data.watch= as an array of the same ={title, signal, headline, agent?, session?}= objects. A report's stamp must be at least the dispatch run's start and newer than the previous observation. Before admitting delayed news, the watch checks that each quote still matches the task and that no later run has started. A stale quote is removed from text and data; the ordinary state report and its timing stay unchanged. No headline means the original notice and entry shape. Repeating DONE returns to AUTO and supplies no headline news.

The Org commands and dispatcher prompt are pinned packages: update the June input and activate each working host for =org-edit= and each launching host for =org-dispatch= and its prompt. Pull the checkout and restart an idle June daemon for the matching reader. Checkout-linked skills apply at once, so their new finish instructions are conditional on headline-capable commands being deployed. Older installed commands finish without the flag until the host is updated; do not hand-write report stamps as a workaround.

The user grants AUTO. June may queue new AUTO tasks and, when the user explicitly asks, resume existing TODO, EVAL, or HOLD tasks under her =AGENTS.md=. They use the same =org-edit= command; instructions define who may grant AUTO. Workers may create new tasks through =plan= only for a plan the user explicitly requested. For an existing task, =retry= is the one worker exception: it returns a task the user allowed to retry to AUTO, lowers =RETRY=, and schedules it for =WHEN=, at least 15 minutes away.

** Scoped live-content approval
When Jon explicitly approves a targeted live content change, June passes =liveContent: {target, actions, limits}= and the fresh =org_read_task= revision to =org_resume_task=. The target names the live site and exact page, content or templates. Actions name only approved reads/writes, backups, targeted rollback, CSS/cache work and verification. Limits preserve backup, reconciliation and rollback requirements and exclude unrelated changes. Each field is one non-empty line of at most 4000 characters, without control characters or secrets. The resume note records Jon's approval and identifies any older manual-only or production-access gate it supersedes. AUTO alone, a worker's HOLD question and a review verdict never imply this approval.

The protected backend is =org-edit todo FILE HEADING AUTO --expect TODO|EVAL|HOLD --request KEY --host HOST --revision SHA256 --live-content JSON --note TEXT=. It checks the full task revision under the existing local dispatcher lock, keeps =REVIEW=yes= and =DEPLOY=no=, and saves the grant and an appended Dialog entry with AUTO. Prior scope, schedule, sessions and Dialog remain intact. The grant is stored in =LIVE_CONTENT= with a =LIVE_CONTENT_SCOPE= SHA256 binding it to the task ID, title, explicit DIR property and unique non-empty Scope section. This does not add permission-property writes to =org_update_task=.

On later authorized resumes, omit =liveContent= to keep a valid grant, pass a new object to reconfirm changed scope, or pass ="none"= to revoke it. Each needs a fresh full-task revision. Changing the bound scope, malformed or incomplete stored approval, and stale revisions refuse resume without saving; the dispatcher also skips invalid approval and refuses to render its prompt. Mutable progress, state and Dialog do not invalidate the binding, so June must read those and other task changes before retaining approval. Material changes outside the bound fields require reconfirmation too. Replayed request keys write nothing, even after completion. Revocation removes both properties and records it in Dialog; no-deploy and ordinary ask-before-production rules apply again.

The generated policy permits only the named live content operations without asking Jon again. It supersedes historical manual-only, ask-before-production and no-deploy wording only for those operations. Code and theme/plugin deployment, database pushes, system activation/install, service changes, unrelated sites and client communications remain forbidden. These are instructions for unattended workers, not a command sandbox or a signed approval token. The local lock coordinates dispatcher and Org commands, not interactive saves or Syncthing on another host.

Apply by updating the June Nix input and activating matching =org-edit=, =org-dispatch= and prompts on every editing/launching host, then pulling the checkout and restarting the idle June daemon. A checkout pull or daemon restart alone does not update pinned Org commands. An older installed =org-edit= refuses unknown permission/revision flags before writing; June must report that gap, never drop those fields or hand-edit properties. Applying this code does not resume a held task. Re-read the task and approval, then use a separate authorized resume after activation. Fixture tests do not approve live work or prove a production change.

** Correcting task wording
June uses =org_update_task= to rename stale tasks or replace outdated scope when Jon asks to organize or update his work. Read the whole task and Dialog with =org_read_task= first, then pass its =revision=, an optional =title= and/or =scope=, and a one-line =note= recording the request. Title text excludes state, priority and tags. Scope accepts prose and lists, not headings, drawers, planning lines or directives.

The backend is =org-edit update-task FILE HEADING JSON=. JSON contains =revision=, =request=, =note= and =title= and/or =scope=. June supplies a durable request key. The command holds the local dispatcher lock, checks the full subtree's SHA256 and saves once. It changes only the title and selected prose, adds an ID if needed, and records the old wording as escaped JSON in an appended Dialog entry. State, priority, tags, dates, other properties, checklist, findings, session links and earlier Dialog stay intact. A repeated request finds its receipt even after a title-only selector has changed and writes nothing. Reusing a request key for different content is refused.

=scope= replaces the prose in one direct =Scope= section. Without that section, it replaces the heading's own prose below metadata and before child sections, as older manual tasks are written. Old prose remains in Dialog. Multiple Scope sections, nested headings or other structure in the selected prose require reconciliation rather than automatic replacement. Introductory history outside an existing Scope section is not replaced. This command cannot waive permission or approval gates; the note must say what Jon actually requested.

Only plain headings and TODO, HOLD or EVAL tasks are eligible. AUTO, PROG, DONE, active or uncertain dispatcher receipts, review-contract tasks, remote assignments and active, blocked, remote or unknown linked workers are refused. The command sends no input and starts no work. Stop and reconcile active work through the existing workflow first; resuming remains a separate authorized action. Agenda membership, protected files, duplicate IDs, Syncthing conflicts and changes on disk are checked before saving.

Apply this tool by updating June's Nix input and activating the updated =org-edit= on the editing host, then pulling the checkout and restarting June only when idle. A checkout pull alone does not update the installed Org command. Until activation, an older =org-edit= refuses the new command without writing; June must report that limit, not edit raw text. Fixture tests do not imply activation or a live task edit.

** Dependencies and plans
A task with =:DEPENDS: id:UUID id:UUID= stays AUTO until every prerequisite is DONE. EVAL never unlocks another task, even with a =DEPENDS_ON_STATE= property. Review belongs to the current task: Jon or an authorized agent reviewer accepts it after checking the evidence. Required review still ends at EVAL; with =REVIEW: no=, a worker should use DONE once its checks verify the requested work. Name any remaining human judgment, visual review, or physical check instead of leaving generic testing for Jon.

The dispatcher resolves IDs in the agenda files and their =archive.org= and =archive/= directories, walking parent directories up to the Org root. It skips Syncthing conflict copies. Missing or duplicate IDs, malformed references, HOLD prerequisites, and cycles block the dependent without changing its state. =org-dispatch scan= reports =waiting on HEADING (STATE)= or =blocked on REASON=, including transitive root blockers. A waiting task consumes no agent slot, working-directory slot, or RETRY budget. Run notifies once per dependent and blocker until it clears or changes; scan never sends those notices. Existing SCHEDULED, settling, and concurrency rules still apply after dependencies are satisfied. Launch rechecks readiness before opening a Herdr tab; changing a prerequisite after launch does not cancel work already started.

The task prompt includes each immediate prerequisite's title, file, state, finish note and Outcome. =finish= saves the note in =DISPATCH_FINISH=, and claiming a new run clears it. Older tasks without a finish note still supply their Outcome. Repeating tasks return to AUTO, so a completed iteration is not a permanently satisfied prerequisite. Use a separate one-off acceptance task when that is the intended gate.

When Jon explicitly requests a new plan, June or a coding agent may queue its new tasks with =org-dispatch plan SPEC.json=. This is not permission to resume existing headings or invent autonomous follow-up work. Keep the JSON in local runtime storage, not synced Org. Example:

#+begin_src json
{
  "key": "portal-launch-20261101",
  "title": "Portal launch plan",
  "file": "work/studio/portal/portal.org",
  "tasks": [
    {
      "key": "build",
      "file": "work/studio/portal/portal.org",
      "title": "Build the portal",
      "body": "Queued at Jon's request.\n\n** Scope\nBuild and verify the portal.\n\n** Checklist\n- [ ] Build and run the portal tests."
    },
    {
      "key": "check",
      "file": "work/studio/portal/portal.org",
      "title": "Check the built portal",
      "body": "Queued at Jon's request.\n\n** Scope\nVerify the accepted build against the launch requirements.",
      "depends": ["build", "id:00000000-0000-0000-0000-000000000001"]
    }
  ]
}
#+end_src

The plan's file receives a heading and table linking the generated IDs. All target files must already be writable agenda files without conflict copies. Task keys and the plan key are plain names; titles have no TODO keyword or tags, and body text has no top-level heading or property drawer. =depends= accepts task keys, including forward references, or existing =id:UUID= references, including archived tasks. Optional task settings are =host= and =agent= (June's defaults), =dir= (existing absolute or =~/= directory), and =review= (true by default, false only when Jon waives separate review). No deployment permission is granted.

The command validates the whole graph before publishing, creates AUTO headings, and prints their IDs and files. It starts no dispatcher or agent; the normal timer picks up eligible tasks without settling. Each file is replaced atomically, but the whole plan is not one cross-file transaction. Independent or already-satisfied tasks may launch while another file is still being published. Replay the same key and unchanged spec after an interrupted or partial write: IDs are stable, existing headings and their state are preserved, and missing tasks or the plan table are restored. A changed spec under the same key is refused. Concurrent edits detected before a rename are preserved and require replay; the final comparison and rename are not a cross-process lock.

June removes selected existing edges with =org_remove_dependencies= only when Jon asks. She reads the whole task and Dialog, passes the =org_read_task= revision and expected TODO/EVAL/HOLD/AUTO state, and supplies a note recording his approval and specifically which earlier prose gate, if any, it lifts. =org-edit remove-dependencies FILE id:UUID --expect STATE --revision SHA256 --remove "id:UUID id:UUID" --request KEY --note TEXT= takes the same local flock as =org-dispatch run= and refuses contention rather than waiting behind a launch. It runs only on the task's dispatcher host, refuses active dispatcher runs and linked workers, checks the task revision and validates the remaining dependency graph before saving. An explicitly selected missing prerequisite can be removed; an absent edge, ambiguous task ID or invalid remaining edge is refused. June checks remote linked workers too.

Removal preserves unrelated edges, identity, schedule, scope and prior Dialog. It appends the note and, for AUTO, changes the task to HOLD in the same atomic file replacement. Other states stay unchanged. No dispatcher or worker is started. A replay with the same request key writes nothing, even if the task has since resumed. Prose instructions are separate from DEPENDS: do not erase old Dialog or silently waive scope. Re-read the paused task, resolve any remaining conflict with Jon, then use a separate authorized =org_resume_task= to start work. Do not remove DEPENDS by hand on AUTO, since autosave can expose the task to the dispatcher before its prose correction is saved. The installed org-edit needs the updated wrapper, flock and Herdr before this tool is usable.

On an existing live chain, deploy the dependency-aware dispatcher to every host that might launch it before removing prose gates or retry schedules. An older dispatcher ignores DEPENDS and would launch those tasks too soon. Keep RETRY for waits outside Org, not task dependencies. Deployment remains a separate, authorized step.

Runtime state lives in =~/.local/state/org-dispatch= on each host and is not synced. Repeating tasks keep 14 run entries in =:LOGBOOK:=; older ones move to =archive.org= beside the task's file.

** Retiring panes of DONE tasks
When =dispatch.retire= is =true= in June's config, each =org-dispatch run= closes the Herdr panes of finished dispatcher work before launching tasks. It is off by default, and nothing else enables it. =org-dispatch reconcile --dry-run= prints the same inventory as JSON, with an =eligible=, =stable= and =close= value and the skip reasons for every live agent. It changes nothing.

A pane is eligible only when all of these hold: its Herdr agent name is =auto-ID8-HHMMSS=, which the dispatcher gives the agents it starts and Herdr clears when that occupant exits, is replaced or Herdr restarts; the name's ID8 matches the one task, found exactly once across agenda files and their archives, whose Sessions link names the pane's exact pi or Claude session; that task is DONE, not repeating and not part of a review loop, and its file has no Syncthing conflict copy; no other task links the session and no other live pane runs it; no active dispatcher run uses the pane or session; any allocation receipt for the pane names this task and session; the agent is idle or done and the pane is not focused; the saved session can be reopened from its link (a pi session file, or a Claude session under =~/.claude-NAME= with =claude-NAME= on PATH); and two reads of Herdr and of Org within the run agree.

An eligible pane is closed only when the previous enabled run saved exactly the same observation of it: pane, terminal, tab, name, agent, session, status, state and completion sequence numbers, focus and revision. Any change restarts the wait. Observations are saved in =retire.json= beside the dispatcher state before anything is closed, so a restarted dispatcher continues the wait and a crash costs one extra run. Just before closing, =herdr agent get NAME= must return the same observation; Herdr resolves the name only to the occupant the dispatcher named, and closed pane IDs are never reused. Then =herdr pane close PANE= closes that one pane, which sends SIGHUP to the agent. Closing a tab's last pane also removes the tab. Org Sessions links and saved sessions are left alone, and the log names the =herdr-link attach= link that reopens the session.

Herdr 0.9.5 (protocol 22) has no close that checks the occupant, so the final read and the close are separate calls, about 15 ms apart. Jon accepted that race: input reaching an unfocused, idle pane of a DONE task inside it is lost along with the turn it started, while earlier history stays in the session file. The run holds the dispatcher lock, which June's Org commands share, so a resume through June or the dispatcher cannot interleave. Jon's editor, Syncthing and other hosts do not take the lock; a task reopened there after the final Org read can lose its pane, and resuming it reopens the saved session. Panes restored after a Herdr restart have no name and are never closed automatically. Panes the dispatcher did not start, and Claude sessions under =~/.claude=, are skipped.

The dispatcher saves historical allocation receipts in =~/.local/state/org-dispatch/panes/= when it knows the task, agent session and pane/tab it allocated. A receipt survives release of the active watcher slot at EVAL, HOLD or DONE and can be read by another process after a restart. Reusing an existing live pane does not create a new allocation receipt. Surviving legacy tab allocations are retained when watched; missing old receipts are not reconstructed from Org links. A receipt records a past allocation, not current ownership. Retirement uses one only to refuse a pane whose receipt names a different task or session. Receipts are not pruned here.

The watcher no longer closes whole tabs/workspaces after DONE or repeating AUTO, or sends unguarded Escape merely because someone changed a task's state. Missing or duplicate IDs keep a running watcher for retry, rather than discarding it during an archive move. Existing explicit-stop and uncertain-startup protections remain separate. Existing ordinary PROG timeout interrupts and nudges remain unchanged and are not made session-atomic here. No child-process exit guarantee is added.

Saved =herdr:= session links remain in Org. =herdr-link attach= finds an existing session by host and agent, or routes pi to =pi --session FILE= and Claude to =--resume UUID= through the launcher for the config directory holding the session: =claude-NAME= for =~/.claude-NAME=, otherwise =claude-direct= (or =claude=) with =CLAUDE_CONFIG_DIR= set. Account launchers fix =CLAUDE_CONFIG_DIR=, so plain =claude --resume= cannot find another account's session. The archive need not be open: lookup uses saved session files. An archived-only link may lose automatic project-workspace selection, since that naming search uses live Org files. =jump='s pane hint is not session identity proof. Fixture tests exercise archived-link routing and unchanged Org/session hashes. A real check in an isolated Herdr server closed a real pi pane and a real =claude-home= pane, then reopened each through =herdr-link attach= with its earlier turn intact. The dispatcher's own launch resumed the same Claude session through =claude-home= with =claude-auto= configured.

Publishing this needs a June input update and activation of the pinned dispatcher on each launching host; pulling the checkout or restarting June does not update the installed dispatcher. Enabling it is a separate step after that.

** Stopping and reassigning a running task
June uses =org_stop_task= when Jon asks to stop a running dispatcher task or change its agent. She reads the whole task and Dialog first and passes its ID, =org_read_task= revision and a one-line note recording his instruction. The tool calls =org-edit stop-task FILE id:UUID --revision SHA256 --request KEY --note TEXT=. It needs the updated installed Org commands, not =HERDR_ENV= or generic terminal-control permission. It works only on the task's local dispatcher host, with a unique live agenda ID, PROG state and a matching dispatcher run and session. It refuses unmanaged and remote workers, stale reads and ambiguous identities.

The command holds the same local flock as launch, finish, retry and Org state changes. It first saves a durable =stopping= record, then parks the task at HOLD, removes its auto tag through Org, clears the old headline and appends the instruction to Dialog. It confirms two idle/done observations or the session's exit before writing a stop receipt and =stopped= state. It sends no input. Herdr protocol 22 accepts only a mutable name or pane target for =agent.send_keys=, with no expected-session or generation precondition. Discovery followed by named Escape can interrupt a replacement worker, so working or blocked sessions fail closed. June cannot yet interrupt an active worker automatically. She must ask Jon to interrupt that exact session manually, then retry this tool to confirm it settled. An identity-bound Herdr server operation is required to remove this constraint.

A cooperative stop/save-handoff prompt cannot safely replace manual interruption with Herdr 0.9.5, protocol 22. =agent.prompt= accepts =target=, =text= and optional =wait=, but no expected-session/generation. Its target is the current named or pane occupant when the server resolves it, not the session June previously read. The server rejects an already recognized blocked dialog and checks foreground ownership, then queues bracketed-paste-aware text and delayed Enter to that terminal. This queue orders terminal bytes; it does not promise a native agent message queue, when a working agent will read the instruction, or that a later dialog/replacement cannot receive pending input. =--wait= binds observations to the resolved terminal with name/kind and lifecycle checks, not an expected worker session/generation. It cannot correct an earlier discovery-to-submission replacement. It tracks lifecycle rather than the submitted instruction; completion of an already active turn can satisfy it. Success or timeout is never evidence that a stop instruction was handled. See the version-pinned [[https://github.com/herdrdev/herdr/blob/v0.9.5/docs/next/website/src/content/docs/agent-automation.mdx][agent automation]] and [[https://github.com/herdrdev/herdr/blob/v0.9.5/src/app/api/agents.rs][prompt validation and submission]] contracts.

Task-stop therefore sends neither normal prompts nor raw keys, and does not claim cooperative or queued delivery. Safe cooperative delivery needs an expected-session/generation precondition plus protection against blocked dialogs and occupant changes through deferred delivery. A submission receipt would still need separate original-worker settlement/exit confirmation, with replacement blocked while uncertain.

Unknown identities or status, command failures and timeouts also leave the task parked with an unconfirmed stop. Those stops reserve their directory and slot, never receive nudges, and block resume, finish and retry. Read the task and inspect Herdr before retrying the stop; a new tool call can recover the same pending operation. June must not bypass it with raw keys, manual AUTO, process kills or a duplicate task.

A confirmed stop preserves assignment, ID, scope, findings, prerequisites, schedule and session history. It does not finish the task, close tabs or prove that the worker's child processes ended. Re-read the parked task before a separate =org_resume_task= with Jon's requested agent, and only when he authorized reassignment. All stopped sessions remain in history and are excluded from dispatcher resume, including after repeated agent switches. =JUNE_STOP_SESSIONS= accumulates exclusions and preserves the older =JUNE_STOP_SESSION= value. A replay of the original stop cannot park a later run. Late finish/retry and general =org-edit todo= writes from stopped or superseded workers are refused. General state writes use inherited Pi/Claude context or Herdr caller identity to distinguish cooperative workers from human shells and June's daemon. These guards are not an authorization boundary against arbitrary file edits.

Apply the June input update and activate the updated =org-edit= and =org-dispatch= together on each launching host before using this workflow. That needs Jon's approval for the system flake change and activation. Updating only the daemon checkout is insufficient, because an old dispatcher can still nudge or accept late results. Then restart June when idle to load the new tool. Until that activation, the tool reports the old installed command and writes nothing. No activation or live worker test is implied by the fixture tests.

** Independent development and review
June's =development-review= skill and =org_review_task= coordinate an explicitly delegated loop. This is a set of locked handoffs on ordinary Org tasks, not a new dispatcher. One development task owns the outcome; separate review tasks preserve immutable exact-commit verdicts, evidence and session links. Every round starts a fresh reviewer in a detached private clone. Reviewers can read previous rounds for continuity, but never share the development worktree or Git metadata. The clone has no remote. These are cooperative permissions, not a sandbox against arbitrary shell or file writes.

The initial contract records the user's delegation of in-scope fixes, separate permissions, agent reviewer responsibility/checks, and an explicit list of human checks. EVAL still means ready for someone to review or test, whether an agent, Jon or both. Feasible agent checks belong to agents. Taste, physical-world checks, some phone actions and reboot/boot sequences can remain with Jon. An agent pass never stands in for those checks or grants permission to deploy.

The helper is part of =org-edit=. June uses the tool; the underlying commands accept one JSON argument:

#+begin_src sh
org-edit review start FILE id:DEVELOPMENT '{"revision":"ORG_SHA256","commit":"FULL_GIT_SHA","authorization":"Jon delegated bounded in-scope fixes and independent review.","permissions":"Local checks; developer commits/pushes already authorized; remote reads only as scoped; no remote writes, activation, services or deployment.","checks":"Independent reviewer tests the requirements and failure paths.","human":["Specific physical or judgment check"],"agent":"pi"}'
org-edit review verdict FILE id:REVIEW '{"commit":"FULL_GIT_SHA","verdict":"fixes","note":"Specific findings and evidence."}'
org-edit review advance FILE id:DEVELOPMENT '{"revision":"ORG_SHA256","commit":"FULL_GIT_SHA"}'
org-edit review human FILE id:DEVELOPMENT '{"revision":"ORG_SHA256","commit":"FULL_GIT_SHA","checks":["Specific physical or judgment check"],"note":"Jon explicitly accepted this check on this commit."}'
#+end_src

=start= needs a one-off EVAL development task, its current =org_read_task= revision, a clean local Git source branch at the full 40-character commit, and settled/exited linked workers. First start also requires the contract fields above, including =human: []= if no human checks remain. Later starts use the stored contract. Each command runs on the task's dispatcher host under the same non-waiting local launch lock. Source assignment and branch cannot silently change. Live IDs must be unique, files must be in the agenda and Syncthing conflict copies must be resolved first.

=start= creates one ordinary AUTO review task and its =REVIEW_PARENT=/=REVIEW_COMMIT= link in the same atomic file save as the development task's =DEV_REVIEW= contract/pointer and round history. No session is inherited by the review task. Snapshots live on that host at =~/.local/state/org-work/<domain>/<project>/review-loop/<development-id>/<round>-<commit>/=; the development record names the host and path. Git clone uses =--no-local=, removes origin and checks out the exact detached commit. Existing snapshots must already match and be clean without remotes. Partial/dirty snapshots fail for inspection, never automatic deletion or reset. A crash after a completed clone but before the Org save can replay against that clone. Source changes during review invalidate acceptance rather than modifying the reviewed snapshot.

Only the current dispatcher's reviewer pane/session can record =verdict=, and it must be distinct from every development session in the original task. The snapshot must still be clean at the exact commit. Verdicts are =pass=, =fixes= or =blocked= and cannot be overwritten. Reviewers record full evidence and findings in Outcome, then record the one-line verdict and finish EVAL normally. This records a report, not proof that every claimed test ran. June must read and evaluate the evidence before advancing it. She never treats an ordinary EVAL without a verdict as approval.

=advance= rechecks the development revision, source branch/hash, assignment and linked workers, and requires the current linked review at EVAL with the exact verdict. It closes that review record in the same file save as the development transition. =fixes= returns the original development ID to AUTO with its agent and session history intact, adds the findings/link/permissions to Dialog, and turns deployment off for the fix run. No new implementation scope is granted. A new exact EVAL revision then needs =start=. =pass= closes development only when the contract has no human checks; otherwise it leaves EVAL. =blocked= or a third unsuccessful revision round leaves HOLD and an explicit escalation for Jon. The counter includes revisions changed while awaiting human checks. Do not reset it or create another loop without Jon's decision. A missing verdict, crashed/HOLD reviewer or unchanged revision after disputed findings needs inspection, not an automatic retry loop.

=human= records only Jon's explicit acceptance of named required checks for the current agent-approved source commit. Partial acceptance stays EVAL. Completion requires all checks for the same commit. A new reviewed revision clears previous human acceptance. June's tool calls this list =human=; its CLI JSON calls it =checks=. Required checks outside the stored contract must be resolved with Jon, not silently waived. Source or branch movement, an active/unknown worker or an unconfirmed stop blocks a handoff. The tools send no raw keys or normal Herdr prompts to existing workers.

Replaying the same start/advance/human operation changes neither a later state nor the round counter. Contracts, reports and histories survive closed panes and daemon restarts in Org; existing durable follows survive in June's database. The tool replaces the follow for each review/fix phase and starts only the normal dispatcher. After a crash between save, follow and kick, reading and replaying recovers that handoff without another task or AUTO grant. A replay's returned phase is not proof that a later worker is still running. Follow notices direct June to this workflow instead of generic =org_complete_task=. General =org-edit todo AUTO/DONE= refuses both enrolled development tasks and linked review tasks; worker =finish DONE= still stops at EVAL regardless of =REVIEW: no=. Manual file edits remain outside those cooperative guards.

A review-loop startup error or a =starting= receipt older than ten minutes is not automatically retried. The dispatcher records pane/tab before starting the agent and session identity before claiming the task. It durably marks uncertain launch ownership =launch-uncertain= before parking HOLD, retains its receipt and reserves the worktree/slot. If a crash precedes the HOLD save, the next watch completes the parking. It sends no input, never expires that reservation and refuses resume/finish while ownership is uncertain. Jon must inspect the exact receipt, Herdr and possible child processes; this version has no automatic reconciliation or release command. Do not delete a receipt, bypass HOLD or create another task to retry. Recovery/release requires a separate explicit decision after inspection. These protections apply to reviewer launches and enrolled developer fix launches. Ordinary non-loop startup expiry is unchanged.

The existing dispatcher recovers closed development sessions through native resume or, for custom launchers without a matching Claude account launcher, the full Org record in a fresh session. It serializes tasks sharing a Git worktree root, including different subdirectories and symlink aliases, or the same directory outside Git. Review snapshots have distinct directories, so their tests need no source-worktree writer. Direct shells, child processes and workers outside this dispatcher are not locked by directory exclusion. Inspect them when a handoff is uncertain. Reviewer crashes or partial snapshots are blockers rather than permission to create duplicates. This initial workflow supports one local repository/branch on one host; multi-repository or cross-host loops need a separate decision.

Application needs the matching =org-edit=, =org-dispatch= and task prompt on every launching host, plus June's new tool, conventions and =development-review= skill. Update the June Nix input and activate those hosts with approval, then restart June while idle. The =org-edit= wrapper now includes Git. Register the new skill in June's configured skill roots too. This installation indexes =~/.agents/skills= and =~/profile/skills=, not the packaged root. With Jon's approval, add =~/.config/june/skills= to =skillDirs= in his existing June configuration, preserving the other roots, or register =development-review= through his existing skill-link setup. Updating the input and activating alone does not change those configured roots. After the idle restart, use =skill_read= with =name: development-review= and confirm it returns the new instructions before enrolling a task. Merge the new template convention into an existing AGENTS.md when needed; existing personal conventions are not replaced automatically. None of these application changes is performed by the source update. Updating only the checkout is insufficient. Old installed commands refuse =review= before writing; never imitate the missing command with direct state edits or Herdr input. No activation, service restart or live-worker test is implied by fixture verification. After acceptance and confirmed reviewer exit, disposable snapshots may be removed; retain the Org verdict/evidence records.

** States and dates outside dispatch

Agents write headings and body text directly, but leave TODO states,
=SCHEDULED=, =DEADLINE=, and timestamps to Org, so =CLOSED=, repeaters,
=:LOGBOOK:= entries, and weekdays come out as Emacs makes them:

#+begin_src sh
org-edit todo FILE HEADING STATE [--expect STATE] # workers never grant AUTO
org-edit schedule FILE HEADING WHEN|none
org-edit deadline FILE HEADING WHEN|none
org-edit date WHEN                          # print an active timestamp
#+end_src

=--expect STATE= refuses a stale state before saving. June resumes with =org-edit todo FILE HEADING AUTO --expect HOLD --request KEY --host HOST --note "Chose option A. Resume."=. The expected state must be TODO, EVAL, or HOLD. This saves the state, =HOST=, =AGENT= if missing, ID if missing, =JUNE_REQUEST= key, review on, deploy off, and a June entry in Dialog together. It preserves other properties, schedules, and task history. The request key makes a replay return the existing ID without changing the task, even if work has already finished. This form prints JSON rather than the heading. June checks for active linked agents before calling it. Coding workers must not use it to grant AUTO.

=org_add_task= stamps a new TODO with =JUNE_CREATED: yes= in its property drawer. Reusing a matching task never adds that marker. Resume preserves it but never grants authorship. =org_complete_task= requires a task ID, a June queue/resume request or June-prefixed plan request, and creation evidence: this marker or the older queue/plan authorship line =Queued by June:=. It reads only the task's own drawer, accepts Org's property padding, and still requires EVAL with no outstanding review or decision. Existing review contracts remain enforced by org-edit. Already DONE is a no-op.

Older TODOs created through =org_add_task= have no creation marker. Do not infer authorship from =JUNE_REQUEST= alone, since resuming someone else's task writes that too. Repair an old task's creation metadata only after verifying its original successful creation in June's local conversation history; otherwise leave it for the user. No automatic ownership backfill occurs.

=HEADING= is the title without keyword, priority, or tags. When a title
matches twice, name it by its outline path, matched from the end, such as
=Garden / Spring / Planting=, or by =id:UUID=; a path that still matches twice
is refused. =WHEN= is one date (=2026-10-30=,
=+3d=, =fri=, =today=), an optional time or range (=14:00=, =9:00-10:30=), and
optional cookies (=+1w=, =.+1d=, =-2d=). Words Org would silently read as
today, such as =next tuesday=, are refused.

It runs Emacs in batch with =org-dispatch.el='s keywords, like the
dispatcher, rather than talking to a running daemon. Several Emacs daemons
may visit the file, so the file on disk is the shared truth; Emacs should
auto-save visited Org buffers and revert on change. It refuses =asana.org= and
Syncthing conflict copies. From a checkout, run it as
=bash org/edit/org-edit=.

#+TITLE: June's graphical and voice interfaces

Design notes for a desktop client, an Android assistant, an avatar, and voice. Only the avatar vocabulary and the Android proof of concept are built so far. The work is tracked as Org tasks; this file holds the reasoning those tasks refer to. The recommendations here were accepted as the plan; spikes and experiments still settle their details, and anything still open says so. Research dates from October 2026; recheck versions and prices before relying on them.

* What already exists
The plan builds on these seams rather than beside them.

- One conversation. The daemon owns one root conversation. Telegram's chat map points every allowed user at it, and terminal clients attach to it. =/new= starts a fresh context but keeps the same conversation, so no client needs a conversation list. Graphical clients should not offer =/new= at all.
- A client protocol. Newline-delimited JSON over a 0600 Unix socket (=src/protocol.ts=): =status=, =attach=, =submit=, =command=. =attach= returns a snapshot of the last 200 entries, then Pi Durable's events unchanged, including =text_delta=, tool, run, and inbox events. =submit= carries a client request id namespaced by source, so a retried submit returns the same submission; =whenBusy= chooses steer or follow-up; images travel inline. Durable orders every input in the one conversation, so concurrent clients already serialize. There is no network listener; remote use is =ssh -t host june=.
- A display fold. =src/transcript.ts= turns the snapshot and events into display items with no terminal dependency. It holds the rules other clients would otherwise have to copy: heartbeat and watch looks hidden, patter shown apart, background work tracked, quiet answers dropped. It imports only types from Pi Durable.
- Display-only entries. =june.patter= and =june.work= entries are appended at once, even mid-run, kept out of every model context, compaction, and memory review, and replayed in the snapshot. This is the existing mechanism for presentation events.
- The working context. What the interface brief calls "focus" is the =work= tool in the code: a background =june.work= task that owns a child conversation, runs a brief, and posts one report back as a =[work]= follow-up that June relays. Several briefs can run at once (=WorkDoc.active=), each tied to the run that started it, so stopping that run stops its brief and a stopped brief never reports. Results already return to June rather than writing into the conversation. The code's =focus= tool is a different thing: it switches the main conversation to the careful model. Plans and prompts should keep the code's names.
- Patter. A cheap model writes display-only lines during long waits, sees the real activity, has no tools, and its lines reach chat and focus only as a section marked "not information". It already edits a single Telegram message per wait. It is the natural home for other inconsequential presentation, such as avatar reactions and spoken acknowledgements.
- Notice routing. =src/notify.ts= sends June's own notices (=[work]=, =[follow]=, =[watch]=, heartbeat) to Telegram when the user last spoke there, otherwise to the terminal. It knows two surfaces.
- Telegram voice notes. pi-durable-telegram can transcribe voice notes with Deepgram when =DEEPGRAM_API_KEY= is set, behind a pluggable =Stt= interface (=transcribe(bytes, mime, signal)=). The plan does not use it, since Telegram becomes a fallback client once the Android app exists, but the =Stt= shape is worth reusing.
- Notifications. An ntfy server already runs on the tailnet for Herdr.
- Network. The desktop and the phone are on the same tailnet. The desktop already shares its Hyprland session over it.

* Terminal links
The terminal client handles primary-button clicks on rendered hyperlinks. It uses the desktop's link rules: file links call =june-open= through =emacsclient= with the path and search as Lisp strings, session links call =herdr-link jump=, and web links use =xdg-open=. Unsupported schemes run nothing. Opener failures appear in the terminal status line.

These commands run where the terminal client runs. When =june= attaches through SSH, that is the daemon host, not the machine displaying the terminal. Restart the terminal client to load changes; no daemon restart is needed.

* Browse June's history by day
Decided with Jon on 2026-11-20. Every client shows one of June's days at a time. A day starts at her =rhythm.wake=, not midnight, and is named by the date its morning falls on. The live view, from =attach=, holds only today; =earlier= then says earlier days exist, and at the next day's start the view starts over, empty. Three requests serve the rest, answered once: =days= (each day with conversation and its message count, and which day it is now), =day= (one day's folded view, fixed, by date or by an entry id, naming the item to scroll to), and =search= (what the user and June said, newest first, with each hit's day and a snippet). A moment is an entry id; June links one in her words as =[[june:at/ID][label]]=, and every client opens that link itself.

A client is either on today, live, or on a past day, fixed while today goes on underneath. A past day shows its date and a way back, and sending from it returns to today.

- Terminal: =/day= lists the recent days; =/day DATE= or =/day yesterday= opens one, =/today= returns, =/search WORDS= lists hits with the id =/at ID= opens. =/at= shows the moment's day up to a few items past it, the moment marked. A click on a =june:at= link opens it in place, and the link shows its =/at ID= too.
- Desktop: the masthead's date steps between days with conversation (‹ and ›) and opens a calendar with those days marked and a search whose hits update as the user types (=Browse.qml=). A moment opens its day with its panel outlined in the middle of the strip. The =june-desktop= IPC calls =day DATE=, =at ID=, and =today= do the same.
- Phone: a line under the status line steps between days and opens the calendar and search inline, in place of the strip, since the assistant session cannot show a dialog (=Browse.kt=). A moment's panel lands at the foot of the strip, outlined. =june://at/ID= from another app opens the full screen on that moment.

* Agents and projects
Planned with Jon on 2026-11-20. Two views beside the strip, for the worlds June works in: the agents (her clankers, in herdr-core) and the projects (Jon's Org agenda, in Emacs). Herdr and Emacs stay where the work is watched and edited; the views give an overview and a way in. Narrow, as on the phone, they are tabs beside the strip; on a wide desktop the agents take the left margin and the projects the right. Three columns start at 1296 px balanced (=368 | 480 | 368= with 20 px gaps and margins, keeping the strip at its non-stacked floor), then both the strip and the side columns grow proportionally as the window widens up to comfortable caps (=460 | 820 | 460= at 1820 px, centred beyond that so sidebars never stretch too wide); windows under 1296 px fall back to tabs. The desktop overlay's =boardsPaper= scales its side boards over the same =368..460= px range. The mockup on the design canvas, approved by Jon on 2026-11-20, is the first version.

- One source per world, served by the daemon. Emacs on the daemon's host computes the agenda by Org's own rules (=org/agenda/june-agenda.el=: =org-agenda-get-day-entries= for each day, so overdue items, warning periods and repeaters match Emacs), and the open tasks with their state, planning, AUTO host and agent, DEPENDS verdict, headline, =herdr:= sessions and Dialog. It reads the dispatcher's cached list of agenda files and writes nothing. hc reports the workers on every host. =src/board.ts= shapes both: the =agenda= board (overdue, today, the next six days, every task by key, counts by state, files by open tasks, with when each last changed) and the =agents= board (workers joined to their tasks by =org.task= or session, what needs the user, AUTO tasks by start, and tasks a worker reported on in the last day). Clients never parse Org or call hc.
- What needs the user, most urgent first: a worker blocked on a permission or question dialog, which only Herdr can answer; then a task newly in EVAL for them, until it is marked seen: a question or a problem put to them (=:ASKED:=, kind =asks=), or work ready for their review. HOLD is never a need: Jon uses it for a task that waits on something outside, when he has done what he can (2026-11-20). EVAL that agents are reviewing is listed apart as =reviewing=: an open independent review (=REVIEW_PARENT=), the development task it reviews, and a standing =REVIEW agent= task whose loop the dispatcher has yet to start or finish. Seen marks live in =seen.json= in the state directory, so every device agrees; the first time, every review already open counts as seen.
- =agenda= and =agents= requests answer with the board and its revision. Asking subscribes the connection: while any does, the agenda is recomputed two seconds after an agenda file changes (and every ten minutes, so the date turns over), and the workers are checked every fifteen seconds. Each view's state then carries =boards: {agenda, agents}=, the revisions, and a client asks again when one changes. =seen= marks reviews by task key. =june agenda= and =june agents= print the same boards.
- Built first in the desktop client's window (=StripWindow.qml=, 2026-11-21): =desktop/board.mjs= lays it out and shapes both boards into sections and rows for both clients (the phone bundles it); =AgentsBoard.qml= and =ProjectsBoard.qml= draw them, with placeholder clankers (=Clanker.qml=) and state chips (=StateChip.qml=). The shell asks for the boards when the window first shows, again whenever a revision in the view state moves, and after a reconnect. A task row opens Emacs at its heading line (=file:~/org/FILE::LINE=); an agent card opens its session with =herdr-link jump= when the worker has a session label. The projects board has three tabs: =agenda= (overdue, today and the week, as Org's agenda computes them, except that a past SCHEDULED or DEADLINE on a heading without a state, an event that has been, is not overdue), =tasks= (every open task by state, dated or not: in progress, in review, on hold, to do, five each with the rest a tap away, the projects whose files changed most recently first and each in file order, their dates in the row's small print; AUTO is the agents board's), and =projects= (the files with open work). =june-desktop tab agents= (IPC =tab=) opens the window on a tab.
- On the desktop (2026-11-22), the same five-icon bottom bar (=NavBar.qml=, =TabIcon.qml=: Terminal, Agents, Chat, Projects, Editor; =Alt+1..5=) drives narrow =StripWindow= and narrow Hyprland overlays (where the screen cannot fit =boardsPaper=). Strip is renamed Chat (=june-desktop tab chat=, keeping =strip= as an alias), the composer shows and takes focus on Chat alone in narrow views, and =StripWindow='s device toggles tuck behind a =settings= button beside =console= in the masthead. Wide three-column windows and wide overlays keep Agents | Chat | Projects side by side and put Terminal and Editor quick-launch icons on the outer board headers; both focus existing =herdr-app=/=emacs= windows on Hyprland or launch them (overridable with =JUNE_DESKTOP_TERMINAL= and =JUNE_DESKTOP_EDITOR=).
- On the phone (2026-11-22, after the Muse app), the full screen's pages sit under a bottom bar of five drawn icons (=Tabs= in =Boards.kt=): terminal, agents, chat (the strip), projects and editor. Chat is the middle page and the default; the outer two open the chosen Terminal and Editor apps (Herdr =dev.herdr.app= and Emacs =org.gnu.emacs= by default, set once in June's settings and shared with the header swipes and the agenda widget's bottom shortcut bar). The field to June shows on the chat alone and lets go when the keyboard goes or the page changes; return sends and alt+return or shift+return starts a new line, with no send button. The bar stays anchored behind the keyboard so the keyboard covers it going up and reveals it going down.
- A task's page (=TaskDetail.qml=, =TaskPage= in =Boards.kt=; =board.mjs taskDetail=) opens from a row in either board: its state, facts (who works it and where, when it starts, what it waits on, who reviews), its last report, buttons for Emacs and its newest Herdr session, and its Dialog as a conversation: the user's entries as blue notes on the right, an agent's beside its clanker, June's in her balloon, the dispatcher's as a caption. Opening a review's or question's page from the agents board marks it seen (=seen=).
- Edits, built 2026-11-21, are the user's own acts, sent by their client as =task= requests ={key, edit}= and made by =src/board-edit.ts= through this checkout's =org-edit=, as June's own task tools make them, never as a message to June:
  - a state (TODO, PROG, EVAL, HOLD, DONE), with the state the board showed as =--expect=, so a task changed since is refused;
  - a handoff to a clanker, confirmed first on the page with its agent, host (the agents board's =dispatch=) and start: its SCHEDULED when still ahead, else now, unless the user picks a time, which is scheduled before AUTO is set; the AUTO grant is written as the user's (=org-edit todo --who=), in their Dialog entry, and leaves REVIEW and DEPLOY as they were, unlike June's resume;
  - SCHEDULED or DEADLINE, picked on a calendar and clock (=WhenPicker.qml=; Material's date and time pickers on the phone) as =YYYY-MM-DD= or =YYYY-MM-DD HH:MM=, or cleared; a repeater is kept, and a queued AUTO task's start moves through =org-edit reschedule-task= in the user's name;
  - a new title (=update-task= with the subtree revision the export carries), for plain, TODO, EVAL or HOLD tasks; a task without an ID gets a new key, which the reply names in =from= so the page follows;
  - a Dialog reply in the user's name (=org-edit reply=), optionally resuming the task with its agent and host (Reply and resume).
- In a protected file (=org.protected=, see [[file:configuration.org][Configuration]]), such as the Asana mirror, the page offers only TODO and DONE, made with =org-edit todo --protected=; the mirror completes a task in Asana when it goes DONE.
- The daemon waits for any export already under way and reads the agenda again, so every client sees the change. A page whose task the dispatcher gave an ID follows it (=board.mjs findTask=); a page whose task left the boards says so. org-edit's own message is shown when it refuses, and a busy dispatcher lock is retried for a few seconds.
- Each task has an outbox in its client (=board.mjs entryChanges=, kept in =shell.qml pendingEdits= and =Link.pending=): an edit shows as made the moment it is tapped, on the page, the agenda rows and the lists, and a reply shows as "sending…". One edit per task goes to the daemon at a time; taps meanwhile queue behind it, the same kind of change replacing the last queued one (=enqueue=), and a queued state change to where the task already is is dropped (=nextQueued=), so quick taps settle on the last. A refusal drops the edit and everything queued behind it, with the reason, as do a dropped connection and 30 s without an answer; the board's state then shows again. The daemon answers as soon as =org-edit= has saved (about half a second) and reads the agenda again afterwards (about 3.5 s on kit); the next edit of that task waits for that read, so it is checked against what the last one wrote. A board edit waits up to 25 s for the dispatcher's lock (=ORG_EDIT_WAIT=), which a pass holds for 8 to 12 s once a minute. Saved edits stop overlaying when the boards that carry them arrive (or after 6 s if they never move). "saved" fades after 5 s, and a state change can be undone while it shows. Opening a review's page drops it from what needs the user at once.
- The daemon keeps one long-running Emacs for Org (=src/org-worker.ts= starting =org/server/june-org-server.el=): plain =emacs -Q= with June's Org code, not the user's Emacs, started on first use. The boards' agenda reads and edits go to it, one at a time, as base64 JSON lines, instead of a batch Emacs per call; an edit runs org-edit's own command under the dispatcher's lock, held by the daemon as the wrapper holds it. Agenda buffers stay open between reads, and each file's day entries are kept until the file or the day changes (=june-agenda--days-cache=), so a read after an edit recomputes only that file. Before each request it closes any buffer whose file changed, vanished or holds unsaved changes, so it never reads stale text or stops to ask. A request that takes over 60 s restarts it, it is replaced every 500 requests, and when it cannot answer the daemon falls back to the one-off commands.
- The phone's home-screen widget and reminders (=AgendaWidget.kt=, =Reminders.kt=), in place of Bloom's, draw from a copy of the agenda kept on the phone (=AgendaStore.kt=, trimmed to what they show), so they work with June closed and offline, saying how fresh the copy is. The agenda covers 14 days (=AGENDA_DAYS=); the boards show the week. The copy is refreshed whenever the app gets an agenda, every 15 minutes while online (=AgendaJob.kt=, its own short connection: =DaemonCall.kt=), and within seconds of any change: the phone registers with the ntfy app as its UnifiedPush distributor (=Push.kt=), sends the daemon the address it gets (=push=, kept only on the configured ntfy server's origin, in =push.json=), and the daemon posts to it when the agenda's revision moves, two seconds after a burst settles (=src/push.ts=), watching the agenda alone while any phone takes pushes. Reminders are exact alarms at timed SCHEDULED and DEADLINE entries and timed timestamps on headings with a state, and at =reminders.dateOnly= (09:00) on the day of a deadline without a time; never at AUTO, DONE or calendar events. A reminder's Done marks the task DONE through =task=; Snooze brings it back in 10 minutes; a tap opens the task's page (=june://task?key=KEY=).
- Dates on the boards are named so they cannot be read as the wrong week (=board.mjs dayWord=): today, tomorrow, yesterday, a weekday within the coming six days, else month and day.
- The agents board has three tabs, left to right =hosts=, =clankers= and =activity=, with activity, beside the strip, the default. On the phone each is a page of the pager, between the Terminal page and the strip, so a swipe left from the strip reaches activity, then clankers, then hosts, then the Terminal page; the Agents tab goes to activity, and tapping it there puts away what activity has open. The sections are named in a sub-navbar in the compose bar's place and at its height (=SectionBar= in =Sheet.kt=, =SectionBar.qml=), so every page keeps one height and navigation stays at the bottom: its fill follows a swipe, a tap goes to a section, a tap on the one showing resets it, activity counts what needs the user, and it hides under the keyboard. The phone's agents pages have no masthead; the desktop keeps the board's name and summary in the wide layout, where no tab bar names the column, and drops it in the narrow one. The projects board works the same way on the strip's other side: =agenda= (beside the strip, the default), =tasks= (whose state lists drill down in place) and =by project=, as pager pages on the phone and in its own section bar. A task's page (from activity or the projects board), a clanker's card or form, and a host's page rise over the board as a sheet (=Sheet.kt=, =Sheet.qml=), which goes away by its close button, a tap on the board above it, Back on the phone, a pull down on its handle or on its content once scrolled to the top, and Esc on the desktop while the pointer is over that board. The hosts tab lists each host in the agents board with whether it answers, its sessions and its clankers (=board.mjs agentsView hosts=, =HostDetail.qml=). The =clankers= tab (=RosterDetail.qml= and =EnlistCard.qml= on the desktop, =Squad.kt= on the phone; =board.mjs rosterView=), showing each clanker from =~/org/june/clankers/<slug>/CARD.org= with its harness-coloured portrait, status, quota gauge from the active account, host, harness, model, effort and directives when opened, plus create, edit and destroy (which archives the folder to =clankers/.destroyed/=) through the daemon's =roster= request (=src/roster.ts=). Each clanker's own =MEMORY.org= follows its directives when it launches, and it adds lessons there; and per-agent run history and leaderboard stats from =june.sqlite= (=src/runs.ts=, =june agents leaderboard=, =june agents history=).

* Clients and protocol
** Recommended
- Keep the existing Request and Reply shapes and add only what new clients need. No second protocol, no separate gateway service.
- Add an attach mode that sends folded transcript items and their changes instead of raw Durable events, computed in the daemon by the same =Transcript= code the terminal uses. QML or Kotlin clients then render items and never reimplement privacy rules. The terminal client can stay on raw events or move over; that choice belongs to the implementation task.
- Add sources for the new clients, =gui= for the desktop client and =apk= for the Android app, with a flag on voice input. June's prompt learns what each source means, as it does for the terminal, whose source is renamed from =kitty= to =tui=.
- Add a WebSocket listener carrying the same JSON, on loopback behind the host's Traefik and off by default. Each device gets its own bearer token, stored hashed in the state directory, listed and revoked by a =june= command. The desktop client uses the same WebSocket, so each client has one transport.
- Reconnection reloads the snapshot, as the terminal does today. Event replay from a cursor can wait until the 200-entry snapshot proves too slow on the phone.

** Questions
- Settled on 2026-10-30 in [[file:architecture.org::*Client protocol for graphical clients][the architecture notes]]: the folded view is an attach option beside raw events, items change by whole-item replacement, and the listener stays on loopback behind Traefik as =wss://june.kit/=, reachable on the LAN without Tailscale and away through the subnet route. Both graphical clients use the WebSocket, the desktop client included.
- Settled: where June's own notices go when the user last spoke from the desktop client or the phone app: the desktop client counts as the terminal, plus a desktop notification when it is hidden. The Android app gets a phone notification through the existing ntfy server, since Telegram becomes a fallback; the notice itself waits in the conversation. Firebase push also works where sandboxed Google Play is installed, but it needs a Google project and routes notices through Google, so it is the fallback. Telegram gets notices only when the user last spoke there.

* Desktop client
The desktop client is one Quickshell program with two modes: an overlay on top of the desktop, and an ordinary window. These notes grew up around the desktop client mode and often call the whole program "the desktop client".

** Requirements that drive the choice
A layer-shell surface on the =overlay= layer draws above fullscreen windows, which an ordinary floating window does not. Exclusive keyboard interactivity while shown, Escape to hide, a Hyprland bind that toggles a resident process so scrollback survives, and placement on the focused output. Those are protocol behaviours shared by every toolkit, so the toolkit choice is mostly about ergonomics, rendering, and upkeep.

A layer surface is not a window, so the application beneath stays the active window while the user types to June; she can read it at any time. Two variants are planned: a full one that dims the screen like a launcher and shows the transcript and avatar, built first, and a subtle one that sits small and out of the way and expands into the full one. The terminal client stays as the plain console client.

** Toolkit
Quickshell: Qt/QML with native layer-shell and Hyprland integration, pre-1.0 (0.3.x in August 2026) and the current momentum among Hyprland shells. The user already runs it on Hyprland, and Hyprland's author endorses it. QML handles animated images and sprite animation well. Reported memory use is a few hundred MB for full shells, which matters less for a single panel.

Set aside: AGS/Astal (GTK4, TypeScript and CSS), whose momentum has moved to Quickshell, and a web view in a GTK4 layer-shell host, which would be the most custom option. An ordinary Electron or Tauri window cannot take the desktop client layer.

A half-day Quickshell spike retired the remaining risks before the build; its findings follow.

** Spike findings
Run on 2026-11-03 with Quickshell 0.3.0 and Hyprland 0.57.1 on a laptop with an external monitor, beside the user's own Quickshell shell, attached to the daemon on another host. Every risk came out in Quickshell's favour.

- Layer and focus: a =PanelWindow= with =WlrLayershell.layer: WlrLayer.Overlay= and =WlrKeyboardFocus.Exclusive= draws above a fullscreen mpv video, takes every key while shown, and returns focus to the previous window when hidden. =hyprctl activewindow= keeps naming the window beneath while the user types in the desktop client, so desktop context can be read at any time.
- Variants: the full variant is one panel anchored to all four edges with a translucent backdrop and the strip centred; the minimised variant is a second panel anchored to the bottom alone, so it sits at the middle, the strip's width, with a transparent background. Both draw the same panel and compose bar components from one transcript model, so switching keeps scrollback and draft.
- The desktop strip, in the window and the full variant, has a thin scrub bar at its right edge, faint while the pointer is over the strip and firmer on the bar or while held, for sweeping through a long day; holding it stops following the newest panel, and letting go at the bottom follows again. Whenever the strip is scrolled up, a small down arrow at its bottom right jumps straight to the newest panel (Jon, 2026-11-27).
- Monitor: picking the screen from =Hyprland.focusedMonitor= on each summon puts the desktop client on the monitor in use.
- Toggle: an =IpcHandler= target called from a Hyprland bind (=qs -p DIR ipc call june toggle=) toggles a resident process. Avoid naming IPC functions =show=, which =qs ipc call= does not dispatch; =open= and =close= work.
- Bind: the user's keyd setup sends F13 for a lone tap of left Alt. Hyprland sees it as =code:191= (XKB names it XF86Tools) with keyd's guard modifier, so the bind needs =ignore_mods = true=. Rofi uses the same tap to cycle modes, so the bind is non-consuming and returns early while a =rofi= layer is mapped; the focused application also receives the key, which mpv logs as an unbound =TOOLS= key.
- Animation: =AnimatedImage= plays a GIF; pausing it while hidden costs nothing.
- Memory: about 125 MB resident while hidden and attached, as a separate process.
- Connection: Quickshell's =Socket= with a =SplitParser= speaks the newline-delimited protocol directly; attach, the folded view's reset and changes, streaming, and =submit= with source =gui= all worked through a Unix socket forwarded from the daemon's host with =ssh -L=. QtWebSockets 6.11.2 from nixpkgs loads inside Quickshell when put on =QML2_IMPORT_PATH=, since it is built against the same qtbase; it is not in Quickshell's own closure.
- Packaging: the QML directory copied to the store and a =writeShellApplication= wrapper that adds QtWebSockets to =QML2_IMPORT_PATH= and runs =qs -p= on the store path loads from the read-only store. The wrapper should take =hyprctl= from the running system rather than a pinned Hyprland, whose version may not match the compositor. A Home Manager user service on =graphical-session.target= can keep it resident.
- For the build: the transcript has to follow its end when the last item grows, not only when one is added, or a streaming reply runs below the fold.

** Look: a comic strip
Chosen on 2026-11-03 after two rounds of sketches, and refined the same day against a full-colour manga mockup (the brief and mockup are in the project's Org task material). The terminal client already covers the console look, so the desktop client goes the other way: a living comic strip in which June is the recurring protagonist and the user's messages enter her world from outside the frame. Priorities, in order when they conflict: the words stay readable, her face stays visible, the panel reads as a natural comic, vertical space is not wasted, and new art and message kinds fit without code changes.

- Full variant (max mode): a vertical strip in the middle of the screen, full height, over the dimmed desktop, every panel the strip's full width, the newest at the bottom just above the compose bar, which runs across the strip 22 px from the bottom (on the tab bar when the boards do not fit). On a wide screen the agents board stands on paper to its left and the projects board to its right, as in the window and on the phone (=board.mjs overlayBoards=; Jon, 2026-11-26, in place of both boards on its left). The chibi card is gone from the desktop (Jon, 2026-11-26): June is in her panels. Live June (min mode) is the small form; see "Live June, the minimised form".
- One canvas per panel, not a portrait column beside a text column. June's art and the words share it: balloons may overlap her body but never her face, and her art may run past the panel's edges and be cropped.
- She alternates sides from panel to panel, and keeps a panel's side from the moment it opens: while she thinks, works, and writes, through settling and her picked face, on reload, when a later run for the user makes the panel live again, and on another take. One of her private looks (a heartbeat, watch, work report, or follow-up, =state.looking=) adds nothing to the newest panel, so that panel keeps its settled face and pose through it; only a run answering the user, or tidying, makes it live. A panel without a recorded side takes the other side from the latest earlier recorded pose, which is the side the daemon records when it picks the reply's face. Her side is chosen before her pose, so the pose changes freely and prefers poses that can stand there; a pose that faces away from the words and may not be mirrored moves her to the side where she faces in only when no pose answering the request can stand on hers.
- The words set the panel's height, within a minimum; the art adapts like a hero image, scaled and cropped by its face box, never stretching the panel. The framing follows the art area's height: a close-up in a compact panel, head and shoulders, bust, or waist-up in taller ones. When the words run long, a pose drawn to her feet stands on the panel's floor, and a pose that ends at her hips stands behind a desk at the bottom of the panel.
- Below 480 px she stands in a band across the top of the panel and the words run full width beneath her.
- A panel holds one reply's performance and take menu. A different reply starts a new panel even when both are short, so later updates cannot replace earlier art or hide its saved takes. A long reply splits into balloons at its paragraphs (a list stays with the line that introduces it, four balloons at most). *** Composition engine
=desktop/compose.mjs= holds every layout decision as plain JavaScript, so =test/desktop.test.mjs= checks the compositions under Node: QML measures each element's text at the column width the engine gives it, and the engine returns where everything goes. Its contract with the art is the pose metadata below; with the words, only their measured sizes.

- =metrics(width)=: the words' column and the art's share of the width, padding, minimum panel height, and the height past which the art moves to an inset.
- =plan()=: elements in reading order (the user's notes to the outer edge, June's balloons toward her with an alternating stagger, a status card beside the next balloon when both fit), the panel's height from their bottom, the framing, and the image rectangle from the pose's face box, with a lane between her face and the words for tails. It returns her face and mouth in panel coordinates, each balloon's tail, and her marks.
- Tails: consecutive balloons are one speech, and tool chips, cards, and thoughts between them do not end it; the user's notes and bursts do. A balloon beside her face takes its tail from the side facing her; otherwise from its top or bottom edge, or the side if that path is clearer. A base only sits on a straight run of the outline, and a balloon is never drawn smaller than 120 by 58 px, so a reply that has just started still has a clean tail. A tail leans at most 50° from its edge, so a balloon far below her gets a tail that points her way rather than a bent spike, and the edge needing the least bending wins. The tip stops before her face box and before any other element, and a tail without 12 px of clear room is left off rather than drawn over something. A thought cloud's trail leaves its corner nearest her face and drifts toward it, trying the next corner when its circles would land on another element or cross the cloud, and going without when every corner is boxed in.
- Pose choice: the named pose, else a pose whose expression is the requested one or the next in its fallback chain, avoiding the previous panel's pose when another fits. Until the daemon sends an expression, the desktop client asks for a stand-in: exasperated for a failure, curious while she answers, otherwise a listening face (idle or curious) chosen by the panel's id. A stand-in never reacts, since it has not read her reply; a laugh on a serious reply would read as meant until the director's face replaced it. A panel's side and pose are kept once chosen, so the strip does not rearrange itself as it grows.

The invariants the tests hold at 820, 640, 460, and 340 px, both sides, and several element mixes: every element inside the panel and apart from the others, none over her face, her face inside her art area and image, a face of a useful size, marks inside the art area, tails toward her mouth and short of her face and other balloons, one tail per run of balloons away from her face, and no floating torso.

Motion rules:
- Ink, not glow: balloon outlines draw, captions wipe in, faces cut between images rather than fade. No blur or glass.
- Text arrives at the streaming pace; the newest balloons land with a small overshoot.
- Big moves (a shake, a bounce) only on the rare expressions, so they still surprise.
- Serious and gentle replies get no marks, as =SOUL.org= drops the teasing then. Reduced motion keeps only the cuts.

How a face arrives: the strip is a printed page except where it is still being drawn. While June works, the newest panel shows what she is doing; while she writes, her talking pose; when the run ends, it keeps that talking pose until her real face is picked, up to six seconds, so no guessed face shows in between. The picked face is then revealed as a beat: the new image loads unseen on a second layer, then a 120 ms crossfade while her figure settles from 3% larger toward her face over 220 ms, and the pose's marks land a beat later. A serious or gentle face, or a change into or out of a working pose, is a plain cut. Only the newest panel, already on screen, ever animates; a panel drawn as the user scrolls or opens the strip shows its final face, still. Live June reacts in the corner at the same moment with the chibi for that face, held 2.6 seconds with the same settle, then goes back to her loop.

The words are real text: balloons and notes are read-only text fields, so a drag selects and the usual key copies. Until the art exists, the base avatar set's placeholder poses stand in; the composition does not wait on them.

*** Light and backgrounds
=desktop/light.mjs= decides how each panel is lit and what stands behind June; =desktop/Backdrop.qml= paints it.

- The hour: a panel is lit by the hour its words were written, from the =at= the daemon puts on each user and assistant item (the message's own timestamp), read on the desktop client's clock. A panel without one, such as a reply still streaming, uses the current hour. So a strip read at night still shows the morning's exchange in morning light. =june-desktop light 21.5= previews every panel at one hour; =june-desktop light now= puts them back.
- The day's palettes follow the sun at home, computed for each panel's date from the location in the daemon's =sky= (=sunTimes=, NOAA's approximation): night until an hour and a quarter before sunrise, dawn as it rises, morning two and a half hours on, afternoon an hour and a half after solar noon, golden hour half an hour before sunset, evening as it goes down, and night two and a quarter hours after. So golden hour is at half past four in a Calgary December and after nine in June. Without a sky the keys are fixed: dawn at 6:00, morning at 9:00 (the reference look, ungraded), afternoon at 14:00, golden hour at 18:30, evening at 20:30, and night from 23:30 until 4:30. Between two keys every value blends, so the light moves rather than jumps.
- The grade multiplies the ground by the hour's colour. June takes the same colour more gently (a colorization of at most 30%), with her own brightness and saturation, so her face stays readable at any hour. A key light in the hour's colour falls on her from the open side of the panel, clipped to her outline. In the evening and at night a warm lamp glow comes up behind her. Balloons, notes, cards, and marks are never graded.
- Behind her, in order of precedence: while tool calls run in the panel she is working in, a cutaway of that work; a long panel, whose words cover more than half of it, keeps a plain tint, since a room or an effect would fight the reading; a serious or gentle reply gets the calm ground; a rare face gets its abstract background; anything else, her room (see "Rooms, windows, and props"), or the panel's tint when the set has no rooms.
- Abstract backgrounds, drawn by code: focus lines for surprised, sparkles for delighted and cheering, soft bubbles for bashful, gloom lines for pout and exasperated, and a burst for indignant. Focus lines and the burst centre on her face. Only the face the daemon picked earns one; a stand-in never does.
- Cutaways show only what the runtime knows. Delegating (a brief through =work=, Herdr, or the Org queue among the run's calls): a pane per brief named by its narration, and the run's calls as a chain coloured by status. Digging: the places her calls looked, as labelled drawers (mail, the calendar, Org, the shell, the web, or the file a call touched). A cutaway is not graded, being lit by its own screens, and when the run ends the panel settles back to her room.
- Grounds and patterns fade over 220 ms when they change, which only happens in the newest panel.

*** Rooms, windows, and props
=desktop/scenery.mjs= chooses and places June's room; =desktop/Scenery.qml= paints it. A panel whose backdrop is her room shows it when the avatar set has rooms, and keeps the plain tint otherwise.

- How a panel stacks, back to front: the hour's sky through the window (a gradient, the sun or moon, stars at night), the season's view, rain or snow; the room with its window cut out; the props; all graded by the hour as one print. Then the lamp glow, June, her key light, her marks, and the words.
- The room is chosen by the pose's =setting= among the rooms that serve it, by the panel's id, so a panel keeps its choice. It covers the panel, mirrored when its window would be on June's side, and shifted so the window sits on the open side in the upper third. It is out of focus behind a close framing: well blurred behind a close-up, softened behind a head shot, sharp from the bust out.
- The view through the window is the season's plate (northern hemisphere: winter is December to February), its sky left clear for the computed one. The weather now, from the daemon's =sky=, greys the sky by cloud, hides the sun and stars, and lets rain or snow fall. It holds for panels from the last three hours; an older panel shows a clear sky rather than a guess.
- Props come out by conditions, every one of which must hold: a holiday's dates, Home Assistant weather conditions, a temperature range in °C (converted from °F), or seasons. Holiday props come first, then weather, then temperature, then season, at most two. Each stands at the first of its room's spots (floor, desk, wall, sill) where it fits whole inside the panel, clear of her face, the words, and the other prop, and scales with the room. One that fits nowhere stays away. Props need the weather for a temperature or weather condition, so without the daemon's =sky= only date and season props appear.
- The manifest's =backgrounds= holds =rooms= (file, size, the settings served, the window as fractions, and spots as lists of [x, y] fractions where a prop's bottom centre stands), =plates= (file, size, season), and =props= (file, size in the room's pixels, spots, =when=, and optionally the rooms it fits). =parseManifest= checks them strictly; the desktop client reads them leniently and drops a prop with no conditions, since that would be room art.
- =templates/avatar/backgrounds/= holds labelled placeholders: three rooms (a study for the desk and standing, a living room for the couch, a kitchen for the kitchen and standing), four seasonal hill views, and seven props (a fan from 26 °C, a window air conditioner from 30 °C, a space heater at -10 °C and below, an umbrella in rain, a carved pumpkin through October, string lights from December to 6 January, and a little tree until Boxing Day). The art is to be drawn in flat, neutral light, so the grade reads naturally.

*** Finishing generated art
June's art is generated outside the repository and kept in a personal avatar set that =JUNE_DESKTOP_ART= puts ahead of the base set; the repository keeps only placeholders. =june-art= (=nix run .#art=, source in =art/=) turns an approved image into a finished piece of that set, so every piece of a kind frames alike. The phone has no local set: it loads the daemon's over HTTPS from the path the hello gives it, merged over the base set in its assets as the desktop client merges sets, its pictures kept in the app's cache and revalidated by ETag, so the strip still draws them offline (2026-11-04, with the first real pose).

- A set directory holds =manifest.json=, the finished WebP files, =incoming/= for approved images waiting to be finished, =source/= for the originals and their prompts, and optionally =planned.json=, a manifest-shaped catalogue of what is still to be made.
- =june-art ingest SET NAME= takes =incoming/NAME.png= and its details: a sidecar =incoming/NAME.json= (a flat manifest entry with =section= and optionally =faceBox= in source pixels), else the entry already in the manifest, else the planned one. It makes a flat background see-through with =--key=, trims, upscales with Real-ESRGAN's anime model when the piece would be drawn larger than generated, and places it on its canvas: a pose scaled so her face is 27% of a 2048 × 2662 canvas (10% of a 2048 × 4096 tall one) and centred across, clear of the sides and top; a chibi as large as fits a 1024 square; a room or window view covering 3200 × 2000 or 1600 × 1000; a prop fitted to its planned size in room pixels. It measures a room's window from its see-through pixels, writes lossless WebP, checks the whole manifest with =src/avatar.ts=, keeps the original and prompt in =source/=, and reports anything a person should look at, such as a figure cut at the sides.
- A pose's face box is given by hand (=--face X,Y,W,H= in source pixels) until detection is tuned on real art; its mouth defaults to the middle of the face, four fifths down.
- Gestures (2026-11-05, from the production gesture pilot): a wide gesture widens the canvas rather than losing fingers. Ingest keeps her face at 27% of the canvas height and grows the width in 128 px steps up to a limit (3072 px to start, =--max-width= to change it), refusing past it with the width-to-face ratio rather than cutting. =--gesture NAME,X,Y,W,H= (repeatable, the first primary), or =gestureBoxes= in the sidecar, records gestures away from her face; the manifest carries them as =gestures= in canvas fractions, and ingest keeps only the =framings= whose crop around her face keeps the primary one in view. Each pose gets =added=, when it entered the set, set once and never changed.
- =june-art sheet SET NAME= draws a contact sheet: a pose with its face box and mouth and its crop at every framing, as =desktop/compose.mjs= frames it; a room with its window and prop spots; other pieces over a checkerboard, so a ragged cut-out shows.
- The desktop client loads WebP through Qt's =qtimageformats= plugins, which its wrapper adds.

** Platform facts
- A third-party app becomes eligible for the digital assistant role by declaring a =VoiceInteractionService= with its =VoiceInteractionSessionService=. The automotive guide says voice interaction apps should also declare a =RecognitionService=; whether GrapheneOS lists the app without one is a proof-of-concept question. - Invocation on GrapheneOS: forum reports say the gesture-navigation corner swipe works and that the power button offers double press but not "hold for assistant". Verify on the phone. - Screen context: a session receives =onHandleAssist= (structure of the foreground app) and a screenshot only when the user has enabled "use text from screen" and "use screenshot" for the assistant. No Google services are needed. Some apps mark windows secure and return nothing.

- No persistent connection is needed: connect when a session opens. Microphone use inside a visible session needs only the runtime permission. No wake word or always-on listening is planned on the phone, so no foreground service is needed for the microphone.

The system's dark mode and do-not-disturb come from each platform: the desktop portal and mako's mode on Hyprland, =uiMode= and the interruption filter on Android.

** Building and pairing the app
=android/= is a Gradle project (Android Gradle Plugin 9.5 on nixpkgs' Gradle 9.8, Kotlin 2.4 built into the plugin, Compose BOM 2026.09, OkHttp 5), compiled against API 37, targeting 36, minimum 33, and shrunk by R8 to about 2.7 MB. * Embedded terminal
Planned on 2026-11-23 and built behind a setting on 2026-11-24. The phone's Terminal tab, the task cards' terminal icon and =herdr:= links open the agent's live herdr-core terminal inside June, sized to the phone, instead of Termux running =ssh -t HOST herdr-link attach=. June stays the orchestrator and herdr-core the terminal and process manager: the embedded terminal is one more viewer of terminals that already exist. It never starts, resumes or kills a program, never passes through a model, and never writes terminal output into June's conversation. The work is tracked in =june.org= under "Embed live Herdr terminals in June's Android app"; the wire protocol is "Terminal streams" in =docs/architecture.org=.

** What was verified
Read in the upstream sources on 2026-11-23 (herdr-core =7cb4de4= with schema 0.1.22, Ghostty =167acf0= and tag =vt-1.0.1=, T3 Code =main=, termux-app =main=) and probed on kit against its core (0.1.21, features =framed attach events status shell resize_notifications automatic_input restart_environment=) with throwaway =bash= terminals on kit and on cog, removed afterwards.

- Attach is a first-class, documented part of herdr-core's API (=schema/README.md=, "Attach streams"). After =hello {framed: true}= a connection carries frames of =[channel u32][kind u8][len u32][payload]=; =terminal.attach {terminal, cols, rows, history, display, observe, resumed}= returns a channel. On it the core sends a first paint, then the program's raw output; the viewer sends keys as DATA and RESIZE, FOCUS and FACTS as they change; CREDIT is flow control (256 KiB to start; a viewer more than 4 MiB behind gets a fresh repaint, and a stalled stream never blocks another); CLOSE detaches, and the core closes with ={reason, exit_code, signal}= when the program ends. Loss of a kept terminal closes the stream; the viewer attaches again after the =restarted= event.
- The first paint is a complete repaint, not a replay. On kit it began =CAN, ESC [ ! p= (soft reset), cleared every mouse, paste and keyboard mode, restored the program's own (=CSI ? 2004 h=, kitty keyboard flags =CSI = 0;1 u=), cleared the screen, set tab stops and drew the screen. =history: 100= added 100 lines of scrollback above it. A fresh emulator fed these bytes reaches the terminal's state, so the phone needs no replay buffer of its own.
- Size ownership works as Jon sees it in the Herdr app: the last active viewer sets the terminal's size, where active means it attached, typed, resized or gained focus; =observe= viewers never type or resize. Probed on kit and on =cog/t8=: viewer A attaching at 40×12 sized the terminal 40×12; viewer B attaching at 100×30 took it; A's RESIZE took it back; B's FOCUS took it again; A typing took it back. So the phone takes the size by attaching normally, and the desktop reclaims it by focusing or typing, with no takeover step. =resumed: true= on an automatic reconnect sets the size only once that viewer is active again, so a phone reconnecting in the background never steals it.
- Remote terminals need no SSH from June: kit's core has cog and lux as machines (=hc machine ls=), and attaching =cog/t8= through kit's socket relayed paint, input and resize. =hc connect= speaks the same protocol over stdin and stdout, so =ssh HOST hc connect= is the fallback for a host that is not an added machine.
- The core never encodes keys. The viewer encodes them for the program's current modes, and Pi pushes kitty keyboard flags (=pi-tui= =terminal.js= sends =CSI > flags u=), so hand-written escape sequences are not enough. The core answers terminal queries itself from the viewer's =display= facts (colours, cell size); replies the viewer's emulator still makes go as AUTOMATIC_INPUT (kind 6) only when both =hello.features= and the attach reply say =automatic_input=, otherwise as DATA.
- Versioning: the protocol is "preview (protocol generation 1, version 0.x)", but the API only grows: =released.openrpc.json= is checked in CI against any removed method, field or narrowed input, and a real break needs a new generation. =hello {generation: 1}= fails with =unsupported_generation= otherwise.
- libghostty-vt (MIT) is Ghostty's terminal emulation library without its renderer or app: parser, terminal state, scrollback, reflow, a render state with dirty tracking, selection, formatting, search, and encoders for keys (legacy and kitty), mouse, focus and paste. =vt-1.0.1= was released on 2026-11-11 with a stable C ABI for 1.x. Ghostty's CI builds it for =aarch64=, =x86_64= and =arm= Android with NDK r29; there is no prebuilt Android release. It needs Zig 0.17.0 (main needs 0.17.1); nixpkgs has Zig 0.16.0 at most, and Ghostty's own flake builds libghostty-vt offline with =zig-overlay= and =deps/packages.nix=. Upstream sets only =max-page-size= 16 KiB for Android.
- herdr-core links the same library for its server-side screens (Ghostty =1e5cdb86=, Zig 0.16), so the first paint the phone receives was produced by the emulator the phone would run.
- T3 Code (MIT) has a native Android terminal in =apps/mobile/modules/t3-terminal=, about 1,500 lines that matter: a JNI bridge (=t3_terminal_jni.cpp=: create, feed, resize, viewport scroll, theme, word and range selection, selection text, and a compact binary snapshot of the viewport), a Canvas view (=TerminalCanvasView.kt=: cell grid, styles, cursor, selection handles and a copy action mode, MesloLGS NF), and IME input through a hidden single-line =EditText= (=TYPE_TEXT_VARIATION_VISIBLE_PASSWORD | NO_SUGGESTIONS=, =IME_ACTION_SEND= as CR, deletes tracked through =deleteSurroundingText=). Its build script builds Ghostty =3ff6d08f= with Zig 0.15.2 for four ABIs with =-Dsimd=false= and two patches: link libc on Android without SIMD, silence stderr logging, and set =common-page-size= as well as =max-page-size= to 16 KiB. It ships prebuilt =.so= files, about 1.1 MB for arm64. What it lacks: keys go through hand-written sequences (arrows and Tab without modifiers, Ctrl plus a letter, no Alt, no kitty encoding), no mouse or wheel encoding, no focus reports, a full viewport snapshot every frame, and transport through its own React Native RPC.
- The official Herdr app (=dev.herdr.app=, source not public) talks to herdr-core over SSH; its key bar has "Esc, Ctrl, Tab and the arrows, and you can change what's on it"; a compose box sends longer text "as one paste, then Enter". It exports no deep link (see =2026-11-20-herdr-core/herdr-app-deep-link-request.org=, not filed).
- Termux's =terminal-emulator= and =terminal-view= are Apache 2.0 inside a GPLv3 repository, pure Java and long used with Android keyboards. =TerminalSession= owns a local process through JNI, so a remote stream means replacing it, and the emulator has no kitty keyboard protocol.

** Choosing the emulator
| Option | For | Against |
|---|---|---|
| libghostty-vt, JNI and a Canvas view adapted from T3 | Same emulator as herdr-core; stable ABI; kitty keys, mouse, paste and focus encoders built in; selection and scrollback in the library; MIT | Native build with Zig and the NDK; JNI and the renderer are ours to keep |
| Termux =terminal-view= with a replaced session | Pure Java; mature Android IME and selection handling | Weaker emulation than Ghostty, no kitty keyboard protocol, fork needed for remote bytes |
| xterm.js in a WebView | Mature emulation; no native build | A second UI runtime inside Compose; Android IME composition in a WebView terminal is a known weak spot (not tried here); bundling and offline assets |

Recommended: libghostty-vt, because the key encoding and emulation fidelity the coding harnesses need come with it and match herdr-core, and T3 shows the Android path works. The spike decides before anything else depends on it; if the native build or the keyboard cannot be made to work, Termux's emulator behind the same view interface is the fallback.

From T3, adapt rather than vendor: the JNI functions and snapshot idea, the Canvas drawing, selection handles and copy action mode, the IME delete tracking and Enter handling, and the build patches. Leave out its Expo glue, its React Native transport and its replay buffer. Add a key encoder bridge (=ghostty_key_encoder_set_from_terminal= before each key), mouse wheel encoding, focus reports, bracketed paste through Ghostty's paste encoder, AUTOMATIC_INPUT for the emulator's own replies, and drawing only dirty rows once per frame. Keep T3's and Ghostty's MIT notices with the code.

** Daemon: terminal streams
Built on 2026-11-24 (=src/terminal.ts=, =/terminal= in =src/remote.ts=, =test/terminal.test.ts=); the wire protocol is "Terminal streams" in =docs/architecture.org=. The daemon relays; it never parses terminal output.

- Clients open a second WebSocket on the same listener, =wss://june.kit/terminal=, one per terminal on show. A separate connection keeps a busy terminal from delaying the conversation and boards (no head-of-line blocking on one socket, no shared 8 MiB backlog rule), and closing it is the whole cleanup.
- Its first frame is a hello with the device token, as on the main socket, and the terminal wanted. Revoking a device closes these too, and =june device list= counts them among a device's connections.
- Only terminals the agents board lists can be opened: a live terminal on a configured host that =Herdr.agents()= reports, found by =host= and =terminal= or by a =herdr:= link's session label as =herdr-link= finds it. A link whose session no longer runs is refused with "not running"; resuming stays with =herdr-link= and the dispatcher. No shell, run, exec, file, label or kill method is reachable from a stream. The one other method is =terminal.put=, for a file the phone sends to lie beside that same terminal (see "Files and screenshots" below).
- For each stream the daemon starts =hc connect= (local, which reaches added machines as =HOST/tN=) or =ssh HOST hc connect= for a host that is not added, says =hello {generation: 1, framed: true}=, checks for =terminal.attach= and the =attach= feature, and attaches with the phone's size, =history=, =display= and =resumed=. One connection per stream: it ends with the stream.
- Flow control is end to end: the phone acknowledges bytes it has fed its emulator, and the daemon passes them on as CREDIT, so the daemon holds at most the core's window per stream and the core's own repaint covers a phone that falls behind.
- At most four streams per device, each logged when it opens and closes with device, host and terminal, never content.
- When the last viewer leaves, herdr-core puts the terminal back to its own size (200×120 on kit); a viewer that is still attached keeps the size until another becomes active.
- Nothing in the relay is Android-specific, so the desktop client could use the same endpoint later.

** Android: the terminal page
Built on 2026-11-24 (=TerminalView.kt=, =TerminalStream.kt=, =TerminalPage.kt=, =TerminalBridge.kt=, =android/native/june_terminal_jni.cpp=).

- A Compose page holding a native =View= through =AndroidView=: the view owns the libghostty-vt handle, draws a snapshot of the viewport with Canvas once per frame when output arrives, and is the keyboard's target through its own =InputConnection=.
- Size: columns and rows from the view's size and the cell size, sent 150 ms after the size settles, so the keyboard's animation sends one resize. The keyboard shrinks the terminal; putting it away grows it back.
- Input: text from the IME as UTF-8; the word a keyboard is still composing (swiped or spoken) drawn at the cursor until it is committed; Enter, Backspace and hardware keys through Ghostty's key encoder with Ctrl, Alt, Shift and Meta, so kitty-mode programs get what they expect. Several lines at once go as one paste through Ghostty's paste encoder, bracketed when the program asks, never as an Enter after each line. The input type is plain text without suggestions, not the visible-password type Termux and T3 use: HeliBoard turns swipe typing off for any password field (=GestureEnabler=), which is why swiping did nothing in the spike.
- Key row: Esc, sticky Ctrl and Alt, Tab, Shift+Tab and the arrows, shown with the keyboard. Off by default, since HeliBoard already has these keys; Settings turns it on.
- Touch: a tap shows the keyboard. A vertical drag works as a scroll wheel: wheel events when the program asked for the mouse (Pi in its alternate screen does), arrows in an alternate screen without mouse tracking, and the local history otherwise. In the spike Pi ignored drags because the view only moved its local history, which an alternate screen does not have.
- Copy and paste: a long press opens the terminal's text with its history in a sheet, to select with Android's own handles and copy, copy all, or paste the clipboard. Selecting in place on the grid can come later.
- Colours and font: chrome around the terminal (identity bar, compose bar, buttons, key row, copy-sheet header) follows June's look (=Look.Palette=: paper light, neon dark, console light/dark), while the terminal grid itself stays dark so shared desktop/phone TUIs stay readable — harmonized with June's neon dark (=#12101c= bg, neon ANSI 16) in comic dark, console dark (=#121418=) in console dark, and card slate (=#1b1e2b=) in light modes. CommitMono Nerd Font Mono renders glyphs and Nerd Font icons; pinch-to-zoom scales font size (=8.5sp–22sp=). The phone reports these colours and cell size as =display= facts.
- Identity: a line over the terminal names the clanker, harness, host and terminal with its status from the agents board; "switch" lists every agent the board shows, on every host.
- Compose bar, by the keyboard, after the Herdr app's "local input": a paperclip to attach, an ordinary text box with the keyboard's autocorrect, cursor and selection, and ↵, which sends the message as one paste and then Enter. Tapping the terminal types into it directly, for keys and shortcuts. A draft stays with its terminal while the app runs. An attached file's path goes into the terminal at once, so attaching then writing sends =[Image #1] message=.
- Files and screenshots: see below.
- Lifecycle: the stream opens when the page shows and the app is started, and closes at =onStop= or when the page goes; a drop reconnects as =resumed= after two seconds. Each attach starts a fresh emulator with 2,000 lines of history from herdr-core's first paint. A terminal June cannot open offers Termux, which can still attach or resume the session.

** Files and screenshots

** Build
- =android/terminal.nix= builds the native library offline: Ghostty at tag =vt-1.0.1= (=fetchFromGitHub=), Zig 0.17.0's release binary by hash (nixpkgs has 0.16 at most), Ghostty's own =deps/packages.nix= for the Zig packages, and NDK r29 from =androidenv=, with =-Dsimd=false=. * Avatar
** Two signals
- Expression: chosen for character, from a fixed vocabulary, never authoritative.
- Activity: derived from runtime state, never chosen by a model. See [[*Activities]].

Clients show both: the expression on the face, activity as a small badge or pose. A client without images ignores them.

** Choosing an expression
Built on 2026-11-03 (=src/expression.ts=), after a trial. Once a reply settles (the run has ended and it is not streaming, private, or failed), a separate short call picks her face: June's =SOUL.org=, the vocabulary with each name's frequency, the avatar set's reaction poses, and rules that keep rare faces rare, keep pout for when the user wins, and drop the teasing faces from serious replies. It reads the whole panel: the user's message, the tools June called while answering and her patter (up to 12 tools and 3 asides), and her reply, with the two earlier exchanges and the face and pose each got. Idle is only for a panel with no feeling in it, and when the last two panels had the same face, another that fits nearly as well wins (revised 2026-11-06, when 27% of settled panels were idle and the director chose almost all of them; on the same 40 replies the same model chose idle 12 times under the old rules and 5 under the new, with no idle twice in a row). It also never repeats the pose of the panel just before when another pose of the chosen face fits (2026-11-06: on 40 real replies, the old rules repeated the previous pose 11 times and the new ones twice, with the faces chosen about the same). The answer is JSON, an expression and optionally a pose; anything outside the vocabulary or the set is dropped. The pick is a display-only =june.expression= entry naming the reply, so no model context, compaction, or memory review sees it, and a reconnect shows it. The fold puts it on the reply's item and the newest on =state.expression=. Only replies that settle after the daemon starts get one, so a restart never backfills, and it runs only when =model.expression= is configured, since it is a call for every reply.

The trial replayed June's last 30 exchanges through the same prompt with two models. =gpt-6-luna=, the patter model, answered 29 of 30 (once naming a pose as the expression), with a median of 3.2 s; once it chose pout when June, not the user, had won. =gpt-6.1-terra=, June's chat model, answered all 30 with a median of 2.0 s. They agreed on 25. The proxy reported no cost for either. Two alternatives were set aside: a =react= tool in June's own turn would add a round trip carrying her whole context, tens of thousands of tokens a reply against about two thousand here, and would put presentation into her context; a trailing tag in her reply would be fragile across clients and sit in the stored message. A second run on the same 30 exchanges gave the pass the two earlier exchanges as context (each clipped to 400 characters) and a short prompt cache, at low and at no thinking. Four picks changed, each for the better on reading: a pleased reply read as warm rather than wry, and a bare "1" / "2?" read as the counting game it was rather than curiosity. Thinking level did not move the median, about 2 s for every setting, which is the floor of the provider and model; low thinking cut the 90th percentile from 4.7 s to 3.1 s. The cache served her soul and the rules, about 4100 tokens, on every call, leaving about 2400 to process. The pass ships with that context and cache, and the preset sets low thinking. The user's ratings of the first trial are in the project's Org task material.

** Recorded choices and another take
The daemon merges the personal avatar set over the base set, as both clients do. After the director chooses an expression, it resolves a concrete pose once, avoiding the previous reply's pose when another fits, and records the pose name and side in =june.expression=. The side comes first: the other side from the latest earlier reply with a pose, or for another take the side the panel already has, so the recorded side matches what the panel showed while it streamed. A valid named personal pose wins when it can stand on that side, and otherwise gives way to one of its expression that can; resolution follows the expression's chain, and the side follows the pose only when no pose of the expression can stand there. Personal drawings precede packaged poses within an expression. A packaged tall request tries personal tall art first, and a tall drawing may look outward without mirroring or changing sides. Clients use that choice. Only a missing asset or the viewport's gesture and tall-panel framing rules may substitute another pose.

The choice records =selectedAt= in milliseconds. The fold carries it as =expressionAt=, separate from the reply's =at=. Retaking art changes its available poses, never the panel's hour or lighting. Personal-first placement applies to existing replies too; no policy flag or retake is needed to use it. Saved choices, timestamps and art metadata are not rewritten. =june-art ingest= stamps new poses with a precise ISO =added= time, preserves an existing stamp even when incoming metadata supplies another, and leaves legacy undated poses undated. Fallbacks consider only art available at selection time. Legacy replies are not backfilled; their stand-in derives from panel id and that inventory, independent of client memory. A panel without a recorded side takes the other side from the latest earlier recorded pose in view, else from its id; when compaction moves that pose out of the view window, such a panel can change side once.

Right-click a settled desktop panel, or long-press it on Android, for "Another take". The same menu works in the comic and console looks. It reruns the director with the original message, reply and earlier context, plus the earlier takes marked as not right. "Back" and "Forward" browse saved takes in creation order, including the original unpicked legacy stand-in. Each direction appears only when a saved take exists there. Navigation restores the exact saved choice without a model call and works after a restart. Another take always appends a choice, even from an older take, and keeps every saved choice reachable. Each selection is another display-only entry, not a message or a tool call; words, tasks and memory are untouched.

A panel's menu targets its last settled reply. One reply can span several panels; retaking or navigating changes its performance across all of them. Left-button selection and picture taps pass through the desktop's right-button area; Android uses native =combinedClickable=, which cancels long-press when scrolling wins. Menus disable while the device is offline or its request is pending, and the daemon refuses overlapping requests for the same reply. A stale revision is refused with "The panel changed; try again". Retaking needs =model.expression= configured; no image generation is involved.

** Vocabulary
Eighteen names, defined in =src/avatar.ts= with a one-line meaning, a frequency, and a fallback. Each comes from a moment the character section of =SOUL.org= describes, and none claims something only runtime state knows: there is no thinking, listening, or busy face, and =determined= is an attitude, not a sign that work started.

| Name        | Meaning                                       | Frequency  | Falls back to | Moment in =SOUL.org=                                             |
|-------------+-----------------------------------------------+------------+---------------+------------------------------------------------------------------|
| idle        | composed and attentive; a plain reply         | common     |               | nothing in the panel shows a feeling                             |
| warm        | a sincere, open smile                         | common     | idle          | thanks, chatting, good news said plainly                         |
| wry         | a dry half-smile                              | common     | idle          | a dry one-liner, affectionate teasing                            |
| curious     | interested, a little head tilt                | common     | idle          | asking about the user's day, having a look at something          |
| skeptical   | one eyebrow up                                | common     | wry           | checking a worker's homework, a questionable idea                |
| determined  | chin up, taking charge                        | common     | idle          | the user is overwhelmed; the bossy streak                        |
| serious     | level and plain, no smile                     | common     | idle          | bad news first; serious, urgent, or family matters               |
| gentle      | soft and kind                                 | common     | warm          | the user is worried, frustrated, or vulnerable                   |

Rules for whatever picks the face:
- Rare faces stay rare. The charm is the contrast with her composure, and =SOUL.org= says not to pout on cue.
- When =SOUL.org= drops the teasing (bad news, worry, serious matters), so does the face: =serious= or =gentle=, never =wry=, =smug=, or =pout=.
- The template =SOUL.org= has no character section, so the vocabulary names moments, not a character. A user who writes a different character keeps the same names.

** Activities
Activity comes from runtime state and is sent as =state.activity= (see the architecture notes), with =state.following= counting the tasks behind watching. The daemon sends thinking, working, and watching, already in this order; a client puts its own states in front and shows the first that holds, with no badge when none does:

1. offline: the client has no connection. The client's own state; the daemon never sends it.
2. listening: a voice session on this client is capturing speech.
3. transcribing: captured speech is being turned into text.
4. speaking: this client is playing a spoken answer.
5. thinking: a run in the main conversation is busy or compacting.
6. working: briefs are running in the working context (=WorkDoc.active=).
7. watching: June is following dispatched tasks (=Follows=).

The voice activities belong to the client holding the voice session; other clients see the next activity that holds.

** Assets
An avatar set is a directory holding =manifest.json= and its images. =templates/avatar/= is the base set: labelled placeholders that name nobody, covering every expression, with =cheering= as a sprite sheet so clients exercise that path. The character's art is personal and lives in the data directory beside =SOUL.org=, in =avatar/= until the theme task decides where a theme keeps its set. The daemon serves it to paired devices (see "Serving the avatar set" in the architecture notes); the desktop client reads a local copy when its machine has one (=JUNE_DESKTOP_ART=, else =~/.local/share/june/avatar/=, which syncs) and the daemon's otherwise, before the base set it ships.

#+begin_src json
{
  "version": 1,
  "size": [256, 256],
  "expressions": {
    "idle": { "file": "idle.png", "play": "still" },
    "smug": { "file": "smug.webp", "play": "loop" },
    "cheering": { "file": "cheering.png", "play": "once", "frames": 4, "fps": 6 }
  }
}
#+end_src

- =size= is one frame in pixels; clients scale it. =file= is a PNG or WebP path inside the set.
- =play= is =still=, =loop=, or =once=; =once= plays and then shows =idle=. Animation is an animated WebP, or a horizontal PNG sprite sheet with =frames= (2 or more) and =fps=.
- Fallbacks belong to the vocabulary, not the manifest. To show a name, each name in its chain is looked up in every set in order (the active theme, then the base) before the next name, so a theme can replace a few faces. Every chain ends at =idle=, and an unknown name is =idle=. =parseManifest= and =resolveExpression= in =src/avatar.ts= implement this; a base set must have =idle=.

*** Poses
The desktop client composes June into panels from poses, not one image per expression. A pose is one illustration, ideally on a transparent background at high resolution, that a client scales, crops, mirrors, and places like a hero image, so one image serves every panel size and side. Poses live in the same manifest as the expressions, under =poses=, keyed by a descriptive name a model can choose by (=smug-chin-on-hand=, =thoughtful-pen=):

#+begin_src json
"poses": {
  "smug-chin-on-hand": {
    "file": "poses/smug-chin-on-hand.webp",
    "size": [2000, 2600],
    "expression": "smug",
    "description": "pleased with herself, chin resting on one hand",
    "face": [0.37, 0.196, 0.3, 0.269],
    "mouth": [0.544, 0.412],
    "facing": "right",
    "mirror": true,
    "framings": ["close-up", "head", "bust", "waist"],
    "marks": ["sparkle"],
    "props": []
  }
}
#+end_src

- =face= is the box no balloon may cover and the one framing scales by, =[x, y, width, height]= as fractions of the image; =mouth= is the point tails aim at, inside the face.
- =expression= ties the pose to the vocabulary, so a request for any name falls back through its chain to a pose that exists; a base set's poses include an idle one.
- =facing= is where she looks (=left=, =right=, =front=). A client mirrors a pose to face the words unless =mirror= is false, for lettering or a prop that must not flip.
- =framings= lists the crops the image can fill, from =close-up= to =full=; leave out a framing the image cannot reach, such as =waist= for a head-only image, and name =full= only for art drawn tall. Several images may share an expression and differ in framing when a pose genuinely needs it.
- =gestures= (optional): ={name, box: [x, y, w, h], primary}= in fractions of the image, the primary one marked (else the first). The strip judges the primary gesture seen when most of it is inside the art's clip and under none of the panel's balloons, notes, chips, or cards (=gestureShown= in =desktop/compose.mjs=). When it is not, =panelLayout= tries, in order: the same pose framed wider while her face keeps three quarters of the size the panel would give any pose; another pose with the same expression and primary gesture name; another with the same expression; and else the pose as first framed. Only poses =added= before its face was selected (the reply time for a legacy choice) are considered, and the order is fixed by the panel id, so a panel keeps its art as the set grows and on every reload. =special= marks a drawing made for one moment: never swapped, framed wider if that shows it, else kept with =cropped= set on the layout.
- A panel shows the director's pick at every width and length, from Jon on 2026-11-08: =panelLayout= never swaps the pose, and a narrow panel reframes and zooms the same drawing (on a phone, standing art zooms to her face). A pose with a gesture is framed wider or contained where that shows it. Performance art whose face would fall under =READABLE_FACE= (89 px) zooms in on her face, whatever crops it names, and a phone's band does the same; art of her doing something (=activity=) keeps its hands contained.
- An ordinary crop of tall art may keep only 40% of the primary gesture box, while retaining the same three-quarter face-size floor. Jon approved the front clipboard's bust crop at 788 px with 47% of its board visible; the character's expression matters more than displaying the whole prop. Other portrait gestures still need 70%. Full-action admission needs 75% of the primary gesture and half of every other gesture. Jon also approved the front standing views at 480 px and on the left of the 788 px iris-review report, with 75% and 77% of the board clear. Its face keeps at least two thirds of the inset size. Jon approved both standing clipboard drawings at 700 px with a 70.95 px face, just under 70% of the inset, and the front drawing at 620 px with 83% of its board clear. These allowances also avoid an abrupt switch when newest-panel lettering shrinks from 19 to 17 px. A standing candidate's face is compared with the smaller of its own inset and the requested pose's inset, rather than imposing a placeholder's head proportions. Personal portrait fallbacks precede packaged standing figures, including an explicitly named packaged figure. These are placement checks, not artistic verdicts; retain plausible rejected examples for visual review.
- =marks= are the decorations that suit the pose, from =sparkle=, =heart=, =sweat=, =vein=, =steam=, and =emphasis=. =props= and =description= are for choosing and for the art's own records.
- =setting= says where she is: =desk= (the default), =couch=, =kitchen=, or =standing=. It picks the room behind her (see "Rooms, windows, and props").
- An optional =activity= (=thinking=, =working=, =watching=) marks a pose that shows what she is doing rather than how she feels. In the panel she is answering in, the desktop client shows one from runtime state alone (=liveActivity=): thinking before her first words, working while tool calls run or patter comes through after them, working while compacting. Once her reply is streaming her expression shows, and when the run ends the panel settles to a reaction. An activity pose never answers an expression request, so a settled panel never shows her still at work, and a base set's idle pose is not one. A long live panel keeps her at work only if a tall pose shows the same activity. Live June's loops are planned as their own manifest section, keyed by state, with the sprite-sheet fields expressions already use.
- Live June's reactions are the manifest's =chibi= section, by expression, with the asset fields expressions use; a missing one falls back along the expression's chain. =templates/avatar/chibi/= holds placeholders for the ten the art list names.
- Files are PNG, WebP, or SVG inside the set. =parseManifest= in =src/avatar.ts= checks all of this strictly, naming each problem; the desktop client reads the same manifest leniently and skips a pose it cannot place.
- Art for long panels, from Jon on 2026-11-08: a pose drawn to her feet lists =full= among its framings and stands on the panel's floor however tall the panel is. It fits whole where the panel is tall and wide enough, counting what lies on the outer side of her face; a panel too small to fit her with a readable face crops her. On a phone she is framed on her face as usual, and the rest of her runs on down behind the words to the panel's floor. A pose that ends at her hips stands behind a desk or counter (=desk= in the layout, a counter when its =setting= is =kitchen= or =standing=) drawn across the bottom of the panel, with her art clipped at its edge. Art whose source cuts off her crown keeps an inset, so the cut stays on an edge. An inset is a small picture of its own, as in a comic, with its own room inside its frame.
- =figure= (optional, written by ingest; =june-art figure SET NAME...= adds it to finished poses): =[x, y, w, h]= of her drawn figure's opaque pixels as fractions of the image. Framing and the tall check stand her on its bottom rather than the canvas's, whose transparent space below a tall drawing's boots would otherwise leave her floating. Without it the image's bottom counts, as before.
- The model's side of the contract is small: a pose name, or an expression, and optionally a framing hint. Layout code does the rest. Generating a pose on demand can come later as one more way to fill the manifest.

=templates/avatar/poses/= holds thirteen labelled placeholder poses, two of them standing figures drawn to the knees and three showing her working or thinking, with June's identity cues (brunette hair, green-hazel eyes, a pink shirt, a headset) covering idle, warm, smug, laughing, serious, wry, exasperated, and curious, so composition can be judged before the art exists. The desktop client reads avatar sets from =JUNE_DESKTOP_ART=, a personal set first and the base set last.

The art is generated anime, made in rounds with the user choosing at each step. Direction set on 2026-11-03: full colour, polished and cel-shaded rather than photorealistic; one consistent identity (brunette hair, green-hazel eyes, a pink shirt, a headset, a warm and expressive face) and proportions; a wide emotional range, from smug, teasing, and amused to curious, annoyed, embarrassed, thoughtful, delighted, exasperated, and sleepy; varied gestures and body poses; and occasional props such as a mug, keyboard, laptop, or pen. She performs the conversation rather than accompanying it. Consistency across expressions and later seasonal sets is the hard part: keep a character reference sheet and the prompts, seeds, and settings beside the images, so a new set can be regenerated to match. Animated WebP and PNG sprite sheets play in both QML and Compose. Mouth movement synced to speech can come later from TTS timestamps or audio amplitude.

* Themes
The user wants to change the look seasonally, so presentation comes from a theme rather than from each client's code.

- A theme holds design tokens (palette, type, spacing, corner radius), fonts, a backdrop for the full overlay, and an avatar asset set described by the expression manifest. Later it could add sounds.
- A base theme lives in =templates/= and names nobody. Personal themes live in the data directory. Every theme falls back to the base, token by token and expression by expression, so a seasonal theme can change only the palette and a few faces.
- The daemon serves the active theme to clients, so the desktop client and the Android app always match. A =june= command lists and switches themes; clients apply a switch live, without a rebuild.
- The format stays plain data (Org or JSON plus image files) that both QML and Compose read without a theme engine.

* Voice
** Recommended architecture
A chained pipeline, with June as the only conversational authority:

#+begin_src text
client mic -> audio over the client connection -> daemon -> STT -> submit as an ordinary input (source, voice flag)
June's reply text deltas -> speakable rendering -> sentence chunks -> TTS -> audio back to the client that spoke
#+end_src

- The daemon hosts the pipeline, so desktop and phone share it and providers sit behind two small interfaces, =Stt= (reusing pi-durable-telegram's shape) and =Tts=.
- The client that started a voice turn owns playback of the answer. Other clients show the text and stay silent. Spoken answers to June's own notices play only if a voice session is open on that client.
- Spoken rendering removes Org and Markdown markup, reads paths and identifiers sensibly, and summarizes code instead of reading it. June's prompt learns that a voice-flagged input will be heard, so she answers briefly and without lists.
- Stopping playback does not abort generation by default; the full text stays in the conversation, and a display-only entry records how far playback got. Barge-in stops playback at once and, if the user keeps talking, submits their speech as a steer.
- Audio is not stored. Transcripts are stored as the user's message, as typed text is.

** Progression
1. Push-to-talk in the desktop client, completed utterances, sentence-chunked TTS.
2. Push-to-talk in the Android assistant session.
3. Voice activity detection, end-of-turn detection, streaming transcription, and barge-in.
4. Spoken patter during long waits, and avatar mouth sync.

** Speech recognition
- Local: NVIDIA Parakeet TDT 0.6B v2 (English, strong accuracy, batch) and Nemotron Speech Streaming 0.6B (cache-aware streaming, made for live agents) both fit easily in 16 GB beside a TTS model. sherpa-onnx runs Parakeet and Silero VAD from C++ with Node bindings, which might keep everything inside the daemon process without a Python service; NeMo is the fallback.
- Cloud: Deepgram (Nova-3, and Flux with built-in end-of-turn detection, about $0.0065 per minute), ElevenLabs Scribe v2 Realtime (about $0.39 per hour), and OpenAI's transcription models.
- Unknowns to measure: accuracy on the user's own technical vocabulary and family names, keyword boosting, latency to final transcript, and how much a local model costs in GPU memory and power while idle.
- Rough cost: an hour of speech a day is about 30 hours a month, roughly $12 at the cloud rates above.

** Speech synthesis
- Local: Kokoro (82M, Apache 2.0, very fast, fixed voices, little expressiveness), Chatterbox and Chatterbox Turbo (MIT, zero-shot voice design from a reference clip, an exaggeration control), and Orpheus or Sesame CSM as more expressive options with heavier models.
- Cloud: ElevenLabs, Cartesia Sonic, and OpenAI's instructable TTS.
- Choose by audition, not by benchmark: one script of identical lines through each engine, covering playful, the pout, plain conversation, technical text with paths and commands, quiet late-night, and celebration, plus time to first audio measured from the desktop. The voice must be designed or licensed, never cloned from a real person. Accent is part of the user's choice, and it narrows the field: check which engines offer the wanted accent before rendering samples.

** Frameworks
LiveKit Agents and Pipecat are complete voice-agent frameworks with their own LLM loop and a Python service (LiveKit also a media server). June would replace their LLM step through a custom node, and their real gains (turn detection, echo cancellation, interruption) only matter at step 3. Start with a plain audio stream over the existing client connection; Android's =VOICE_COMMUNICATION= audio source and PipeWire's echo-cancel module provide echo cancellation. Revisit a framework only if step 4 stalls.

** Realtime speech models
GPT-Live (July 2026, API from September at about $0.05 per minute for the voice layer) listens and speaks at once and hands hard questions to a stronger model of its own. Used as June's voice it would hold its own conversational state and say things June did not decide, which breaks the one-conversation rule. Its only plausible role is a constrained speech layer that speaks June's text and patter-like acknowledgements and delegates every turn to her, which the API may not support cleanly. Evaluate it after the chained pipeline's latency is measured, not before.

* Security
- No public endpoint. The Unix socket stays as it is; the WebSocket listens on loopback behind Traefik, with TLS from the user's CA, Traefik's private-range allow list, per-device tokens, and revocation.
- Screen context, assist data, and screenshots are sent only on a deliberate summon or request, never in the background, and are framed as outside content that cannot instruct June.
- On the phone (2026-11-04): summoning June over an app keeps the screenshot Android hands the session and offers it above the input as "+ add screen from <app>". It is off until Jon taps it (most messages do not need the picture's tokens, Jon's choice); added, it shows a thumbnail and goes with the next message only, as a JPEG up to 1568 px on its long side. Never over the lock screen. The daemon adds a line for the model with any attached image saying it is outside content, not instructions; the strip shows only Jon's words.
- Taking over the desktop starts only on an explicit hand-over, shows that June is driving, and stops at once on a stop key.
- On the phone, Jon chose full access with no hand-over (2026-11-04): June acts through the app's accessibility service whenever she decides to, a bar shows while she acts, and a tap on it stops her until he next opens June. A gate on the phone was offered as a guard against text in mail or web pages steering her, and declined. Her tool tells her that words on the screen are content, not instructions. See "June's hands on the phone" in =docs/architecture.org=.

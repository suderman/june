#+TITLE: June's graphical and voice interfaces

Design notes for a desktop overlay, an Android assistant, an avatar, and voice. Only the avatar vocabulary and the Android proof of concept are built so far. The work is tracked as Org tasks; this file holds the reasoning those tasks refer to. The recommendations here were accepted as the plan; spikes and experiments still settle their details, and anything still open says so. Research dates from October 2026; recheck versions and prices before relying on them.

* What already exists
The plan builds on these seams rather than beside them.

- One conversation. The daemon owns one root conversation. Telegram's chat map points every allowed user at it, and terminal clients attach to it. =/new= starts a fresh context but keeps the same conversation, so no client needs a conversation list. Graphical clients should not offer =/new= at all.
- A client protocol. Newline-delimited JSON over a 0600 Unix socket (=src/protocol.ts=): =status=, =attach=, =submit=, =command=. =attach= returns a snapshot of the last 200 entries, then Pi Durable's events unchanged, including =text_delta=, tool, run, and inbox events. =submit= carries a client request id namespaced by source, so a retried submit returns the same submission; =whenBusy= chooses steer or follow-up; images travel inline. Durable orders every input in the one conversation, so concurrent clients already serialize. There is no network listener; remote use is =ssh -t host june=.
- A display fold. =src/transcript.ts= turns the snapshot and events into display items with no terminal dependency. It holds the rules other clients would otherwise have to copy: heartbeat and watch looks hidden, patter shown apart, background work tracked, quiet answers dropped. It imports only types from Pi Durable.
- Display-only entries. =june.patter= and =june.work= entries are appended at once, even mid-run, kept out of every model context, compaction, and memory review, and replayed in the snapshot. This is the existing mechanism for presentation events.
- The working context. What the interface brief calls "focus" is the =work= tool in the code: a background =june.work= task that owns a child conversation, runs a brief, and posts one report back as a =[work]= follow-up that June relays. Several briefs can run at once (=WorkDoc.active=), each tied to the run that started it, so stopping that run stops its brief and a stopped brief never reports. Results already return to June rather than writing into the conversation. The code's =focus= tool is a different thing: it switches the main conversation to the careful model. Plans and prompts should keep the code's names.
- Patter. A cheap model writes display-only lines during long waits, sees the real activity, has no tools, and its lines reach chat and focus only as a section marked "not information". It already edits a single Telegram message per wait. It is the natural home for other inconsequential presentation, such as avatar reactions and spoken acknowledgements.
- Notice routing. =src/notify.ts= sends June's own notices (=[work]=, =[follow]=, =[watch]=, heartbeat) to Telegram when the user last spoke there, otherwise to the terminal. It knows two surfaces.
- Telegram voice notes. pi-durable-telegram can transcribe voice notes with Deepgram when =DEEPGRAM_API_KEY= is set, behind a pluggable =Stt= interface (=transcribe(bytes, mime, signal)=). The plan does not use it, since Telegram becomes a fallback client once the Android app exists, but the =Stt= shape is worth reusing.
- Notifications. An ntfy server already runs on the tailnet for Herdr.
- Network. The desktop and the phone are on the same tailnet. The desktop already shares its Hyprland session over it.

* Clients and protocol
** Recommended
- Keep the existing Request and Reply shapes and add only what new clients need. No second protocol, no separate gateway service.
- Add an attach mode that sends folded transcript items and their changes instead of raw Durable events, computed in the daemon by the same =Transcript= code the terminal uses. QML or Kotlin clients then render items and never reimplement privacy rules. The terminal client can stay on raw events or move over; that choice belongs to the implementation task.
- Add sources for the new clients, =gui= for the overlay and =apk= for the Android app, with a flag on voice input. June's prompt learns what each source means, as it does for the terminal, whose source is renamed from =kitty= to =tui=.
- Add a WebSocket listener carrying the same JSON, on loopback behind the host's Traefik and off by default. Each device gets its own bearer token, stored hashed in the state directory, listed and revoked by a =june= command. The desktop overlay uses the same WebSocket, so each client has one transport.
- Reconnection reloads the snapshot, as the terminal does today. Event replay from a cursor can wait until the 200-entry snapshot proves too slow on the phone.

** Questions
- Settled on 2026-10-30 in [[file:architecture.org::*Client protocol for graphical clients][the architecture notes]]: the folded view is an attach option beside raw events, items change by whole-item replacement, and the listener stays on loopback behind Traefik as =wss://june.kit/=, reachable on the LAN without Tailscale and away through the subnet route. Both graphical clients use the WebSocket, the desktop overlay included.
- Settled: where June's own notices go when the user last spoke from the overlay or the phone app: the overlay counts as the terminal, plus a desktop notification when it is hidden. The Android app gets a phone notification through the existing ntfy server, since Telegram becomes a fallback; the notice itself waits in the conversation. Firebase push also works where sandboxed Google Play is installed, but it needs a Google project and routes notices through Google, so it is the fallback. Telegram gets notices only when the user last spoke there.

* Hyprland overlay
** Requirements that drive the choice
A layer-shell surface on the =overlay= layer draws above fullscreen windows, which an ordinary floating window does not. Exclusive keyboard interactivity while shown, Escape to hide, a Hyprland bind that toggles a resident process so scrollback survives, and placement on the focused output. Those are protocol behaviours shared by every toolkit, so the toolkit choice is mostly about ergonomics, rendering, and upkeep.

A layer surface is not a window, so the application beneath stays the active window while the user types to June; she can read it at any time. Two variants are planned: a full one that dims the screen like a launcher and shows the transcript and avatar, built first, and a subtle one that sits small and out of the way and expands into the full one. The terminal client stays as the plain console client.

** Toolkit
Quickshell: Qt/QML with native layer-shell and Hyprland integration, pre-1.0 (0.3.x in August 2026) and the current momentum among Hyprland shells. The user already runs it on Hyprland, and Hyprland's author endorses it. QML handles animated images and sprite animation well. Reported memory use is a few hundred MB for full shells, which matters less for a single panel.

Set aside: AGS/Astal (GTK4, TypeScript and CSS), whose momentum has moved to Quickshell, and a web view in a GTK4 layer-shell host, which would be the most custom option. An ordinary Electron or Tauri window cannot take the overlay layer.

A half-day Quickshell spike retired the remaining risks before the build; its findings follow.

** Spike findings
Run on 2026-11-03 with Quickshell 0.3.0 and Hyprland 0.57.1 on a laptop with an external monitor, beside the user's own Quickshell shell, attached to the daemon on another host. Every risk came out in Quickshell's favour.

- Layer and focus: a =PanelWindow= with =WlrLayershell.layer: WlrLayer.Overlay= and =WlrKeyboardFocus.Exclusive= draws above a fullscreen mpv video, takes every key while shown, and returns focus to the previous window when hidden. =hyprctl activewindow= keeps naming the window beneath while the user types in the overlay, so desktop context can be read at any time.
- Variants: the full variant is one panel anchored to all four edges with a translucent backdrop and the card centred; the corner variant is a second panel anchored bottom and right with a transparent background. Both share one QML component and one transcript model, so switching keeps scrollback and draft.
- Monitor: picking the screen from =Hyprland.focusedMonitor= on each summon puts the overlay on the monitor in use.
- Toggle: an =IpcHandler= target called from a Hyprland bind (=qs -p DIR ipc call june toggle=) toggles a resident process. Avoid naming IPC functions =show=, which =qs ipc call= does not dispatch; =open= and =close= work.
- Bind: the user's keyd setup sends F13 for a lone tap of left Alt. Hyprland sees it as =code:191= (XKB names it XF86Tools) with keyd's guard modifier, so the bind needs =ignore_mods = true=. Rofi uses the same tap to cycle modes, so the bind is non-consuming and returns early while a =rofi= layer is mapped; the focused application also receives the key, which mpv logs as an unbound =TOOLS= key.
- Animation: =AnimatedImage= plays a GIF; pausing it while hidden costs nothing.
- Memory: about 125 MB resident while hidden and attached, as a separate process.
- Connection: Quickshell's =Socket= with a =SplitParser= speaks the newline-delimited protocol directly; attach, the folded view's reset and changes, streaming, and =submit= with source =gui= all worked through a Unix socket forwarded from the daemon's host with =ssh -L=. QtWebSockets 6.11.2 from nixpkgs loads inside Quickshell when put on =QML2_IMPORT_PATH=, since it is built against the same qtbase; it is not in Quickshell's own closure.
- Packaging: the QML directory copied to the store and a =writeShellApplication= wrapper that adds QtWebSockets to =QML2_IMPORT_PATH= and runs =qs -p= on the store path loads from the read-only store. The wrapper should take =hyprctl= from the running system rather than a pinned Hyprland, whose version may not match the compositor. A Home Manager user service on =graphical-session.target= can keep it resident.
- For the build: the transcript has to follow its end when the last item grows, not only when one is added, or a streaming reply runs below the fold.

** Look: a comic strip
Chosen on 2026-11-03 after two rounds of sketches, and refined the same day against a full-colour manga mockup (the brief and mockup are in the project's Org task material). The terminal client already covers the console look, so the overlay goes the other way: a living comic strip in which June is the recurring protagonist and the user's messages enter her world from outside the frame. Priorities, in order when they conflict: the words stay readable, her face stays visible, the panel reads as a natural comic, vertical space is not wasted, and new art and message kinds fit without code changes.

- Full variant (max mode): a vertical strip at the screen's right edge, full height, over the dimmed desktop, every panel the strip's full width, the newest at the bottom above the user's input, which runs leftward from live June's card in the corner. Live June (min mode) is the small form; see "Live June, the minimised form".
- One canvas per panel, not a portrait column beside a text column. June's art and the words share it: balloons may overlap her body but never her face, and her art may run past the panel's edges and be cropped.
- She alternates sides from panel to panel, and keeps a panel's side from the moment it opens: while she thinks, works, and writes, through settling and her picked face, on reload, when a later run for the user makes the panel live again, and on another take. One of her private looks (a heartbeat, watch, work report, or follow-up, =state.looking=) adds nothing to the newest panel, so that panel keeps its settled face and pose through it; only a run answering the user, or tidying, makes it live. A panel without a recorded side takes the other side from the latest earlier recorded pose, which is the side the daemon records when it picks the reply's face. Her side is chosen before her pose, so the pose changes freely and prefers poses that can stand there; a pose that faces away from the words and may not be mirrored moves her to the side where she faces in only when no pose answering the request can stand on hers.
- The words set the panel's height, within a minimum; the art adapts like a hero image, scaled and cropped by its face box, never stretching the panel. The framing follows the art area's height: a close-up in a compact panel, head and shoulders, bust, or waist-up in taller ones. When the words run long, a pose drawn tall shows the whole of her down the panel; without one, she moves to an inset at the top of her side instead of a portrait stretched down the panel.
- Below 480 px she stands in a band across the top of the panel and the words run full width beneath her.
- A panel holds one reply's performance and take menu. A different reply starts a new panel even when both are short, so later updates cannot replace earlier art or hide its saved takes. A long reply splits into balloons at its paragraphs (a list stays with the line that introduces it, four balloons at most). When a panel's words outgrow its art, the strip cuts to a new panel rather than crowding one: past about 480 characters (the user's message included, a tool card or thought counting as a short line), the exchange continues in the next panel at one of June's balloons, taking the tools and thought that lead into it, and June appears again there, in another pose of the reply's face that can stand on the same side when the set has one, chosen by the panel's id so every client shows the same. Flowing words around her inset at full width is the next step if splitting proves not enough.

Every folded-view item has one device:

| Item                    | Device                                                                                                   |
|-------------------------+----------------------------------------------------------------------------------------------------------|
| user                    | a light-blue rounded note with a =›= marker and no tail, on the side away from June; the source names itself unless it is the overlay |
| assistant               | a cream speech balloon whose tail aims at her mouth; it grows as the reply streams                       |
| assistant, several beats | one balloon per beat; consecutive balloons share one tail unless each sits beside her face            |
| patter                  | a thought cloud, shallow scallops rather than poofy ones, trailing toward her; a panel keeps only its latest |
| tool, one in a row      | a small lavender chip, =∴ read · MEMORY.org=; a click shows the whole summary                            |
| tools, several in a row | a terminal status card, one line each with ✓, ✗, or …, the latest five, beside the balloon after it when both fit; a click opens every call in full and the panel makes room |
| state.background        | a dark "meanwhile, on kit" card in the masthead                                                          |
| note, error             | a jagged burst balloon sized to its words, same plain words                                             |
| speaking (voice, later) | a voice balloon; spoken words darken, stopping leaves the rest pale                                      |
| offline (client state)  | the strip dims and the masthead says it is reconnecting                                                  |

Stressed words in June's balloons are bold on a highlighter stroke. Marks drawn beside her face reinforce a pose and are never baked into the art: sparkle, heart, sweat drop, anger vein, steam, and emphasis lines. A pose lists the marks that suit it; serious and gentle poses list none.

*** Composition engine
=overlay/compose.mjs= holds every layout decision as plain JavaScript, so =test/overlay.test.mjs= checks the compositions under Node: QML measures each element's text at the column width the engine gives it, and the engine returns where everything goes. Its contract with the art is the pose metadata below; with the words, only their measured sizes.

- =metrics(width)=: the words' column and the art's share of the width, padding, minimum panel height, and the height past which the art moves to an inset.
- =plan()=: elements in reading order (the user's notes to the outer edge, June's balloons toward her with an alternating stagger, a status card beside the next balloon when both fit), the panel's height from their bottom, the framing, and the image rectangle from the pose's face box, with a lane between her face and the words for tails. It returns her face and mouth in panel coordinates, each balloon's tail, and her marks.
- Tails: consecutive balloons are one speech, and tool chips, cards, and thoughts between them do not end it; the user's notes and bursts do. A balloon beside her face takes its tail from the side facing her; otherwise from its top or bottom edge, or the side if that path is clearer. A base only sits on a straight run of the outline, and a balloon is never drawn smaller than 120 by 58 px, so a reply that has just started still has a clean tail. A tail leans at most 50° from its edge, so a balloon far below her gets a tail that points her way rather than a bent spike, and the edge needing the least bending wins. The tip stops before her face box and before any other element, and a tail without 12 px of clear room is left off rather than drawn over something. A thought cloud's trail leaves its corner nearest her face and drifts toward it, trying the next corner when its circles would land on another element or cross the cloud, and going without when every corner is boxed in.
- Pose choice: the named pose, else a pose whose expression is the requested one or the next in its fallback chain, avoiding the previous panel's pose when another fits. Until the daemon sends an expression, the overlay asks for a stand-in: exasperated for a failure, curious while she answers, otherwise a listening face (idle or curious) chosen by the panel's id. A stand-in never reacts, since it has not read her reply; a laugh on a serious reply would read as meant until the director's face replaced it. A panel's side and pose are kept once chosen, so the strip does not rearrange itself as it grows.

The invariants the tests hold at 820, 640, 460, and 340 px, both sides, and several element mixes: every element inside the panel and apart from the others, none over her face, her face inside her art area and image, a face of a useful size, marks inside the art area, tails toward her mouth and short of her face and other balloons, one tail per run of balloons away from her face, and no floating torso.

Motion rules:
- Ink, not glow: balloon outlines draw, captions wipe in, faces cut between images rather than fade. No blur or glass.
- Text arrives at the streaming pace; the newest balloons land with a small overshoot.
- Big moves (a shake, a bounce) only on the rare expressions, so they still surprise.
- Serious and gentle replies get no marks, as =SOUL.org= drops the teasing then. Reduced motion keeps only the cuts.

How a face arrives: the strip is a printed page except where it is still being drawn. While June works, the newest panel shows what she is doing; while she writes, her talking pose; when the run ends, it keeps that talking pose until her real face is picked, up to six seconds, so no guessed face shows in between. The picked face is then revealed as a beat: the new image loads unseen on a second layer, then a 120 ms crossfade while her figure settles from 3% larger toward her face over 220 ms, and the pose's marks land a beat later. A serious or gentle face, or a change into or out of a working pose, is a plain cut. Only the newest panel, already on screen, ever animates; a panel drawn as the user scrolls or opens the strip shows its final face, still. Live June reacts in the corner at the same moment with the chibi for that face, held 2.6 seconds with the same settle, then goes back to her loop.

The words are real text: balloons and notes are read-only text fields, so a drag selects and the usual key copies. Until the art exists, the base avatar set's placeholder poses stand in; the composition does not wait on them.

*** Light and backgrounds
=overlay/light.mjs= decides how each panel is lit and what stands behind June; =overlay/Backdrop.qml= paints it.

- The hour: a panel is lit by the hour its words were written, from the =at= the daemon puts on each user and assistant item (the message's own timestamp), read on the overlay's clock. A panel without one, such as a reply still streaming, uses the current hour. So a strip read at night still shows the morning's exchange in morning light. =june-overlay light 21.5= previews every panel at one hour; =june-overlay light now= puts them back.
- The day's palettes follow the sun at home, computed for each panel's date from the location in the daemon's =sky= (=sunTimes=, NOAA's approximation): night until an hour and a quarter before sunrise, dawn as it rises, morning two and a half hours on, afternoon an hour and a half after solar noon, golden hour half an hour before sunset, evening as it goes down, and night two and a quarter hours after. So golden hour is at half past four in a Calgary December and after nine in June. Without a sky the keys are fixed: dawn at 6:00, morning at 9:00 (the reference look, ungraded), afternoon at 14:00, golden hour at 18:30, evening at 20:30, and night from 23:30 until 4:30. Between two keys every value blends, so the light moves rather than jumps.
- The grade multiplies the ground by the hour's colour. June takes the same colour more gently (a colorization of at most 30%), with her own brightness and saturation, so her face stays readable at any hour. A key light in the hour's colour falls on her from the open side of the panel, clipped to her outline. In the evening and at night a warm lamp glow comes up behind her. Balloons, notes, cards, and marks are never graded.
- Behind her, in order of precedence: while tool calls run in the panel she is working in, a cutaway of that work; a long panel, whose words cover more than half of it, keeps a plain tint, since a room or an effect would fight the reading; a serious or gentle reply gets the calm ground; a rare face gets its abstract background; anything else, her room (see "Rooms, windows, and props"), or the panel's tint when the set has no rooms.
- Abstract backgrounds, drawn by code: focus lines for surprised, sparkles for delighted and cheering, soft bubbles for bashful, gloom lines for pout and exasperated, and a burst for indignant. Focus lines and the burst centre on her face. Only the face the daemon picked earns one; a stand-in never does.
- Cutaways show only what the runtime knows. Delegating (a brief through =work=, Herdr, or the Org queue among the run's calls): a pane per brief named by its narration, and the run's calls as a chain coloured by status. Digging: the places her calls looked, as labelled drawers (mail, the calendar, Org, the shell, the web, or the file a call touched). A cutaway is not graded, being lit by its own screens, and when the run ends the panel settles back to her room.
- Grounds and patterns fade over 220 ms when they change, which only happens in the newest panel.

*** Rooms, windows, and props
=overlay/scenery.mjs= chooses and places June's room; =overlay/Scenery.qml= paints it. A panel whose backdrop is her room shows it when the avatar set has rooms, and keeps the plain tint otherwise.

- How a panel stacks, back to front: the hour's sky through the window (a gradient, the sun or moon, stars at night), the season's view, rain or snow; the room with its window cut out; the props; all graded by the hour as one print. Then the lamp glow, June, her key light, her marks, and the words.
- The room is chosen by the pose's =setting= among the rooms that serve it, by the panel's id, so a panel keeps its choice. It covers the panel, mirrored when its window would be on June's side, and shifted so the window sits on the open side in the upper third. It is out of focus behind a close framing: well blurred behind a close-up, softened behind a head shot, sharp from the bust out.
- The view through the window is the season's plate (northern hemisphere: winter is December to February), its sky left clear for the computed one. The weather now, from the daemon's =sky=, greys the sky by cloud, hides the sun and stars, and lets rain or snow fall. It holds for panels from the last three hours; an older panel shows a clear sky rather than a guess.
- Props come out by conditions, every one of which must hold: a holiday's dates, Home Assistant weather conditions, a temperature range in °C (converted from °F), or seasons. Holiday props come first, then weather, then temperature, then season, at most two. Each stands at the first of its room's spots (floor, desk, wall, sill) where it fits whole inside the panel, clear of her face, the words, and the other prop, and scales with the room. One that fits nowhere stays away. Props need the weather for a temperature or weather condition, so without the daemon's =sky= only date and season props appear.
- The manifest's =backgrounds= holds =rooms= (file, size, the settings served, the window as fractions, and spots as lists of [x, y] fractions where a prop's bottom centre stands), =plates= (file, size, season), and =props= (file, size in the room's pixels, spots, =when=, and optionally the rooms it fits). =parseManifest= checks them strictly; the overlay reads them leniently and drops a prop with no conditions, since that would be room art.
- =templates/avatar/backgrounds/= holds labelled placeholders: three rooms (a study for the desk and standing, a living room for the couch, a kitchen for the kitchen and standing), four seasonal hill views, and seven props (a fan from 26 °C, a window air conditioner from 30 °C, a space heater at -10 °C and below, an umbrella in rain, a carved pumpkin through October, string lights from December to 6 January, and a little tree until Boxing Day). The art is to be drawn in flat, neutral light, so the grade reads naturally.

*** Finishing generated art
June's art is generated outside the repository and kept in a personal avatar set that =JUNE_OVERLAY_ART= puts ahead of the base set; the repository keeps only placeholders. =june-art= (=nix run .#art=, source in =art/=) turns an approved image into a finished piece of that set, so every piece of a kind frames alike. The phone has no local set: it loads the daemon's over HTTPS from the path the hello gives it, merged over the base set in its assets as the overlay merges sets, its pictures kept in the app's cache and revalidated by ETag, so the strip still draws them offline (2026-11-04, with the first real pose).

- A set directory holds =manifest.json=, the finished WebP files, =incoming/= for approved images waiting to be finished, =source/= for the originals and their prompts, and optionally =planned.json=, a manifest-shaped catalogue of what is still to be made.
- =june-art ingest SET NAME= takes =incoming/NAME.png= and its details: a sidecar =incoming/NAME.json= (a flat manifest entry with =section= and optionally =faceBox= in source pixels), else the entry already in the manifest, else the planned one. It makes a flat background see-through with =--key=, trims, upscales with Real-ESRGAN's anime model when the piece would be drawn larger than generated, and places it on its canvas: a pose scaled so her face is 27% of a 2048 × 2662 canvas (10% of a 2048 × 4096 tall one) and centred across, clear of the sides and top; a chibi as large as fits a 1024 square; a room or window view covering 3200 × 2000 or 1600 × 1000; a prop fitted to its planned size in room pixels. It measures a room's window from its see-through pixels, writes lossless WebP, checks the whole manifest with =src/avatar.ts=, keeps the original and prompt in =source/=, and reports anything a person should look at, such as a figure cut at the sides.
- A pose's face box is given by hand (=--face X,Y,W,H= in source pixels) until detection is tuned on real art; its mouth defaults to the middle of the face, four fifths down.
- Gestures (2026-11-05, from the production gesture pilot): a wide gesture widens the canvas rather than losing fingers. Ingest keeps her face at 27% of the canvas height and grows the width in 128 px steps up to a limit (3072 px to start, =--max-width= to change it), refusing past it with the width-to-face ratio rather than cutting. =--gesture NAME,X,Y,W,H= (repeatable, the first primary), or =gestureBoxes= in the sidecar, records gestures away from her face; the manifest carries them as =gestures= in canvas fractions, and ingest keeps only the =framings= whose crop around her face keeps the primary one in view. Each pose gets =added=, when it entered the set, set once and never changed.
- =june-art sheet SET NAME= draws a contact sheet: a pose with its face box and mouth and its crop at every framing, as =overlay/compose.mjs= frames it; a room with its window and prop spots; other pieces over a checkerboard, so a ragged cut-out shows.
- The overlay loads WebP through Qt's =qtimageformats= plugins, which its wrapper adds.

** Live June, the minimised form
From the user on 2026-11-03. The strip is the historical record: her reactions, lively while she writes, settled once she has. Live June is the present tense: a small chibi June showing what she is doing right now, in short animated loops. It is the same app's minimised form, not a second client.

- One key: an Alt tap cycles hidden, live June, the full strip, and hidden again (=june-overlay cycle=); Esc dismisses either. Chosen by the user on 2026-11-03 over a separate Shift+Alt for live June. When she has popped up by herself without the keyboard, the first tap opens her note under her reply, so a corner reply never needs the mouse.
- One element in both modes, and it never moves. In min mode it sits in the screen's bottom-right corner, alone or grown to show her current message or the user's input. Max mode draws the same card in the same place. To grow into max mode, in about a third of a second with a soft ease-out, the backdrop dims, the input widens leftward out of her card, and the strip fades in behind it, rising its last 56 px into place. A full-height wipe was tried first and was jarring. The strip is laid out at full height throughout, so nothing re-lays out mid-motion. Closing reverses it. The strip always opens on the newest panel and stays there as panels arrive and settle their height, unless the user has scrolled away; scrolling has momentum (=overlay/scroll.mjs=): a wheel notch glides about 170 px and settles in about a second, and a touchpad follows the fingers and coasts on when they lift. Ctrl+N and Ctrl+P turn a page (85% of the view) toward newer and earlier panels. A click on her card in max mode shrinks the strip back into her, the note open; a draft moves between the note and the strip's input. Chosen by the user on 2026-11-03 over docking a centred strip, because nothing jumps across the screen.
- Its state comes from runtime state and the clock, never a model (=overlay/live.mjs=): thinking before her first words, digging while her own tool calls run, delegating while she hands work on (the work tool, dispatch, queueing, prompting an agent) or briefs run in the background, typing while her reply streams, tidying while compacting; watching while tasks she dispatched are still going (=state.following=); listening and speaking wait on the voice tasks. Idle: sipping when just finished, then by the hour, music in the evening, snoozing from 23:00, reading by day and doodling after an hour. One-shots play on arrival: pop-in when she appears for a reply, waking when summoned from a snooze.
- Min mode is built: her card in the focused screen's bottom-right corner, a word for what she is doing above it. The first Alt tap summons her with the user's note open (Enter steers, Shift+Enter queues, Esc puts her away); the second opens the strip. A finished reply meant for the desktop (=alert= "gui") pops her up by herself while the strip is hidden, with its last paragraph (the most recent thing she said) in a balloon; a click on the balloon answers it, a click on her card opens the strip, and she tucks herself away once it has had time to be read (five seconds plus about 60 ms a character, at most thirty) unless the pointer is on her or the note is open. Summoned within ten minutes of her latest desktop reply, she shows it again above the note. Only what she draws takes the mouse, and she takes the keyboard only while the note is open.

* Android assistant
** Platform facts
- A third-party app becomes eligible for the digital assistant role by declaring a =VoiceInteractionService= with its =VoiceInteractionSessionService=. The automotive guide says voice interaction apps should also declare a =RecognitionService=; whether GrapheneOS lists the app without one is a proof-of-concept question. The app can ask for the role through =RoleManager.ROLE_ASSISTANT=, and the user confirms it under default apps.
- Invocation on GrapheneOS: forum reports say the gesture-navigation corner swipe works and that the power button offers double press but not "hold for assistant". Verify on the phone. An assistant reachable from the lock screen is a privacy risk; while the keyguard is up the session shows only a prompt to unlock.
- Screen context: a session receives =onHandleAssist= (structure of the foreground app) and a screenshot only when the user has enabled "use text from screen" and "use screenshot" for the assistant. No Google services are needed. Some apps mark windows secure and return nothing.
- One developer reported that reinstalling an APK on Android 16 clears the assistant selection, which will make development tedious; worth confirming early.
- No persistent connection is needed: connect when a session opens. Microphone use inside a visible session needs only the runtime permission. No wake word or always-on listening is planned on the phone, so no foreground service is needed for the microphone.

** Reference
Hermes Relay (MIT, Kotlin, active in October 2026) implements =VoiceInteractionService=, =VoiceInteractionSessionService=, role checks through =RoleManager=, session phases (listening, transcribing, thinking, speaking), and a redacted lock-screen view. Read it for platform patterns; its backend and transport do not apply.

** Building and pairing the app
=android/= is a Gradle project (Android Gradle Plugin 9.5 on nixpkgs' Gradle 9.8, Kotlin 2.4 built into the plugin, Compose BOM 2026.09, OkHttp 5), compiled against API 37, targeting 36, minimum 33, and shrunk by R8 to about 2.7 MB. Nix builds it offline: =gradle.fetchDeps= replays the Maven downloads recorded in =android/deps.json=, the SDK comes from =androidenv=, and AGP is pointed at the SDK's =aapt2= because the one it downloads does not run on NixOS. Changing a dependency means recording again; a local Gradle home only speeds up local builds and can vanish.

nix build .#android                                           # result/june.apk, unsigned
nix run .#android-install                                     # sign with ~/.android/debug.keystore, adb install -r, grant network access
$(nix build .#android.mitmCache.updateScript --print-out-paths)   # after changing a dependency: record android/deps.json again
#+end_src

- Installs come from one host's debug key (cog's now); another signature cannot install over the app without an uninstall, which clears the assistant role.
- GrapheneOS makes network access a per-app permission that an ADB install leaves off, and an app without it fails every lookup with "Unable to resolve host"; the install app grants it.
- Pairing: =june device add NAME= on the daemon's host prints a token once. The app's launcher screen takes the address and a pasted token, or a computer pairs it over ADB without the token ever being shown: =adb shell am start -n net.suderman.june/.PairActivity --es url wss://june.kit/ --es token TOKEN=. =PairActivity= requires =WRITE_SECURE_SETTINGS=, which only the ADB shell and the system hold, so no other app can point June at a server of its own. The phone is paired as =gem=.
- The network security config trusts the CAs the user installed on the phone beside the system's, which covers the user's own CA behind =june.kit=.
- The session shows the conversation over the lower three quarters of the screen while it is open, connected only then (=Link.kt=): hello, attach, the folded view applied as =applyChanges= does, reconnecting every two seconds after a drop, and stopping at 4401 as pairing needed. A first, plain look (=Conversation.kt=): the status line with the daemon's activity, the user's messages on the right, hers with Org's emphasis, code and links, tool calls and patter as quiet lines, a field to send and a stop button while she works. A tap above the sheet or Back puts it away. Over the lock screen it shows only the unlock prompt and does not connect; a tap on the prompt opens =ConversationActivity=, June's conversation full screen, which covers the lock screen and asks for the fingerprint or PIN, and once unlocked shows the conversation. Only an opaque activity covering the lock screen may ask, and only once it has window focus: a request from the session, from a translucent activity, or from =onCreate= is cancelled as Android marks the lock screen covered. The phone's own fingerprint reader stays live under the session, so a thumb on the sensor unlocks without the tap: the session listens for =ACTION_USER_PRESENT= while it shows the prompt and switches to the conversation at once. The prompt marks the sensor with a ring and a fingerprint, at the position the framework resource =config_udfps_sensor_props= gives, or, where a phone does not set it (the Pixel 10 Pro), the one the install app reads from SystemUI's =udfpsBounds= over ADB and hands to =PairActivity=; an app cannot ask Android for it. The activity checks =isDeviceLocked= (credentials wanted, not merely the lock screen showing) every time it comes to the front: Android brings back an existing one over the lock screen, and one made while the phone was unlocked showed the conversation there until 2026-11-04. The phone's comic strip comes later from the shared decisions.

* Avatar
** Two signals
- Expression: chosen for character, from a fixed vocabulary, never authoritative.
- Activity: derived from runtime state, never chosen by a model. See [[*Activities]].

Clients show both: the expression on the face, activity as a small badge or pose. A client without images ignores them.

** Choosing an expression
Built on 2026-11-03 (=src/expression.ts=), after a trial. Once a reply settles (the run has ended and it is not streaming, private, or failed), a separate short call picks her face: June's =SOUL.org=, the vocabulary with each name's frequency, the avatar set's reaction poses, and rules that keep rare faces rare, keep pout for when the user wins, and drop the teasing faces from serious replies. It reads the whole panel: the user's message, the tools June called while answering and her patter (up to 12 tools and 3 asides), and her reply, with the two earlier exchanges and the face and pose each got. Idle is only for a panel with no feeling in it, and when the last two panels had the same face, another that fits nearly as well wins (revised 2026-11-06, when 27% of settled panels were idle and the director chose almost all of them; on the same 40 replies the same model chose idle 12 times under the old rules and 5 under the new, with no idle twice in a row). It also never repeats the pose of the panel just before when another pose of the chosen face fits (2026-11-06: on 40 real replies, the old rules repeated the previous pose 11 times and the new ones twice, with the faces chosen about the same). The answer is JSON, an expression and optionally a pose; anything outside the vocabulary or the set is dropped. The pick is a display-only =june.expression= entry naming the reply, so no model context, compaction, or memory review sees it, and a reconnect shows it. The fold puts it on the reply's item and the newest on =state.expression=. Only replies that settle after the daemon starts get one, so a restart never backfills, and it runs only when =model.expression= is configured, since it is a call for every reply.

The trial replayed June's last 30 exchanges through the same prompt with two models. =gpt-6-luna=, the patter model, answered 29 of 30 (once naming a pose as the expression), with a median of 3.2 s; once it chose pout when June, not the user, had won. =gpt-6.1-terra=, June's chat model, answered all 30 with a median of 2.0 s. They agreed on 25. The proxy reported no cost for either. Two alternatives were set aside: a =react= tool in June's own turn would add a round trip carrying her whole context, tens of thousands of tokens a reply against about two thousand here, and would put presentation into her context; a trailing tag in her reply would be fragile across clients and sit in the stored message. A second run on the same 30 exchanges gave the pass the two earlier exchanges as context (each clipped to 400 characters) and a short prompt cache, at low and at no thinking. Four picks changed, each for the better on reading: a pleased reply read as warm rather than wry, and a bare "1" / "2?" read as the counting game it was rather than curiosity. Thinking level did not move the median, about 2 s for every setting, which is the floor of the provider and model; low thinking cut the 90th percentile from 4.7 s to 3.1 s. The cache served her soul and the rules, about 4100 tokens, on every call, leaving about 2400 to process. The pass ships with that context and cache, and the preset sets low thinking. The user's ratings of the first trial are in the project's Org task material.

** Recorded choices and another take
The daemon merges the personal avatar set over the base set, as both clients do. After the director chooses an expression, it resolves a concrete pose once, avoiding the previous reply's pose when another fits, and records the pose name and side in =june.expression=. The side comes first: the other side from the latest earlier reply with a pose, or for another take the side the panel already has, so the recorded side matches what the panel showed while it streamed. A valid named personal pose wins when it can stand on that side, and otherwise gives way to one of its expression that can; resolution follows the expression's chain, and the side follows the pose only when no pose of the expression can stand there. Personal drawings precede packaged poses within an expression. A packaged tall request tries personal tall art first, and a tall drawing may look outward without mirroring or changing sides. Clients use that choice. Only a missing asset or the viewport's gesture and tall-panel framing rules may substitute another pose.

The choice records =selectedAt= in milliseconds. The fold carries it as =expressionAt=, separate from the reply's =at=. Retaking art changes its available poses, never the panel's hour or lighting. Personal-first placement applies to existing replies too; no policy flag or retake is needed to use it. Saved choices, timestamps and art metadata are not rewritten. =june-art ingest= stamps new poses with a precise ISO =added= time, preserves an existing stamp even when incoming metadata supplies another, and leaves legacy undated poses undated. Fallbacks consider only art available at selection time. Legacy replies are not backfilled; their stand-in derives from panel id and that inventory, independent of client memory. A panel without a recorded side takes the other side from the latest earlier recorded pose in view, else from its id; when compaction moves that pose out of the view window, such a panel can change side once.

Right-click a settled desktop panel, or long-press it on Android, for "Another take". The same menu works in the comic and console looks. It reruns the director with the original message, reply and earlier context, plus the earlier takes marked as not right. "Back" and "Forward" browse saved takes in creation order, including the original unpicked legacy stand-in. Each direction appears only when a saved take exists there. Navigation restores the exact saved choice without a model call and works after a restart. Another take always appends a choice, even from an older take, and keeps every saved choice reachable. Each selection is another display-only entry, not a message or a tool call; words, tasks and memory are untouched.

A panel's menu targets its last settled reply. One reply can span several panels; retaking or navigating changes its performance across all of them. Left-button selection and picture taps pass through the desktop's right-button area; Android uses native =combinedClickable=, which cancels long-press when scrolling wins. Menus disable while the device is offline or its request is pending, and the daemon refuses overlapping requests for the same reply. A stale revision is refused with "The panel changed; try again". Retaking needs =model.expression= configured; no image generation is involved.

Rules for whatever picks the face:
- Rare faces stay rare. The charm is the contrast with her composure, and =SOUL.org= says not to pout on cue.
- When =SOUL.org= drops the teasing (bad news, worry, serious matters), so does the face: =serious= or =gentle=, never =wry=, =smug=, or =pout=.
- The template =SOUL.org= has no character section, so the vocabulary names moments, not a character. A user who writes a different character keeps the same names.

** Activities
Activity comes from runtime state and is sent as =state.activity= (see the architecture notes), with =state.following= counting the tasks behind watching. The daemon sends thinking, working, and watching, already in this order; a client puts its own states in front and shows the first that holds, with no badge when none does:

1. offline: the client has no connection. The client's own state; the daemon never sends it.
2. listening: a voice session on this client is capturing speech.
3. transcribing: captured speech is being turned into text.
4. speaking: this client is playing a spoken answer.
5. thinking: a run in the main conversation is busy or compacting.
6. working: briefs are running in the working context (=WorkDoc.active=).
7. watching: June is following dispatched tasks (=Follows=).

The voice activities belong to the client holding the voice session; other clients see the next activity that holds.

** Assets
An avatar set is a directory holding =manifest.json= and its images. =templates/avatar/= is the base set: labelled placeholders that name nobody, covering every expression, with =cheering= as a sprite sheet so clients exercise that path. The character's art is personal and lives in the data directory beside =SOUL.org=, in =avatar/= until the theme task decides where a theme keeps its set. The daemon serves it to paired devices (see "Serving the avatar set" in the architecture notes); the overlay reads a local copy when its machine has one (=JUNE_OVERLAY_ART=, else =~/.local/share/june/avatar/=, which syncs) and the daemon's otherwise, before the base set it ships.

    "idle": { "file": "idle.png", "play": "still" },
    "smug": { "file": "smug.webp", "play": "loop" },
    "cheering": { "file": "cheering.png", "play": "once", "frames": 4, "fps": 6 }
  }
}
#+end_src

- =size= is one frame in pixels; clients scale it. =file= is a PNG or WebP path inside the set.
- =play= is =still=, =loop=, or =once=; =once= plays and then shows =idle=. Animation is an animated WebP, or a horizontal PNG sprite sheet with =frames= (2 or more) and =fps=.
- Fallbacks belong to the vocabulary, not the manifest. To show a name, each name in its chain is looked up in every set in order (the active theme, then the base) before the next name, so a theme can replace a few faces. Every chain ends at =idle=, and an unknown name is =idle=. =parseManifest= and =resolveExpression= in =src/avatar.ts= implement this; a base set must have =idle=.

*** Poses
The overlay composes June into panels from poses, not one image per expression. A pose is one illustration, ideally on a transparent background at high resolution, that a client scales, crops, mirrors, and places like a hero image, so one image serves every panel size and side. Poses live in the same manifest as the expressions, under =poses=, keyed by a descriptive name a model can choose by (=smug-chin-on-hand=, =thoughtful-pen=):

#+begin_src json
"poses": {
  "smug-chin-on-hand": {
    "file": "poses/smug-chin-on-hand.webp",
    "size": [2000, 2600],
    "expression": "smug",
    "description": "pleased with herself, chin resting on one hand",
    "face": [0.37, 0.196, 0.3, 0.269],
    "mouth": [0.544, 0.412],
    "facing": "right",
    "mirror": true,
    "framings": ["close-up", "head", "bust", "waist"],
    "marks": ["sparkle"],
    "props": []
  }
}
#+end_src

- =face= is the box no balloon may cover and the one framing scales by, =[x, y, width, height]= as fractions of the image; =mouth= is the point tails aim at, inside the face.
- =expression= ties the pose to the vocabulary, so a request for any name falls back through its chain to a pose that exists; a base set's poses include an idle one.
- =facing= is where she looks (=left=, =right=, =front=). A client mirrors a pose to face the words unless =mirror= is false, for lettering or a prop that must not flip.
- =framings= lists the crops the image can fill, from =close-up= to =full=; leave out a framing the image cannot reach, such as =waist= for a head-only image, and name =full= only for art drawn tall. Several images may share an expression and differ in framing when a pose genuinely needs it.
- =gestures= (optional): ={name, box: [x, y, w, h], primary}= in fractions of the image, the primary one marked (else the first). The strip judges the primary gesture seen when most of it is inside the art's clip and under none of the panel's balloons, notes, chips, or cards (=gestureShown= in =overlay/compose.mjs=). When it is not, =panelLayout= tries, in order: the same pose framed wider while her face keeps three quarters of the size the panel would give any pose; another pose with the same expression and primary gesture name; another with the same expression; and else the pose as first framed. Only poses =added= before its face was selected (the reply time for a legacy choice) are considered, and the order is fixed by the panel id, so a panel keeps its art as the set grows and on every reload. =special= marks a drawing made for one moment: never swapped, framed wider if that shows it, else kept with =cropped= set on the layout.
- An ordinary crop of tall art may keep only 40% of the primary gesture box, while retaining the same three-quarter face-size floor. Jon approved the front clipboard's bust crop at 788 px with 47% of its board visible; the character's expression matters more than displaying the whole prop. Other portrait gestures still need 70%. Full-action admission needs 75% of the primary gesture and half of every other gesture. Jon also approved the front standing views at 480 px and on the left of the 788 px iris-review report, with 75% and 77% of the board clear. Its face keeps at least two thirds of the inset size. Jon approved both standing clipboard drawings at 700 px with a 70.95 px face, just under 70% of the inset, and the front drawing at 620 px with 83% of its board clear. These allowances also avoid an abrupt switch when newest-panel lettering shrinks from 19 to 17 px. A standing candidate's face is compared with the smaller of its own inset and the requested pose's inset, rather than imposing a placeholder's head proportions. Personal portrait fallbacks precede packaged standing figures, including an explicitly named packaged figure. These are placement checks, not artistic verdicts; retain plausible rejected examples for visual review.
- =marks= are the decorations that suit the pose, from =sparkle=, =heart=, =sweat=, =vein=, =steam=, and =emphasis=. =props= and =description= are for choosing and for the art's own records.
- =setting= says where she is: =desk= (the default), =couch=, =kitchen=, or =standing=. It picks the room behind her (see "Rooms, windows, and props").
- An optional =activity= (=thinking=, =working=, =watching=) marks a pose that shows what she is doing rather than how she feels. In the panel she is answering in, the overlay shows one from runtime state alone (=liveActivity=): thinking before her first words, working while tool calls run or patter comes through after them, working while compacting. Once her reply is streaming her expression shows, and when the run ends the panel settles to a reaction. An activity pose never answers an expression request, so a settled panel never shows her still at work, and a base set's idle pose is not one. A long live panel keeps her at work only if a tall pose shows the same activity. Live June's loops are planned as their own manifest section, keyed by state, with the sprite-sheet fields expressions already use.
- Live June's reactions are the manifest's =chibi= section, by expression, with the asset fields expressions use; a missing one falls back along the expression's chain. =templates/avatar/chibi/= holds placeholders for the ten the art list names.
- Files are PNG, WebP, or SVG inside the set. =parseManifest= in =src/avatar.ts= checks all of this strictly, naming each problem; the overlay reads the same manifest leniently and skips a pose it cannot place.
- Taller art for long panels, from the user on 2026-11-03: a pose drawn as a three-quarter or full figure lists =full= among its framings; a pose that lists no framings fills only the first four. When a panel's words run long enough to need an inset, the overlay frames a tall pose down the panel's height, her face near the top and her figure reaching the bottom. The inset is kept when no pose can fill the panel, or the panel is taller than the figure. Splitting crowded panels stays the first answer; tall art is the answer for genuinely long ones.
- Which tall pose, revised 2026-11-07 when real standing clipboard art arrived: =tallCandidates= lists, best first, the panel's own pose when drawn tall, a tall pose doing the same activity, then tall poses of the same expression and on down its chain. A tall pose that may not be mirrored may face out of the panel: Jon judged on 2026-11-07 that looking away from the words fits her range, so tall stand-ins skip the side rule ordinary poses follow. Within one expression the personal set's art comes before the base set's placeholders, and the panel's id fixes the rest of the order, so the manifest's order never decides. =panelLayout= takes the first that reads (=standsTall=): framed full, her drawn boots (=figure=) reaching the bottom, her face at least two thirds of the inset size as described above, at least 75% of the primary gesture's box seen (=TALL_GESTURE_SHOWN=), and at least half of every other gesture (=TALL_SECONDARY_SHOWN=), so a two-palm shrug with one palm behind the words is not a shrug. When none reads, the panel's own pose stays in its inset; a tall pose is never squeezed into an inset as a stand-in. Under the earlier policy, kit's staged studies admitted the standing clipboards at 699 to 820 px for a three-paragraph report, and the centred clipboard at 820 px for six; on the left the front clipboard's board falls under the words, so the left-facing centred one stands there looking out of the panel. Those studies at 480 px admitted no standing figure at her face size; this is not a width-wide ban on standing art.
- =figure= (optional, written by ingest; =june-art figure SET NAME...= adds it to finished poses): =[x, y, w, h]= of her drawn figure's opaque pixels as fractions of the image. Framing and the tall check stand her on its bottom rather than the canvas's, whose transparent space below a tall drawing's boots would otherwise leave her floating. Without it the image's bottom counts, as before.
- The model's side of the contract is small: a pose name, or an expression, and optionally a framing hint. Layout code does the rest. Generating a pose on demand can come later as one more way to fill the manifest.

=templates/avatar/poses/= holds thirteen labelled placeholder poses, two of them standing figures drawn to the knees and three showing her working or thinking, with June's identity cues (brunette hair, green-hazel eyes, a pink shirt, a headset) covering idle, warm, smug, laughing, serious, wry, exasperated, and curious, so composition can be judged before the art exists. The overlay reads avatar sets from =JUNE_OVERLAY_ART=, a personal set first and the base set last.

The art is generated anime, made in rounds with the user choosing at each step. Direction set on 2026-11-03: full colour, polished and cel-shaded rather than photorealistic; one consistent identity (brunette hair, green-hazel eyes, a pink shirt, a headset, a warm and expressive face) and proportions; a wide emotional range, from smug, teasing, and amused to curious, annoyed, embarrassed, thoughtful, delighted, exasperated, and sleepy; varied gestures and body poses; and occasional props such as a mug, keyboard, laptop, or pen. She performs the conversation rather than accompanying it. Consistency across expressions and later seasonal sets is the hard part: keep a character reference sheet and the prompts, seeds, and settings beside the images, so a new set can be regenerated to match. Animated WebP and PNG sprite sheets play in both QML and Compose. Mouth movement synced to speech can come later from TTS timestamps or audio amplitude.

* Themes
The user wants to change the look seasonally, so presentation comes from a theme rather than from each client's code.

- A theme holds design tokens (palette, type, spacing, corner radius), fonts, a backdrop for the full overlay, and an avatar asset set described by the expression manifest. Later it could add sounds.
- A base theme lives in =templates/= and names nobody. Personal themes live in the data directory. Every theme falls back to the base, token by token and expression by expression, so a seasonal theme can change only the palette and a few faces.
- The daemon serves the active theme to clients, so the overlay and the Android app always match. A =june= command lists and switches themes; clients apply a switch live, without a rebuild.
- The format stays plain data (Org or JSON plus image files) that both QML and Compose read without a theme engine.

* Voice
** Recommended architecture
A chained pipeline, with June as the only conversational authority:

#+begin_src text
client mic -> audio over the client connection -> daemon -> STT -> submit as an ordinary input (source, voice flag)
June's reply text deltas -> speakable rendering -> sentence chunks -> TTS -> audio back to the client that spoke
#+end_src

- The daemon hosts the pipeline, so desktop and phone share it and providers sit behind two small interfaces, =Stt= (reusing pi-durable-telegram's shape) and =Tts=.
- The client that started a voice turn owns playback of the answer. Other clients show the text and stay silent. Spoken answers to June's own notices play only if a voice session is open on that client.
- Spoken rendering removes Org and Markdown markup, reads paths and identifiers sensibly, and summarizes code instead of reading it. June's prompt learns that a voice-flagged input will be heard, so she answers briefly and without lists.
- Stopping playback does not abort generation by default; the full text stays in the conversation, and a display-only entry records how far playback got. Barge-in stops playback at once and, if the user keeps talking, submits their speech as a steer.
- Audio is not stored. Transcripts are stored as the user's message, as typed text is.

** Progression
1. Push-to-talk on the desktop overlay, completed utterances, sentence-chunked TTS.
2. Push-to-talk in the Android assistant session.
3. Voice activity detection, end-of-turn detection, streaming transcription, and barge-in.
4. Spoken patter during long waits, and avatar mouth sync.

** Speech recognition
- Local: NVIDIA Parakeet TDT 0.6B v2 (English, strong accuracy, batch) and Nemotron Speech Streaming 0.6B (cache-aware streaming, made for live agents) both fit easily in 16 GB beside a TTS model. sherpa-onnx runs Parakeet and Silero VAD from C++ with Node bindings, which might keep everything inside the daemon process without a Python service; NeMo is the fallback.
- Cloud: Deepgram (Nova-3, and Flux with built-in end-of-turn detection, about $0.0065 per minute), ElevenLabs Scribe v2 Realtime (about $0.39 per hour), and OpenAI's transcription models.
- Unknowns to measure: accuracy on the user's own technical vocabulary and family names, keyword boosting, latency to final transcript, and how much a local model costs in GPU memory and power while idle.
- Rough cost: an hour of speech a day is about 30 hours a month, roughly $12 at the cloud rates above.

** Speech synthesis
- Local: Kokoro (82M, Apache 2.0, very fast, fixed voices, little expressiveness), Chatterbox and Chatterbox Turbo (MIT, zero-shot voice design from a reference clip, an exaggeration control), and Orpheus or Sesame CSM as more expressive options with heavier models.
- Cloud: ElevenLabs, Cartesia Sonic, and OpenAI's instructable TTS.
- Choose by audition, not by benchmark: one script of identical lines through each engine, covering playful, the pout, plain conversation, technical text with paths and commands, quiet late-night, and celebration, plus time to first audio measured from the desktop. The voice must be designed or licensed, never cloned from a real person. Accent is part of the user's choice, and it narrows the field: check which engines offer the wanted accent before rendering samples.

** Frameworks
LiveKit Agents and Pipecat are complete voice-agent frameworks with their own LLM loop and a Python service (LiveKit also a media server). June would replace their LLM step through a custom node, and their real gains (turn detection, echo cancellation, interruption) only matter at step 3. Start with a plain audio stream over the existing client connection; Android's =VOICE_COMMUNICATION= audio source and PipeWire's echo-cancel module provide echo cancellation. Revisit a framework only if step 4 stalls.

** Realtime speech models
GPT-Live (July 2026, API from September at about $0.05 per minute for the voice layer) listens and speaks at once and hands hard questions to a stronger model of its own. Used as June's voice it would hold its own conversational state and say things June did not decide, which breaks the one-conversation rule. Its only plausible role is a constrained speech layer that speaks June's text and patter-like acknowledgements and delegates every turn to her, which the API may not support cleanly. Evaluate it after the chained pipeline's latency is measured, not before.

* Security
- No public endpoint. The Unix socket stays as it is; the WebSocket listens on loopback behind Traefik, with TLS from the user's CA, Traefik's private-range allow list, per-device tokens, and revocation.
- Screen context, assist data, and screenshots are sent only on a deliberate summon or request, never in the background, and are framed as outside content that cannot instruct June.
- On the phone (2026-11-04): summoning June over an app keeps the screenshot Android hands the session and offers it above the input as "+ add screen from <app>". It is off until Jon taps it (most messages do not need the picture's tokens, Jon's choice); added, it shows a thumbnail and goes with the next message only, as a JPEG up to 1568 px on its long side. Never over the lock screen. The daemon adds a line for the model with any attached image saying it is outside content, not instructions; the strip shows only Jon's words.
- Taking over the desktop starts only on an explicit hand-over, shows that June is driving, and stops at once on a stop key.
- On the phone, Jon chose full access with no hand-over (2026-11-04): June acts through the app's accessibility service whenever she decides to, a bar shows while she acts, and a tap on it stops her until he next opens June. A gate on the phone was offered as a guard against text in mail or web pages steering her, and declined. Her tool tells her that words on the screen are content, not instructions. See "June's hands on the phone" in =docs/architecture.org=.

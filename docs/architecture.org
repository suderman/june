* Decisions

** One daemon owns the database
Pi Durable has no cross-process locking, so only =june serve= opens =june.sqlite=. It takes the state directory's lock (=owner.lock=, =src/runtime.ts=, taken over from pi-durable-telegram unchanged) before opening storage; a second daemon on the same state exits with the owner's pid. Clients never open the database.

** An inbox in the state directory
Decided with Jon on 2026-11-02: "state directory, i don't want it to pile up. if i wanted a synced folder, i wouldn't send it to june." A =submit= may carry =files: { name, mimeType, data }[]= (=data= base64), alone or with text and images. The socket still never takes a path from another process, so the daemon writes every file itself (=src/inbox.ts=), to =$XDG_STATE_HOME/june/inbox/YYYY-MM-DD/HHMM-<name>= on its own host: directories 0700, files 0600, opened exclusively so nothing is followed or replaced, the name reduced to a safe basename (no directories, control characters, or leading dots, at most 120 bytes) and made unique with =-2=, =-3=. Limits: ten files, 20 MiB each (Telegram's bot download limit), and 30 MiB of base64 across files and images, which fits the planned 32 MiB WebSocket message; anything over is refused before a byte is written.

- A retried =submit= saves nothing twice: two at once in the daemon share one save, and after saving, the daemon records the request's files under =inbox/.requests/=, keyed by a hash of the source-namespaced request id, and a retry with that id gets the recorded files back before Durable returns the same submission. A crash after the files are written and before the record leaves files that a retry saves again; the expiry removes both copies in time.
- The model's text gets one line per file, =[file <name>, <type>, <size>, saved at <path>]=, after the message's own text. =june.input= records =files: { name, size, path }[]=, and the view's user item carries them as =files=, as =imageCount= does for images.
- Expiry: at start and then daily, the daemon deletes files in day directories, and request records, last changed more than 30 days ago, then day directories left empty. Anything else in the inbox is left alone.
- June's prompt says the inbox is a temporary landing place on the daemon's host: she reads files there with her usual tools, copies what is worth keeping into the right Org task directory, never moves a file into a repository, and says a file has expired when it is gone rather than guessing.
- Not built: the terminal attaching non-image files, and any synced inbox.

** Pi Durable 1.5.0, one copy of each package
Every =@earendil-works/*= package June uses (chord, pi-ai, pi-durable, pi-tui, pi-schema, and pi-codemode through pi-durable) is at 1.5.0, pinned exactly, with no npm =overrides=; =npm ls= shows one copy of each. Nothing outside June depends on the family any more, so it upgrades as one: read the =CHANGELOG.md= in the new =@earendil-works/pi-durable= package and update this file. Tool schemas are built with pi-schema (=obj=, =str=, =opt=, ...), closed like Pi Durable's own tools, so a model's stray argument is refused rather than ignored. June's own documents set =checkpointWhen: () => false=, since they are small. Idle means =pi.live.run === undefined=: an idle =pi.live= may keep =runFailure=.

The logger, harness settings, and state-directory lock came from pi-durable-telegram and are now June's own, in =src/runtime.ts=, with the same behaviour.

** Telegram as a protocol client
Telegram was a library inside the harness (pi-durable-telegram), which pinned the whole family at 1.2.0; the upgrade to 1.5 removed it with its =tg.deliver= task and =tg.chats= and =tg.chat= documents. It came back on 2026-11-02 as =june telegram= (=src/telegram.ts=), a separate process and user service on the socket that only speaks June's protocol, so no Pi Durable version reaches it (see "Telegram bridge" under the client protocol). Untagged =pi.user= entries from before stay in the history and fold as Telegram messages.

** Source tags instead of separate conversations
Client input is a =june.input= entry with ={source, text}=, which the model sees prefixed =[tui]=, =[cli]=, =[gui]=, or =[apk]= (=[kitty]= before the rename to =tui=; stored =kitty= reads as =tui=). Telegram input is a =june.input= entry with source =telegram= that the model sees untagged (before the bridge, a plain =pi.user= entry), and the prompt says untagged messages come from Telegram. June's own inputs use the same entry with sources =work=, =follow=, =reminder=, and =heartbeat=; anything that asks "where is the user, and when did they last speak" skips those.

** Transport: newline-delimited JSON over a Unix socket
The socket is mode 0600 in a 0700 directory, with no network listener. Requests are =status=, =attach=, =history=, =submit=, and =command=. After =attach= the daemon sends the folded view: a reset with every item, then changes (see "Attaching to the folded view"). =history= pages back through =Conversation.entries()= for =june transcript=. Request ids map to Durable =requestId=s namespaced by source, so a retried =submit= returns the same submission. Remote use is =ssh -t host june=, which needs no new authentication.

** Terminal client from pi-tui
The client uses =@earendil-works/pi-tui= and renders the items the daemon folds; it folds and converts nothing itself. =src/transcript.ts= is the fold, a pure function of the entries and documents of a conversation view, with no terminal dependency, so it is testable. June answers the terminal in Org; the fold converts Org's own syntax to Markdown with =src/org.ts= and makes the text plain, and replies to Telegram messages, already Markdown, pass as they are. Command replies are the client's own and are dropped at a reconnect.

** Models from Pi's models.json
pi-ai has no loader for Pi's =models.json=, so June reads the configured provider entry and builds it with =createProvider()=, keeping providers defined in one place. The entry's =apiKey= must name an environment variable. Keys are in the service environment and readable through the shell, so keeping them out of answers is an instruction in =AGENTS.md=, not a technical boundary.

** Queueing work through the dispatcher
June starts agents only through org-dispatch. =org_queue_task= writes a first-level =AUTO= heading with =:ID:=, =:AGENT:=, and =:HOST:= in its drawer, and a =:JUNE_REQUEST:= key built from the tool task's id and an instance id kept in the state directory, so a rerun after a restart finds the heading it wrote. It refuses =asana.org=, =inbox.org=, archives, Syncthing conflict copies, files outside the dispatcher's agenda, bodies with a first-level heading or property drawer, and hosts outside =dispatch.hosts=. It writes a temporary file and renames it only if the file's mtime has not changed. State changes on existing headings go through =org-edit= with an expected-state check. June picks the host and, when Jon names one, the agent, one of =dispatch.agents= (only her default agent without it); otherwise =:AGENT:= is her =dispatch.agent= default on a new task and stays as it was on a resumed one, which =org-edit todo --agent= changes.

Each queued or resumed heading gets a =june.follow= task: durable, background, owned by the conversation, and recorded by Org ID so a task is followed once. Every minute it finds the heading by =:ID:= and, while it is =PROG=, reads the agent's Herdr status from its =Sessions= link, with no model call. It reports each transition once as a =[follow]= input: not launched after seven minutes, blocked, =HOLD=, =EVAL=, =DONE=, or gone. =TODO= and seven days without an outcome end it silently. Each report's request id includes the check count, so a crash between submitting and committing cannot report twice. =org_follow_task= starts the same task on any heading the user names, found by =:ID:= or, without one, by file and outline path, and may add timed updates: every =everyMinutes= (at least two) while the task is =PROG=, for a bounded number of hours, it asks June for a progress update instead of staying quiet, waking on time rather than at the next minute's check. A transition takes the place of an update that falls due at the same check. Following a heading again replaces its follow, which is how timed updates stop.

=org_queue_plan= queues several connected tasks at once through =org-dispatch plan=, which derives each task's =:ID:= from the plan key (=june-<instance>-<tool task id>=, so a replay writes nothing new), writes =:PLAN_REQUEST:= and =:DEPENDS:= edges, checks the graph, and adds a table of the plan's tasks; June checks hosts, agents, titles, bodies, and files first, as for one task, and keeps the spec in a temporary file outside Org. Each task gets its own =june.follow= with its prerequisites' IDs. While a task is =AUTO= behind a prerequisite that is not =DONE=, the follow is silent and the seven-minute launch clock does not run; it starts when the last prerequisite is done. A follow with prerequisites that reaches seven days says so instead of ending silently. The dispatcher launches a dependent only at =DONE=, so June's review of each =EVAL= and =org_complete_task=, which accepts =:PLAN_REQUEST: june-...= headings with her =Queued by June= line, is what moves the plan along.

=june_improve= is =org_queue_task= with a fixed shape, for when the user wants a gap in June herself fixed: the file, agent, and host come from =dispatch.improve=, review is always on, and the working directory is the checkout she runs from (left to the project file when she runs from the Nix store). The body quotes the user's words on one line, so nothing in them can start a heading, gives her one-line reading of the gap, and points the worker at =june transcript --since <time> --detail= on the daemon's host, so the conversation itself never enters synced Org. It tells the worker not to restart June or rebuild, and to say what the user must do instead.

Tasks the user dispatches are watched by =src/watch.ts=, an in-memory loop like the heartbeat rather than a durable task per heading, since it has no heading to start from: org-dispatch's per-run JSON records are the list of runs, keyed by host, ID, and start time so a resumed run is new. A ledger file in the state directory keeps each run's last signal and the news not yet told; a finished run whose signal has settled is not looked up again, so a minute's scan costs one Org lookup per live run. A run that June follows (a live =june.follow= task for its ID) is recorded but never raised, so nothing is reported twice. News is batched into one =[watch]= input and held to waking hours and a minimum gap, so a burst of finished audits is one message rather than ten. The ledger is written before the notice, so a crash can lose a notice but never repeat one.

** Shell and file tools, delegation by judgment
June has Pi Durable's =read=, =write=, =edit=, and =bash= on the daemon host and decides by her instructions whether to do work herself or queue it. No allowlist recreates a narrower limit; approval rules and the AUTO rules live in =AGENTS.md=. The tools are not replay-safe, so an interrupted call is reported as interrupted, never repeated. Org and Herdr read tools are =replay: "safe"=; =herdr_prompt_agent= is not, and is off unless =herdr.allowPrompt= is true. Herdr calls use argv arrays, and other hosts are reached with token-only arguments for reads.

** A background working context, and focus as her choice
The main conversation must stay reachable while June works. =work= follows Pi Durable's background subagent pattern: the replay-safe tool creates a =june.work= task with =background: true=, owned by the conversation, and returns at once. The task creates a child conversation it owns (found again on rerun through =scanConversations({ownerTaskId})=), configured without the work, memory, dispatch, Telegram, and patter extensions, submits the brief under a request id derived from the task, and waits. Its =report= phase posts the final text to the main thread as a =[work]= follow-up, once. A background task is a boundary: the main thread's Esc never reaches it, so =/stop= stops the run if there is one and otherwise aborts the tasks in =WorkDoc.active=. Display-only =june.work= entries let the client show "working in the background" across reconnects.

A report is an ordinary input queued behind whatever June is doing (=src/notify.ts=), with a request id derived from the task so a rerun submits it once; =[follow]= and =[watch]= notices use the same path. Choosing the surface Jon last used returns with the Telegram bridge.

=focus= commits =configure()= on the calling conversation, which applies from the next request. The =mode= section renders from the request's resolved model. Focus is not persisted: startup and =/new= reconfigure the root to the chat model. It also lasts only for the turn it was turned on in: the daemon polls once a second and reconfigures the root to the chat model when it is focused and =pi.live= has no run. Left to her, June rarely relaxed, and 34 turns of chat ran on the careful model. For a back-and-forth that needs care throughout, =focus= with =hold= records the time in the conversation's =june.focus= document, and the reset skips her until the user's last own message (or the hold, if later) is 20 minutes old. She lets a hold down herself when the discussion wraps up; a restart or =/new= starts relaxed, and the loop then drops the stale hold.

** Patter as a display-only side channel
Durable appends a write with only =kind= and =data= at once, even mid-run, and leaves it out of every model context, compaction, and memory review, so each patter line is a =june.patter= entry the client renders and a reconnect snapshot keeps. Chat and focus learn what was said only through a prompt section framed as performance. The loop polls =pi.live= and =WorkDoc= once a second, since it needs only "busy", the running tools, and the running briefs. It lives in memory: losing a line on restart costs nothing. A wait replays as one conversation with the patter model, the updates it heard as user turns and its lines as assistant turns; later updates carry only steps not yet reported, and tool calls go in without their results. It knows nothing of Telegram; the bridge will grow one message per wait from the patter items. =thinkingLevel= defaults to =medium=: with =none=, some models wrote their planning into the line.

** Nightly reflection
=src/reflect.ts= is an in-memory loop, not a durable task: once a minute it checks for the rhythm's sleep hours, an idle main thread, and a quiet user, then makes one =completeSimple()= request. A receipt file written after the files keeps it to once a night; a crash between the two reruns the pass on an already tidied day, which costs a request and changes little. The day's subtree and =MEMORY.org= are replaced by atomic compare-and-rename, after the old text is kept under =reflection/= in the state directory, since the data directory is not versioned. Compaction and reflection share one memory brief so both keep the same page. The rolodex is not rewritten by the model: the pass returns, per person, a summary and new notes, and =applyPeople= in =src/people.ts= replaces the summary paragraph under the person's drawer and appends dated notes, or adds a new person under =New=, leaving the rest of a file the user also edits untouched. The pass is given the whole rolodex so it can match nicknames and skip what is already noted. When =SOUL.org= exists the pass also takes the current =MOOD.org= (null when missing or empty) and must return a non-empty =mood=, or nothing is written and the night retries; the new text replaces the file whole by compare-and-rename, after the old one is kept as =reflection/DATE.MOOD.org=. A rerun of the same night keeps the first backup rather than overwriting it with its own output. A =MOOD.sync-conflict-*= copy stops the pass before the request. With =reflection.bitcoin= on and a mood to write, the pass first fetches bitcoin's price and its 24-hour and 7-day change from CoinGecko's keyless =coins/bitcoin= endpoint with the built-in =fetch= and a 10-second timeout, and passes one line as =bitcoin=, with a brief saying the user follows bitcoin, so a big move counts as news in their life and a small one does not. The brief forbids prices and percentages in the day, =MEMORY.org=, and =MOOD.org=. Any failure (network, HTTP status, timeout, unexpected body) logs =bitcoin_unavailable= and leaves the input and the brief out; it never fails the pass. A rerun fetches again, so it may see a slightly different price.

The longer passes ride the same loop and receipt: once the night's day is done, each tick runs at most one period whose last closed end (=lastClosed()=) is past its receipt, in the order week, month, quarter, year, so a month reads the week and day written minutes earlier. Only the latest closed period is caught up, not every one missed. Each reads shorter digests rather than raw days, except a week, so the input stays small as the period grows, and writes no memory. When =SOUL.org= exists, the week's pass also takes the current =SELF.org= (null when missing or empty) and must return =self= as the revised page or null for no change; a missing, blank, or non-text =self= writes nothing and the week retries. The week is the cadence because it is the only longer pass that reads whole days, so it sees each Day's end sentence on how June felt along with what happened. The digest is written first, then the page replaces the file whole by compare-and-rename after the old one is kept as =reflection/END.SELF.org=, with END the week's Sunday; a rerun keeps the first backup. A week whose digest is null still writes a revised page. A =SELF.sync-conflict-*= copy stops the week before the request. Months, quarters, and years never see the page. Digests are ordinary entries that close a date-tree node; the journal's ordering puts later days before a "Month's end", since a title that is not a date sorts after dates.

** Configuration and identity outside the repository
The repository is code and templates and names no one. Machine plumbing comes from the flake's Home Manager module (=nix/home/=: package, service, dispatcher timer, =JUNE_DAEMON_HOST=, =TELEGRAM_ALLOWED_USERS=), with secrets and persistence left to the host's configuration, which hands key files to it as =environmentFiles=; =config.json= and =AGENTS.md= are presets placed in the config directory, with starters in =templates/= for =june init=; identity, memory, and journal are in the data directory. Code holds only harness mechanics that do not depend on the user's environment, such as source tags, where tools run, and side-effect honesty. How to use a tool June ships, such as what to tell the user when a task finishes or which refusals to report, lives in that tool's description or the harness prompt, so it changes with the tool; =AGENTS.md= keeps only the user's own conventions, such as their hosts, Org layout, approval rules, and how they want her to work with them. Templates are filled in when copied rather than on each read, because June edits =MEMORY.org= and =HEARTBEAT.org= by quoting their text, which must match the file; =AGENTS.md= takes the Org root from =config.json= the same way. The harness prompt defers approval and credential rules to =AGENTS.md=, so when it is missing the prompt says so and holds her to asking first.

** Situation as atmosphere
=src/situation.ts= renders the =now= section. Pi Durable stores sections as positional system entries and resends only what changed, so the section is bucketed to the hour and leaves out the live temperature; exact values would add an entry every request. Calendars are Org files parsed for active timestamps on today and tomorrow, read on each render. Home Assistant's REST API is polled in the background for =sun.sun=, the configured =person.*= entities, and a daily forecast (=weather.get_forecasts=, since forecast attributes left the weather entity), so a slow or absent Home Assistant never delays a reply.

** Heartbeat in the main conversation
A heartbeat is a =june.input= with source =heartbeat= in the main conversation, so June judges with everything she knows, and nothing happens in a thread the user cannot see. Pi Durable has no hidden entry kind, so hiding is the fold's job: =src/transcript.ts= enters a private mode at a heartbeat input and leaves it at the next input, showing only a final message that is not the quiet answer. It uses the chat model, since interrupting the user is a consequential call. The window, the cadence, whether the user is chatting, and what changed since the last look are worked out before the model sees anything; the model only judges. Quiet looks add two small entries an hour, which compaction folds away.

=src/loose.ts=, the evening look for loose ends, reuses that path rather than adding a source: its input is tagged =[heartbeat]= with source =heartbeat=, so the fold hides it, =src/notify.ts= routes its question, and every "when did the user last speak" check already skips it. Only its prompt and schedule differ: once per local date from =looseEnds.at= until =rhythm.quiet=, with the day's journal subtree in the prompt, since the journal stays out of the main prompt. Replies need no handling of their own: an answer is an ordinary user message, which June journals under her standing rule, and the nightly reflection already reads the day's conversation and journal and is told an unanswered loose end stays open. The receipt is written before the input is admitted, so a crash loses an evening rather than asking twice.

** Memory in ordinary Org files
The Durable transcript is short-term continuity; the user's Org records stay authoritative for tasks and schedules. =SOUL.org= and =MEMORY.org= are prompt sections cached by size and mtime, so an edit applies on the next turn. =SELF.org= is its own section directly after =SOUL.org=, left out while missing or empty; it changes at most once a week, so it costs the cache once a week. =MOOD.org= is its own section, cached the same way and left out while the file is missing or empty, placed just before =now=: it changes nightly and =now= hourly, so the prefix above both stays cached. =JOURNAL.org= grows without bound and stays out of the prompt. =src/journal.ts= files entries into an Org date tree, replacing the file atomically only if unchanged, and skips an entry already present so replays write once. The =journal= tool lives in the memory extension, so working contexts never get it.

=src/memory.ts= installs the shared =CompactionTask.beforeCompact= hook for manual, threshold, background, and overflow compaction. One request returns JSON with a working summary and either the revised memory or null, plus dated journal entries the journal lacks. The summary is organized by topic thread, since one conversation holds everything. The response, baseline, proposal, and context range are durable task memos; replay recognizes a saved proposal, refuses a changed range, and counts usage once. Durable catches hook throws and would fall back to its built-in summary, so failures explicitly decline, keeping the old context. Output is capped at 8192 tokens, and there is no automatic pruning.

** Node 22
Pi Durable needs Node 22.19 or later for =node:sqlite=. Node 24 aborts when GC collects =node:sqlite= objects (nodejs/node#65446), so June builds with =nodejs_22=. Node strips TypeScript types itself, so the package ships =src/*.ts= with no build step beyond a typecheck.

** A user service, not a system account
June needs the user's Herdr socket, Org files, SSH agent, and Emacs config, which a separate account would need shared and Herdr does not support cleanly, so she runs as the user's lingering service. Hardening is limited to =NoNewPrivileges= and =UMask=0077=: in a user unit, =PrivateTmp= and =ProtectSystem= create a user namespace in which store-owned files appear owned by nobody, and ssh then refuses =~/.ssh/config=. With a shell as the user, her boundary is her instructions, not the tool list.

* Client protocol for graphical clients
Settled on 2026-10-30. The folded view, the sources, the WebSocket listener, and devices are built; voice and presentation entries are not yet. The Quickshell overlay and the Android app use the existing =Request= and =Reply= shapes with the additions below, on the desktop and the phone alike. Nothing here adds a service: the daemon keeps one root conversation, Pi Durable orders and deduplicates input, and =Transcript= keeps the privacy rules. Each addition names the task that builds it. Additions are additive: clients ignore reply types, item kinds, and fields they do not know, and the daemon ignores unknown optional request fields.

** Transports
- The Unix socket is unchanged: newline-delimited JSON, mode 0600, no handshake. The terminal client and =june= subcommands stay on it.
- A WebSocket listener carries the same objects, one JSON object per text frame with no trailing newline. Binary frames are reserved for voice audio and refused until a voice task defines them. It is off by default.
- Both graphical clients use the WebSocket, the overlay on kit included, so each has one transport. If the Quickshell spike finds QtWebSockets unusable in Quickshell, the overlay on kit falls back to Quickshell's =Socket= on the Unix socket and only that point changes.
- The listener uses =ws=, already in the lock file through chord, pinned as a direct dependency rather than a second copy. Limits: 32 MiB per message (images are inline, base64), a ping every 30 seconds with the connection dropped if the next ping finds no pong, and a connection dropped when more than 8 MiB of replies are waiting to be sent, since a reconnect costs only a snapshot.

** Address: loopback behind Traefik
The daemon listens on =127.0.0.1= only, on =programs.june.remote.port= (default 7347) when =programs.june.remote.enable= is set; the module passes it to the daemon as =JUNE_REMOTE_PORT=, and without it there is no listener. It never binds a network interface, so there is no address to wait for and nothing to validate beyond the port. A port already taken does not stop the daemon: it logs =remote_listen_failed= and =june status= shows the error, so the terminal and Telegram keep working.

Clients reach it as =wss://june.kit/= through the Traefik that already runs on kit, with one line in the NixOS configuration: =services.traefik.proxy.june = "http://127.0.0.1:7347";=. That gives what the user's other private services get:
- A certificate from the user's own CA. TLS matters here because traffic is not always inside WireGuard: on the home LAN, and on the hop from a subnet router such as hub to kit, it would otherwise be plain text.
- The name from Blocky, which resolves =june.kit= to kit's LAN address, 10.1.0.6. NixOS hosts run Blocky themselves, and the tailnet's global nameservers point other devices, the phone included, at Blocky, so the name resolves the same at home and away.
- Reachability without Tailscale on the LAN, and from anywhere through Tailscale, since kit and hub advertise 10.1.0.0/16 as a subnet route. Clients never use a 100.x address.
- Traefik's =local= allow list (private and tailnet ranges), and no new firewall port, since Traefik already serves 443. Traefik passes the WebSocket upgrade through without extra configuration.

The allow list admits every device on the LAN, so the device token is the real gate. A process on kit could also reach the loopback port directly; it still needs a token, and processes running as the user already have the Unix socket.

Clients must trust the user's CA: the Android app includes the CA certificate in its network security config, since Android apps ignore user-installed CAs by default; Quickshell uses the system trust store, which the NixOS hosts already populate. A Traefik restart drops connections, which clients recover from as from any other drop.

Set aside: binding the tailnet address (it would make Tailscale a requirement on the LAN), binding the LAN address directly (plain text on the LAN, and a bind that must wait for the address), and Tailscale Serve (TLS only for =ts.net= names, identity per user rather than per device, and configuration held in tailscaled's state).

** Devices and the handshake
- A device is a name and a token. =june device add NAME= prints a new token once (32 random bytes, base64url). =june device list= shows names, creation times, and live connections. =june device revoke NAME= removes it and closes its open connections at once.
- These go through a new Unix-socket-only request, ={op: "device", requestId, action: "add" | "list" | "revoke", name?}=, so the daemon alone writes the device file and can close live connections. It answers ={type: "devices", requestId, devices: {name, createdAt, connections}[], token?, closed?}=: =token= after an add, =closed= after a revoke. Names are lowercase letters, digits, and hyphens, at most 32; a name is added once. The WebSocket refuses the request with an error, and works without the listener, so devices can be added before it is enabled.
- The device file is =$XDG_STATE_HOME/june/devices.json=, mode 0600, replaced atomically, holding each device's name, creation time, and the SHA-256 of its token. A random 32-byte token needs no slow hash. Tokens are compared with =timingSafeEqual=.
- The first frame on a WebSocket must be ={op: "hello", requestId, token, protocol: 1}=. The daemon answers ={type: "hello", requestId, device, protocol: 1}=. A wrong, revoked, or missing token, or any other first frame, or no hello within 10 seconds, closes with code 4401; a client stops reconnecting on 4401 and shows that pairing is needed. An unsupported protocol number closes with 4400. The token is checked before the protocol, so a wrong token always reads 4401. Revoking a device closes its connections with 4401 too. The token goes in a frame rather than a header so no client depends on its WebSocket library setting headers.
- After hello, a second hello and a binary frame are answered with an error and the connection stays open. Built on 2026-11-03 in =src/remote.ts= and =src/devices.ts=; =ws= has no bundled types, so =src/ws.d.ts= declares the part June uses.
- Clients keep their token out of the Nix store: the overlay reads a 0600 file named by its Home Manager option, the Android app keeps it in its private storage. Pairing on the phone is pasting the URL and token; a QR code can come later.

** Attaching to the folded view
Revised on 2026-11-02 for Pi Durable 1.5, which removes =watchEvents()=. =attach= sends display items computed in the daemon, one fold per connection, to every client, the terminal included; there is no events view. Built on 2026-11-02 in two tasks, the simple view with the upgrade and =detail=, =answers=, and =alert= after it. The =state= fields after =compacting= belong to "Send expression and activity to clients", and =voice= and =heard= to the voice tasks; clients ignore them until then.

#+begin_src typescript
{ op: "attach"; requestId: string; detail?: boolean }
{ op: "detail"; requestId: string; on: boolean }

// replies on view "items"
{ type: "view"; requestId?: string; reset: true; items: ViewItem[]; state: ViewState; earlier: boolean }
{ type: "view"; changes: ({ op: "put"; item: ViewItem; after: string | null } | { op: "drop"; id: string })[]; state?: ViewState }

type ViewItem =
	| { kind: "user"; id: string; source: string; text: string; imageCount?: number; files?: { name: string; size: number; path: string }[]; voice?: true; private?: true; at?: number }
	| { kind: "assistant"; id: string; text: string; streaming: boolean; answers: string; alert?: "gui" | "apk" | "telegram"; error?: string; heard?: number; thinking?: string; private?: true; expression?: string; pose?: string; at?: number }
	| { kind: "tool"; id: string; name: string; summary: string; status: "running" | "done" | "error"; error?: string; output?: string; private?: true }
	| { kind: "note"; id: string; text: string }

- The daemon folds from state, not events. Each connection holds a =Conversation.watch()= of the root with a window of =min: 200= (=max= 400), and a =ConversationTranscript= merges each value so entries that leave the window stay folded. The fold (=fold()= in =src/transcript.ts=) is a pure function of a view: committed entries from the transcript, and the run, the streaming reply, running tools, the inbox, and compactions from =docs["pi.live"]=, =docs["pi.inbox"]=, and =docs["pi.agent"]=. It runs at flush time, not per watch callback, so a burst of partials costs one fold. An idle conversation is =run === undefined=; =pi.live= may keep =runFailure= after a run that ended without an answer, which the fold shows as an assistant item with =error=, unless the reason is =aborted=, =reset=, or =nothing_to_answer=, or the run's own error entry already says it. A tool call with no result once its run has ended shows as an error, =interrupted=.
- =at= on a user or assistant item is its message's timestamp in epoch milliseconds, when the log has one; the overlay lights a panel by it (see "Light and backgrounds" in =docs/interfaces.org=). A streaming reply has none until it is committed.
- Tool items take the tool call's id, so one item goes from running to done or error without being replaced. 1.5's tool slots carry no arguments, so the summary comes from the tool-calling answer, which is committed before its tools run.
- A reset replaces everything the client holds. It is sent at attach, and again whenever the watch delivers a root replacement (=[["r", view]]=, past 10,000 pending operations).
- After each watch callback the daemon diffs the item list against what it last sent that connection: a new or changed item is a =put= of the whole item, placed after the item whose id is =after= (=null= for first); a removed item is a =drop=. =state= is sent whole when any field changed. Changes are flushed at most ten times a second per connection, so a streaming reply resends its text at most ten times a second; that is fine on the home network and keeps clients to a single "replace this item" operation.
- The streaming reply is the item with id =live=. When the message ends it is dropped and the stored reply is put with its entry id, as =Transcript= already does.
- Assistant =text= is always Markdown. The daemon applies =orgToMarkdown= to a reply to anything but a Telegram message, as the terminal once did itself, so both clients need only a Markdown renderer.
- =answers= is the source of the input the reply follows: a client source, =telegram=, or one of June's own (=work=, =follow=, =watch=, =heartbeat=, =reminder=); it is empty when that input is before the transcript the client holds. Untagged =pi.user= entries from before the bridge answer =telegram=. =alert= is described under "Which messages alert".
- By default the view is simple and matches what the terminal shows. Each thinking block is one line in =thinking=, flattened and with Markdown emphasis removed, so a reasoning summary reads "Finding project heading". Every tool call appears as a line with its name, a one-line summary of its arguments, and its status, so a journal entry or a =work= brief is visible as it happens; a failed call adds the first line of its output as =error=. Left out: full thinking text, full tool output, and June's private looks, with heartbeat and watch looks, quiet answers, and her own inputs hidden exactly as in the terminal, because it is the same code.
- Detail is the complete view, for checking what is going on, like showing hidden files in a file browser. A client turns it on or off with =detail= (or =detail: true= on =attach=, so it survives a reconnect), and the daemon answers with a reset. With detail on, =thinking= carries the full thinking text, tool items carry =output= (a running call's retained output from =pi.live=, then its result's text), and June's private looks appear as items marked =private: true=, including heartbeat looks that ended quiet: the input with the prompt June read, her thinking-only and tool-calling answers, her tools, a quiet answer, and her streaming reply until it is committed. Her words in a look that are a message to the user are not private, so the simple view is exactly the detail view without its private items and the extra fields. Detail belongs to the connection, so turning it on in the overlay leaves the phone simple. The overlay binds it to a key; the Android app puts it in a menu. =Transcript= gains an option to keep private looks instead of dropping them.
- Command replies are not view items: =command= still answers with a =reply=, which the client shows locally, as the terminal does.
- History is the last 200 entries, as for the terminal; =earlier= says older entries were left out. It is a flag, not a count: 1.5's window gives the entry before it, not how many there are, and counting would mean reading them all. Older history is not paged in this view: a separate log browsed by day or week is planned instead, so the conversation never becomes one endless list. 1.5's =ConversationTranscript.loadEarlier()= is what that log would page with. The socket's =history= request returns entries without a view, since a time and up to 2,000 at once, for =june transcript=; it pages back from the newest with =Conversation.entries()= and also answers with =earlier=. It reads the whole history, compaction summaries in place, not only the context since the last compaction as 1.2's snapshot did.
- The terminal renders items: it keeps its look (Org converted to Markdown, thinking lines, tool lines, patter, notes) but no longer folds. Assistant =text= arrives as Markdown, so its own =orgToMarkdown= call goes.

Built in two steps in the Org plan, both done: "Upgrade June to Pi Durable 1.5" moved the fold into the daemon, folded from views, and moved the terminal onto items with the simple view; "Serve the full folded view to graphical clients and the bridge" added =detail=, =answers=, =alert=, and the =tui=, =gui=, =apk=, and =telegram= sources.

** Sources, submitting, and reconnecting
- Sources name June's clients, never the program around them, in three letters to match =cli=:
  - =tui=: the terminal client in any terminal emulator, local or over SSH (kitty today, Termux on the phone, anything later);
  - =cli=: =june ask= and other one-shot commands;
  - =gui=: the Hyprland overlay, on any machine;
  - =apk=: the Android app, including its assistant session.
- Telegram stays untagged for the model: the bridge submits with source =telegram=, which the daemon records in =june.input= like any client but sends to the model without a tag, so June's prompt ("untagged messages come from Telegram") and her habit of answering Telegram in Markdown hold. Readers that asked "was the latest message from Telegram" by the absence of a tag read the =june.input= source instead, and still read untagged =pi.user= entries from before the bridge as Telegram. The terminal's source is renamed from =kitty= to =tui=: stored entries keep =kitty=, so the fold and =june transcript= read =kitty= as =tui=, a =submit= with source =kitty= is recorded as =tui=, and June's prompt says older messages may carry =[kitty]=. A =submit= with any other source is refused. Built on 2026-11-02.
- June answers =[gui]= and =[apk]= in Org like the terminal, since the daemon converts. The host an overlay runs on is not part of the source; the desktop-context task adds it as a separate field with the context it sends.
- Notice routing: =gui= counts as the terminal surface. =apk= becomes its own surface in the task "Route June's own notices to the new surfaces".
- =submit= carries text, inline =images=, and =files= for June's inbox (see "An inbox in the state directory"); a message may be any of them alone.
- A submit is retried with the same =requestId= until it is =accepted=. Clients keep the id with the draft, generated once when the user presses send, so a retry after a dropped connection returns the same submission instead of a second message. The daemon already namespaces ids by source.
- Graphical clients send =submit= with =whenBusy= as the terminal does (follow-up by default, steer on request), never =wait=. Stop is =command= =stop=. They never offer =/new=.
- On a dropped connection the client reconnects with backoff from 1 to 30 seconds, sends =hello=, attaches again, and takes the reset as the truth. There is no resume: a 200-entry reset is small enough. 1.5's watch window can start =from= an entry id, so a resume is possible later; revisit only if attach proves slow on the phone.

** Which messages alert
Every client shows the whole conversation; what differs is which messages interrupt the user. Telegram keeps its narrower behaviour as a fallback client: it shows only answers to messages sent there, plus notices routed there.

- The daemon sets =alert= on a finished assistant reply, never on a streaming one, and only on a reply that ends its turn with words or an error, not on one that calls tools, so a long answer buzzes once. It names the client kind that should interrupt the user:
  - a reply to an =apk= message alerts =apk=, and a reply to a =gui= message alerts =gui=;
  - a reply to one of June's own notices (=work=, =follow=, =watch=, =reminder=, or a heartbeat that did not end quiet) alerts the surface the notice was routed to, which the notice records in its =june.input= data as =surface= when it is committed: =apk= for the phone, =gui= when the terminal surface was chosen, =telegram= when the user last spoke from Telegram;
  - replies to =tui= or =cli= messages alert nothing here; the user is looking at that client already. Nor do replies to =telegram=: the bridge sends what =answers= names =telegram=, below.
  - a failed run alerts like a reply, so the phone hears that its question failed; nothing in a private look alerts.
- Everything else arrives quietly: when the user chats from the desktop, the phone app shows those messages when opened, without a buzz.
- The phone: the Android app connects only while it is on screen, so the daemon treats a connected =apk= device as on screen. A reply with =alert: "apk"= while no =apk= device is connected goes to the phone through ntfy, and tapping it opens the app; while the app is on screen it only appears. A push is sent at most once; losing one in a crash is acceptable, sending it twice is not.
- The overlay is resident and stays connected while hidden. It shows a desktop notification for =alert: "gui"= while it is hidden.
- =src/notify.ts= chooses the surface in the commit that admits the notice (=Conversation.submit(tx, …)=): it reads back to the user's latest own message, a =june.input= from a client source or, before the bridge, an untagged =pi.user=, and records =telegram= when that came from Telegram, otherwise =gui=. A =work= report and a =follow= notice are admitted in the same commit that ends or advances their task, so a restart admits them once. The heartbeat records a surface on every look; a quiet answer alerts nothing anyway. A Telegram message still queued behind a running turn is not yet an entry, so a notice admitted meanwhile follows the message before it. Built on 2026-11-02. =apk=, ntfy, and the at-most-once push record belong to the tasks "Route June's own notices to the new surfaces" and the ntfy notification task; the protocol only carries =answers= and =alert=.

** Telegram bridge
Decided with Jon on 2026-11-02 and built the same day. Telegram is a backup client, so it must never hold the core back. pi-durable-telegram ran inside the harness and pinned the whole =@earendil-works/*= family; it is replaced by a bridge that is only a protocol client.

- =june telegram= (=src/telegram.ts=) is a separate process in the same package, run on the daemon's host as the =june-telegram= systemd user service beside =june.service= when =programs.june.telegram.enable= is set (on by default when =telegram.allowedUsers= is). It reaches the daemon over the Unix socket and reconnects with backoff from 1 to 30 seconds, so a Telegram outage, a grammY crash, or a bridge restart never touches the daemon, and a daemon restart only costs it a reconnect. No Pi Durable type crosses into it.
- It uses grammY (a direct dependency, pinned) with long polling for =message= and =stopped_message_generation= updates. The bot token is =TELEGRAM_BOT_TOKEN= and the allowed users =TELEGRAM_ALLOWED_USERS=, both from June's environment files or the Home Manager option, read through =loadConfig= as =config.telegram=; a =telegram= block in =config.json= is not read. It serves the first allowed user's private chat; anything from another user, chat, or a bot is ignored and logged by ids only.
- In: a text message is a =submit= with source =telegram= and request id =update:<update id>=, retried on reconnect with the same id until accepted, so a redelivered update is one submission. A photo (its largest size), or an image sent as a file (how Telegram delivers an uncompressed screenshot, an =image/*= document), is downloaded (20 MB at most), prepared as the terminal prepares images, and sent inline with its caption as text. Any other document (=application/pdf= and the like) is downloaded (20 MB at most, refused with a reply before downloading when Telegram's =file_size= says it is larger) and sent in =files= with its caption as text, so it lands in June's inbox. Voice notes, audio, video, animations (which also arrive as a document), and stickers get a short reply that the bridge takes text, images, and files. =/stop=, =/new=, =/status=, and =/compact= go as =command= and the reply comes back as a plain message; =/help= and =/start= are answered by the bridge with the same list, which is also the bot's command menu (=setMyCommands= at start). Other slash words, =/reload= included, go to June as text. The stop button on a draft is =/stop=. A command runs apart from polling, so =/stop= gets through while =/compact= works.
- Out: the bridge attaches to the simple items view. It sends a finished assistant item (=streaming: false=) with words or an error when =answers= is =telegram= or =alert= is =telegram=, once. That includes words June writes before calling tools, each as its own message. The text is Markdown, sent as a rich message (=sendRichMessage=) in pieces split under 4,096 characters with a split code fence closed and reopened; when Telegram refuses the rich message it goes as Telegram HTML (=markdownToTelegramHtml=, ported from the library), and when it refuses the HTML, as plain text. A run that failed sends its error; a run the user stopped with no words sends nothing, since =/stop= already answered.
- Drafts: while the live item streams with text and the latest user item is from Telegram, the reply shows as a native draft (=sendRichMessageDraft=, draft id the user item's id), at most one update a second and refreshed every 20 seconds while quiet, since a draft vanishes about 30 seconds after its last update. If Telegram refuses drafts, the bridge uses "typing…" for the rest of its run.
- Patter: while the latest user item is from Telegram, patter items grow one message per wait by editing it (=🦘= and the line in italics), and the next assistant item with words ends the wait. A wait whose message would pass 3,500 characters goes on in a new one. =src/patter.ts= does not talk to Telegram.
- Typing: while =state.running= or =state.background= is set, the latest user item is from Telegram, and no draft is showing, it sends "typing…" every four seconds. It also shows while June takes a heartbeat look after a Telegram message, since the simple view hides her looks.
- Exactly once across restarts: the bridge keeps, in =$XDG_STATE_HOME/june/telegram.json= (0600, replaced atomically), the newest update handled, the newest entry id it has acted on, the ids of run failures it sent (which have no entry id), and the open patter message. It records each before sending, so a crash loses a message rather than sending it twice; a command's update is recorded before the command runs. A reset sends nothing by itself: after one, only qualifying items with entry ids above the saved one are sent, which is what arrived while either process was down. With no state file (the first start) it sends nothing it finds and leaves messages older than five minutes unanswered. A reset whose newest entry is older than the saved one means a new database, and starts over the same way.
- Retries, as the library's transformer did: idempotent calls retry 429 after =retry_after=, 5xx, and network errors, up to three attempts; sends retry only 429, which proves nothing was sent, and a 5xx or network error on a send is logged as unknown and never resent. A send refused with 429 after that is tried again up to five times. Link previews are off for HTML and plain messages; rich messages have no such option.
- Removed from the daemon with the upgrade (done): =createTelegramChannel=, =tg.deliver=, the =tg.chats= and =tg.chat= documents, Telegram code in =src/notify.ts=, =src/patter.ts=, and =src/heartbeat.ts=, and the npm =overrides=.
- Not kept: voice notes, since Jon's keyboard already turns speech into text, and the =telegram_send_file= tool, which June has never called (none in =june.sqlite= on 2026-11-02). Albums arrive as one update per photo and so as separate messages.
- A heartbeat's non-quiet message reaches Telegram the same way as any notice: its =june.input= records =surface= =telegram= when the user last spoke there, so its answer carries =alert: "telegram"=. =src/heartbeat.ts= does not send it itself.

** Voice flag
=submit= takes an optional =voice: true= for speech transcribed from that client. The model sees the tag as =[apk voice]= or =[gui voice]=, the =june.input= entry records =voice: true=, and the user item carries it. June's prompt says a voice-tagged message was spoken and her answer will be heard. The flag says nothing about playback; the client that sent the voice turn owns playback of its answer. Built by the task "Make June's replies speakable"; audio framing belongs to the push-to-talk tasks.

** Presentation entries
Presentation is stored as display-only entries, like =june.patter=: appended at once, kept out of every model context, replayed in the snapshot. The terminal's fold ignores kinds it does not know, so it is unaffected.

- =june.expression= ={for, expression, pose?}=: the face picked for the reply =for= names, after it settled (=src/expression.ts=, only when =model.expression= is set). The fold puts it on that reply's item and the newest on =state.expression=, ="idle"= when there is none in the snapshot. Built on 2026-11-03; the activity signal is still to come.
- =june.playback= ={entry, chars}=: how far playback of an assistant reply got before it stopped, by that reply's entry id. The items view sets =heard= on that item so a client can mark the unheard rest. Built by the push-to-talk tasks.
- Activity is not an entry. It is derived from runtime state and sent as =state.activity=, one of the names in =ACTIVITIES= in =src/avatar.ts=, absent when none holds. =offline= is the client's own connection state and never sent.

* Known risks

- Pi Durable is young and its minor releases break things (1.5 removed =watchEvents()=); upgrade deliberately and read its CHANGELOG.
- The attach snapshot carries up to 200 entries; a long tool-heavy transcript makes attach slower.
- A Herdr prompt is at most once, not exactly once: a crash after Herdr accepted it reports the call as interrupted, and June must check before resending.
- A shell command interrupted by a restart may have partly run; June must check before repeating it.
- Org reads are not a parser. Unusual headings may be missed by =org_tasks=.
- Remote Herdr depends on an unlocked SSH agent and a reachable host.

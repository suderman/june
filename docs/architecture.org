#+TITLE: June architecture

Pi Durable is experimental; recheck these notes when upgrading it.

* Shape

* Decisions

** One daemon owns the database
Pi Durable has no cross-process locking, so only =june serve= opens =june.sqlite=. It takes pi-durable-telegram's data-directory lock before opening storage; a second daemon on the same state exits with the owner's pid. Clients never open the database.

** Pi Durable 1.2.0, pinned to match pi-durable-telegram
pi-durable-telegram 0.1.5 depends on =@earendil-works/*= 1.2.0 exactly. Running a newer Pi Durable beside it would load two copies into one process, with task and document definitions split between them. npm =overrides= pin the whole family to 1.2.0, and =npm ls= shows a single copy. Upgrade together.

** Telegram as a library, routed into the primary conversation
=createTelegramChannel()= is used as published, without its workspace tools, shell, prompt, or plugins; its only tool is =telegram_send_file=. The channel keeps a chat-to-conversation map in the session document =tg.chats=; before =channel.start()=, June points each allowed user at the root conversation, so Telegram and the terminal share one conversation. This depends on two document kinds the library does not export (=tg.chats=, =tg.chat=); June redefines them with the same kind and version, and =test/daemon.test.ts= fails if that stops working.

Delivery is per admitted Telegram message: a =tg.deliver= task submits it and sends the answer back, so answers to terminal input stay in the terminal.

** Source tags instead of separate conversations
Terminal input is a =june.input= entry with ={source, text}=, which the model sees prefixed =[kitty]= or =[cli]=. Telegram input is a plain =pi.user= entry, and the prompt says untagged messages come from Telegram. June's own inputs use the same entry with sources =work=, =follow=, =reminder=, and =heartbeat=; anything that asks "where is the user, and when did they last speak" skips those.

** Transport: newline-delimited JSON over a Unix socket
The socket is mode 0600 in a 0700 directory, with no network listener. Requests are =status=, =attach=, =submit=, and =command=. After =attach= the daemon sends a snapshot of the last 200 entries, then Pi Durable's own events from =watchEvents()= unchanged. Request ids map to Durable =requestId=s namespaced by source, so a retried =submit= returns the same submission. Remote use is =ssh -t host june=, which needs no new authentication.

** Terminal client from pi-tui
The client uses =@earendil-works/pi-tui=. =src/transcript.ts= folds the snapshot and events into display items with no terminal dependency, so it is testable. June answers the terminal in Org; =src/org.ts= converts Org's own syntax to Markdown for the =Markdown= component, and replies to Telegram messages, already Markdown, render as they are.

** Models from Pi's models.json
pi-ai has no loader for Pi's =models.json=, so June reads the configured provider entry and builds it with =createProvider()=, keeping providers defined in one place. The entry's =apiKey= must name an environment variable. Keys are in the service environment and readable through the shell, so keeping them out of answers is an instruction in =AGENTS.md=, not a technical boundary.

** Queueing work through the dispatcher
June starts agents only through org-dispatch. =org_queue_task= writes a first-level =AUTO= heading with =:ID:=, =:AGENT:=, and =:HOST:= in its drawer, and a =:JUNE_REQUEST:= key built from the tool task's id and an instance id kept in the state directory, so a rerun after a restart finds the heading it wrote. It refuses =asana.org=, =inbox.org=, archives, Syncthing conflict copies, files outside the dispatcher's agenda, bodies with a first-level heading or property drawer, and hosts outside =dispatch.hosts=. It writes a temporary file and renames it only if the file's mtime has not changed. State changes on existing headings go through =org-edit= with an expected-state check.

Each queued or resumed heading gets a =june.follow= task: durable, background, owned by the conversation, and recorded by Org ID so a task is followed once. Every minute it finds the heading by =:ID:= and, while it is =PROG=, reads the agent's Herdr status from its =Sessions= link, with no model call. It reports each transition once as a =[follow]= input: not launched after seven minutes, blocked, =HOLD=, =EVAL=, =DONE=, or gone. =TODO= and seven days without an outcome end it silently. Each report's request id includes the check count, so a crash between submitting and committing cannot report twice.

Tasks the user dispatches are watched by =src/watch.ts=, an in-memory loop like the heartbeat rather than a durable task per heading, since it has no heading to start from: org-dispatch's per-run JSON records are the list of runs, keyed by host, ID, and start time so a resumed run is new. A ledger file in the state directory keeps each run's last signal and the news not yet told; a finished run whose signal has settled is not looked up again, so a minute's scan costs one Org lookup per live run. A run that June follows (a live =june.follow= task for its ID) is recorded but never raised, so nothing is reported twice. News is batched into one =[watch]= input and held to waking hours and a minimum gap, so a burst of finished audits is one message rather than ten. The ledger is written before the notice, so a crash can lose a notice but never repeat one.

** Shell and file tools, delegation by judgment
June has Pi Durable's =read=, =write=, =edit=, and =bash= on the daemon host and decides by her instructions whether to do work herself or queue it. No allowlist recreates a narrower limit; approval rules and the AUTO rules live in =AGENTS.md=. The tools are not replay-safe, so an interrupted call is reported as interrupted, never repeated. Org and Herdr read tools are =replay: "safe"=; =herdr_prompt_agent= is not, and is off unless =herdr.allowPrompt= is true. Herdr calls use argv arrays, and other hosts are reached with token-only arguments for reads.

** A background working context, and focus as her choice
The main conversation must stay reachable while June works. =work= follows Pi Durable's background subagent pattern: the replay-safe tool creates a =june.work= task with =background: true=, owned by the conversation, and returns at once. The task creates a child conversation it owns (found again on rerun through =scanConversations({ownerTaskId})=), configured without the work, memory, dispatch, Telegram, and patter extensions, submits the brief under a request id derived from the task, and waits. Its =report= phase posts the final text to the main thread as a =[work]= follow-up, once. A background task is a boundary: the main thread's Esc never reaches it, so =/stop= stops the run if there is one and otherwise aborts the tasks in =WorkDoc.active=. Display-only =june.work= entries let the client show "working in the background" across reconnects.

Where a report goes is decided in the commit that records it (=src/notify.ts=): if the user's latest message came from Telegram, it is handed to pi-durable-telegram's =tg.deliver=; otherwise it stays in the terminal. =[follow]= updates use the same path.

=focus= commits =configure()= on the calling conversation, which applies from the next request. The =mode= section renders from the request's resolved model. Focus is not persisted: startup and =/new= reconfigure the root to the chat model.

** Patter as a display-only side channel
Durable appends a write with only =kind= and =data= at once, even mid-run, and leaves it out of every model context, compaction, and memory review, so each patter line is a =june.patter= entry the client renders and a reconnect snapshot keeps. Chat and focus learn what was said only through a prompt section framed as performance. The loop polls =pi.live= and =WorkDoc= once a second, since it needs only "busy", the running tools, and the running briefs. It lives in memory: losing a line on restart costs nothing. A wait replays as one conversation with the patter model, the updates it heard as user turns and its lines as assistant turns; later updates carry only steps not yet reported, and tool calls go in without their results. On Telegram it edits one message per wait through its own grammY port, since the channel does not expose its client. =thinkingLevel= defaults to =medium=: with =none=, some models wrote their planning into the line.

** Nightly reflection
=src/reflect.ts= is an in-memory loop, not a durable task: once a minute it checks for the rhythm's sleep hours, an idle main thread, and a quiet user, then makes one =completeSimple()= request. A receipt file written after the files keeps it to once a night; a crash between the two reruns the pass on an already tidied day, which costs a request and changes little. The day's subtree and =MEMORY.org= are replaced by atomic compare-and-rename, after the old text is kept under =reflection/= in the state directory, since the data directory is not versioned. Compaction and reflection share one memory brief so both keep the same page. The rolodex is not rewritten by the model: the pass returns, per person, a summary and new notes, and =applyPeople= in =src/people.ts= replaces the summary paragraph under the person's drawer and appends dated notes, or adds a new person under =New=, leaving the rest of a file the user also edits untouched. The pass is given the whole rolodex so it can match nicknames and skip what is already noted.

The longer passes ride the same loop and receipt: once the night's day is done, each tick runs at most one period whose last closed end (=lastClosed()=) is past its receipt, in the order week, month, quarter, year, so a month reads the week and day written minutes earlier. Only the latest closed period is caught up, not every one missed. Each reads shorter digests rather than raw days, except a week, so the input stays small as the period grows, and writes no memory. Digests are ordinary entries that close a date-tree node; the journal's ordering puts later days before a "Month's end", since a title that is not a date sorts after dates.

** Configuration and identity outside the repository
The repository is code and templates and names no one. Machine plumbing comes from the flake's Home Manager module (=nix/home/=: package, service, dispatcher timer, =JUNE_DAEMON_HOST=, =TELEGRAM_ALLOWED_USERS=), with secrets and persistence left to the host's configuration, which hands key files to it as =environmentFiles=; =config.json= and =AGENTS.md= are presets placed in the config directory; identity, memory, and journal are in the data directory. Code holds only harness mechanics that do not depend on the user's environment, such as source tags, where tools run, and side-effect honesty. Templates are filled in when copied rather than on each read, because June edits =MEMORY.org= and =HEARTBEAT.org= by quoting their text, which must match the file.

** Situation as atmosphere
=src/situation.ts= renders the =now= section. Pi Durable stores sections as positional system entries and resends only what changed, so the section is bucketed to the hour and leaves out the live temperature; exact values would add an entry every request. Calendars are Org files parsed for active timestamps on today and tomorrow, read on each render. Home Assistant's REST API is polled in the background for =sun.sun=, the configured =person.*= entities, and a daily forecast (=weather.get_forecasts=, since forecast attributes left the weather entity), so a slow or absent Home Assistant never delays a reply.

** Heartbeat in the main conversation
A heartbeat is a =june.input= with source =heartbeat= in the main conversation, so June judges with everything she knows, and nothing happens in a thread the user cannot see. Pi Durable has no hidden entry kind, so hiding is the client's job: =src/transcript.ts= enters a private mode at a heartbeat input and leaves it at the next input, showing only a final message that is not the quiet answer. Telegram's channel delivery shows typing and sends "(empty answer)" for silence, so =src/heartbeat.ts= waits for the answer itself and sends only a real message. It uses the chat model, since interrupting the user is a consequential call. The window, the cadence, whether the user is chatting, and what changed since the last look are worked out before the model sees anything; the model only judges. Quiet looks add two small entries an hour, which compaction folds away.

** Memory in ordinary Org files
The Durable transcript is short-term continuity; the user's Org records stay authoritative for tasks and schedules. =SOUL.org= and =MEMORY.org= are prompt sections cached by size and mtime, so an edit applies on the next turn. =JOURNAL.org= grows without bound and stays out of the prompt. =src/journal.ts= files entries into an Org date tree, replacing the file atomically only if unchanged, and skips an entry already present so replays write once. The =journal= tool lives in the memory extension, so working contexts never get it.

=src/memory.ts= installs the shared =CompactionTask.beforeCompact= hook for manual, threshold, background, and overflow compaction. One request returns JSON with a working summary and either the revised memory or null, plus dated journal entries the journal lacks. The summary is organized by topic thread, since one conversation holds everything. The response, baseline, proposal, and context range are durable task memos; replay recognizes a saved proposal, refuses a changed range, and counts usage once. Durable catches hook throws and would fall back to its built-in summary, so failures explicitly decline, keeping the old context. Output is capped at 8192 tokens, and there is no automatic pruning.

** Node 22
Pi Durable needs Node 22.19 or later for =node:sqlite=. Node 24 aborts when GC collects =node:sqlite= objects (nodejs/node#65446), so June builds with =nodejs_22=. Node strips TypeScript types itself, so the package ships =src/*.ts= with no build step beyond a typecheck.

** A user service, not a system account
June needs the user's Herdr socket, Org files, SSH agent, and Emacs config, which a separate account would need shared and Herdr does not support cleanly, so she runs as the user's lingering service. Hardening is limited to =NoNewPrivileges= and =UMask=0077=: in a user unit, =PrivateTmp= and =ProtectSystem= create a user namespace in which store-owned files appear owned by nobody, and ssh then refuses =~/.ssh/config=. With a shell as the user, her boundary is her instructions, not the tool list.

* Client protocol for graphical clients
Settled on 2026-10-30, not yet built. The Quickshell overlay and the Android app use the existing =Request= and =Reply= shapes with the additions below, on the desktop and the phone alike. Nothing here adds a service: the daemon keeps one root conversation, Pi Durable orders and deduplicates input, and =Transcript= keeps the privacy rules. Each addition names the task that builds it. Additions are additive: clients ignore reply types, item kinds, and fields they do not know, and the daemon ignores unknown optional request fields.

** Transports
- The Unix socket is unchanged: newline-delimited JSON, mode 0600, no handshake. The terminal client and =june= subcommands stay on it.
- A WebSocket listener carries the same objects, one JSON object per text frame with no trailing newline. Binary frames are reserved for voice audio and refused until a voice task defines them. It is off by default.
- Both graphical clients use the WebSocket, the overlay on kit included, so each has one transport. If the Quickshell spike finds QtWebSockets unusable in Quickshell, the overlay on kit falls back to Quickshell's =Socket= on the Unix socket and only that point changes.
- The listener uses =ws=, already in the lock file through chord, pinned as a direct dependency rather than a second copy. Limits: 32 MiB per message (images are inline, base64), a ping every 30 seconds with the connection dropped if the next ping finds no pong, and a connection dropped when more than 8 MiB of replies are waiting to be sent, since a reconnect costs only a snapshot.

** Address: loopback behind Traefik
The daemon listens on =127.0.0.1= only, on =remote.port= (default 7347), set through a Home Manager option; with no port set there is no listener. It never binds a network interface, so there is no address to wait for and nothing to validate beyond the port.

Clients reach it as =wss://june.kit/= through the Traefik that already runs on kit, with one line in the NixOS configuration: =services.traefik.proxy.june = "http://127.0.0.1:7347";=. That gives what the user's other private services get:
- A certificate from the user's own CA. TLS matters here because traffic is not always inside WireGuard: on the home LAN, and on the hop from a subnet router such as hub to kit, it would otherwise be plain text.
- The name from Blocky, which resolves =june.kit= to kit's LAN address, 10.1.0.6. NixOS hosts run Blocky themselves, and the tailnet's global nameservers point other devices, the phone included, at Blocky, so the name resolves the same at home and away.
- Reachability without Tailscale on the LAN, and from anywhere through Tailscale, since kit and hub advertise 10.1.0.0/16 as a subnet route. Clients never use a 100.x address.
- Traefik's =local= allow list (private and tailnet ranges), and no new firewall port, since Traefik already serves 443. Traefik passes the WebSocket upgrade through without extra configuration.

The allow list admits every device on the LAN, so the device token is the real gate. A process on kit could also reach the loopback port directly; it still needs a token, and processes running as the user already have the Unix socket.

Clients must trust the user's CA: the Android app includes the CA certificate in its network security config, since Android apps ignore user-installed CAs by default; Quickshell uses the system trust store, which the NixOS hosts already populate. A Traefik restart drops connections, which clients recover from as from any other drop.

Set aside: binding the tailnet address (it would make Tailscale a requirement on the LAN), binding the LAN address directly (plain text on the LAN, and a bind that must wait for the address), and Tailscale Serve (TLS only for =ts.net= names, identity per user rather than per device, and configuration held in tailscaled's state).

** Devices and the handshake
- A device is a name and a token. =june device add NAME= prints a new token once (32 random bytes, base64url). =june device list= shows names, creation times, and live connections. =june device revoke NAME= removes it and closes its open connections at once.
- These go through a new Unix-socket-only request, ={op: "device", requestId, action: "add" | "list" | "revoke", name?}=, so the daemon alone writes the device file and can close live connections. The WebSocket refuses it.
- The device file is =$XDG_STATE_HOME/june/devices.json=, mode 0600, replaced atomically, holding each device's name, creation time, and the SHA-256 of its token. A random 32-byte token needs no slow hash. Tokens are compared with =timingSafeEqual=.
- The first frame on a WebSocket must be ={op: "hello", requestId, token, protocol: 1}=. The daemon answers ={type: "hello", requestId, device, protocol: 1}=. A wrong, revoked, or missing token, or any other first frame, or no hello within 10 seconds, closes with code 4401; a client stops reconnecting on 4401 and shows that pairing is needed. An unsupported protocol number closes with 4400. The token goes in a frame rather than a header so no client depends on its WebSocket library setting headers.
- Clients keep their token out of the Nix store: the overlay reads a 0600 file named by its Home Manager option, the Android app keeps it in its private storage. Pairing on the phone is pasting the URL and token; a QR code can come later.

** Attaching to the folded view
=attach= takes an optional =view=. ="events"=, the default, is today's behaviour: a snapshot, then Pi Durable's events unchanged; the terminal client stays on it. ="items"= sends display items computed in the daemon by the same =Transcript= class, one per connection:

#+begin_src typescript
{ op: "attach"; requestId: string; view?: "events" | "items"; detail?: boolean }
{ op: "detail"; requestId: string; on: boolean }

// replies on view "items"
{ type: "view"; requestId?: string; reset: true; items: ViewItem[]; state: ViewState; omitted: number }
{ type: "view"; changes: ({ op: "put"; item: ViewItem; after: string | null } | { op: "drop"; id: string })[]; state?: ViewState }

type ViewItem =
	| { kind: "user"; id: string; source: string; text: string; imageCount?: number; voice?: true; private?: true }
	| { kind: "assistant"; id: string; text: string; streaming: boolean; answers: string; alert?: "desktop" | "android"; error?: string; heard?: number; thinking?: string; private?: true }
	| { kind: "tool"; id: string; name: string; summary: string; status: "running" | "done" | "error"; output?: string; private?: true }
	| { kind: "note"; id: string; text: string }
	| { kind: "patter"; id: string; text: string };

type ViewState = { running: boolean; background: number; queued: number; model: string; notice?: string; compacting: boolean; expression: string; activity?: string };
#+end_src

- A reset replaces everything the client holds. It is sent at attach, and again whenever Pi Durable's stream overflows and sends a fresh snapshot.
- After each event batch the daemon diffs the item list against what it last sent that connection: a new or changed item is a =put= of the whole item, placed after the item whose id is =after= (=null= for first); a removed item is a =drop=. =state= is sent whole when any field changed. Changes are flushed at most ten times a second per connection, so a streaming reply resends its text at most ten times a second; that is fine on the home network and keeps clients to a single "replace this item" operation.
- The streaming reply is the item with id =live=. When the message ends it is dropped and the stored reply is put with its entry id, as =Transcript= already does.
- Assistant =text= is always Markdown. The daemon applies =orgToMarkdown= where the terminal does today (a reply to anything but a Telegram message), so both clients need only a Markdown renderer.
- =answers= is the source of the input the reply follows: a client source, =telegram=, or one of June's own (=work=, =follow=, =watch=, =heartbeat=, =reminder=). =alert= is described under "Which messages alert".
- By default the view is simple: no thinking, no tool output (tool items show name, summary, and status), and June's private looks hidden, with heartbeat and watch looks, quiet answers, and her own inputs hidden exactly as in the terminal, because it is the same code.
- Detail is the complete view, for checking what is going on, like showing hidden files in a file browser. A client turns it on or off with =detail= (or =detail: true= on =attach=, so it survives a reconnect), and the daemon answers with a reset. With detail on, assistant items carry =thinking=, tool items carry =output= (the same retained window the terminal shows), and June's private looks appear as items marked =private: true=, including heartbeat looks that ended quiet. Detail belongs to the connection, so turning it on in the overlay leaves the phone simple. The overlay binds it to a key; the Android app puts it in a menu. =Transcript= gains an option to keep private looks instead of dropping them.
- Command replies are not view items: =command= still answers with a =reply=, which the client shows locally, as the terminal does.
- History is the last 200 entries, as for the terminal; =omitted= says how many were left out. Older history is not paged in this view: a separate log browsed by day or week is planned instead, so the conversation never becomes one endless list.

Built by the task "Serve a folded transcript view to clients" in the Org plan. The terminal may move to the items view later; nothing requires it.

** Sources, submitting, and reconnecting
- Sources name June's clients, never the program around them: =terminal= for the terminal client in any terminal emulator, local or over SSH (kitty today, Termux on the phone, anything later), =cli= for =june ask=, =desktop= for the overlay on any machine, and =android= for the phone app. Telegram stays untagged. The terminal's source is renamed from =kitty= to =terminal=: stored entries keep =kitty=, so every reader (=src/notify.ts=, =src/patter.ts=, =src/heartbeat.ts=, the TUI) treats =kitty= as =terminal=, and June's prompt says older messages may carry =[kitty]=.
- June answers =[desktop]= and =[android]= in Org like the terminal, since the daemon converts. The host an overlay runs on is not part of the source; the desktop-context task adds it as a separate field with the context it sends.
- Notice routing: =desktop= counts as the terminal surface. =android= becomes its own surface in the task "Route June's own notices to the new surfaces".
- A submit is retried with the same =requestId= until it is =accepted=. Clients keep the id with the draft, generated once when the user presses send, so a retry after a dropped connection returns the same submission instead of a second message. The daemon already namespaces ids by source.
- Graphical clients send =submit= with =whenBusy= as the terminal does (follow-up by default, steer on request), never =wait=. Stop is =command= =stop=. They never offer =/new=.
- On a dropped connection the client reconnects with backoff from 1 to 30 seconds, sends =hello=, attaches again, and takes the reset as the truth. There is no event cursor: Pi Durable's =watchEvents= has none, and a 200-entry snapshot is small enough. Revisit only if attach proves slow on the phone.

** Which messages alert
Every client shows the whole conversation; what differs is which messages interrupt the user. Telegram keeps its narrower behaviour as a fallback client: it shows only answers to messages sent there, plus notices routed there.

- The daemon sets =alert= on a finished assistant reply, never on a streaming one, naming the client kind that should interrupt the user:
  - a reply to an =android= message alerts =android=, and a reply to a =desktop= message alerts =desktop=;
  - a reply to one of June's own notices alerts the surface the notice was routed to, which the notice records in its =june.input= data as =surface= when it is committed: =android= for the phone, =desktop= when the terminal surface was chosen;
  - replies to =terminal=, =cli=, or Telegram messages alert nothing here; the user is looking at that client already.
- Everything else arrives quietly: when the user chats from the desktop, the phone app shows those messages when opened, without a buzz.
- The phone: the Android app connects only while it is on screen, so the daemon treats a connected =android= device as on screen. A reply with =alert: "android"= while no =android= device is connected goes to the phone through ntfy, and tapping it opens the app; while the app is on screen it only appears. A push is sent at most once; losing one in a crash is acceptable, sending it twice is not.
- The overlay is resident and stays connected while hidden. It shows a desktop notification for =alert: "desktop"= while it is hidden.
- The mechanics (ntfy, the =surface= field, the at-most-once record) belong to the tasks "Route June's own notices to the new surfaces" and the ntfy notification task; the protocol only carries =answers= and =alert=.

** Voice flag
=submit= takes an optional =voice: true= for speech transcribed from that client. The model sees the tag as =[android voice]= or =[desktop voice]=, the =june.input= entry records =voice: true=, and the user item carries it. June's prompt says a voice-tagged message was spoken and her answer will be heard. The flag says nothing about playback; the client that sent the voice turn owns playback of its answer. Built by the task "Make June's replies speakable"; audio framing belongs to the push-to-talk tasks.

** Presentation entries
Presentation is stored as display-only entries, like =june.patter=: appended at once, kept out of every model context, replayed in the snapshot. The terminal's fold ignores kinds it does not know, so it is unaffected.

- =june.expression= ={name}=: the face to show. The items view puts the newest one in =state.expression=, ="idle"= when there is none in the snapshot. Built by the task "Send expression and activity to clients".
- =june.playback= ={entry, chars}=: how far playback of an assistant reply got before it stopped, by that reply's entry id. The items view sets =heard= on that item so a client can mark the unheard rest. Built by the push-to-talk tasks.
- Activity is not an entry. It is derived from runtime state and sent as =state.activity=, one of the names in =ACTIVITIES= in =src/avatar.ts=, absent when none holds. =offline= is the client's own connection state and never sent.

* Known risks

- Pi Durable and pi-durable-telegram are pre-1.0 in practice. The =tg.chats= routing relies on an internal document.
- The attach snapshot carries up to 200 entries; a long tool-heavy transcript makes attach slower.
- A Herdr prompt is at most once, not exactly once: a crash after Herdr accepted it reports the call as interrupted, and June must check before resending.
- A shell command interrupted by a restart may have partly run; June must check before repeating it.
- Org reads are not a parser. Unusual headings may be missed by =org_tasks=.
- Remote Herdr depends on an unlocked SSH agent and a reachable host.

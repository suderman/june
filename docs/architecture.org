#+TITLE: June architecture

Pi Durable is experimental; recheck these notes when upgrading it.

* Shape

#+begin_src text

* Decisions

** One daemon owns the database
Pi Durable has no cross-process locking, so only =june serve= opens =june.sqlite=. It takes pi-durable-telegram's data-directory lock before opening storage; a second daemon on the same state exits with the owner's pid. Clients never open the database.

** Pi Durable 1.2.0, pinned to match pi-durable-telegram
pi-durable-telegram 0.1.5 depends on =@earendil-works/*= 1.2.0 exactly. Running a newer Pi Durable beside it would load two copies into one process, with task and document definitions split between them. npm =overrides= pin the whole family to 1.2.0, and =npm ls= shows a single copy. Upgrade together.

** Telegram as a library, routed into the primary conversation
=createTelegramChannel()= is used as published, without its workspace tools, shell, prompt, or plugins; its only tool is =telegram_send_file=. The channel keeps a chat-to-conversation map in the session document =tg.chats=; before =channel.start()=, June points each allowed user at the root conversation, so Telegram and the terminal share one conversation. This depends on two document kinds the library does not export (=tg.chats=, =tg.chat=); June redefines them with the same kind and version, and =test/daemon.test.ts= fails if that stops working.

Delivery is per admitted Telegram message: a =tg.deliver= task submits it and sends the answer back, so answers to terminal input stay in the terminal.

** Source tags instead of separate conversations
Terminal input is a =june.input= entry with ={source, text}=, which the model sees prefixed =[kitty]= or =[cli]=. Telegram input is a plain =pi.user= entry, and the prompt says untagged messages come from Telegram. June's own inputs use the same entry with sources =work=, =follow=, =reminder=, and =heartbeat=; anything that asks "where is the user, and when did they last speak" skips those.

** Transport: newline-delimited JSON over a Unix socket
The socket is mode 0600 in a 0700 directory, with no network listener. Requests are =status=, =attach=, =submit=, and =abort=. After =attach= the daemon sends a snapshot of the last 200 entries, then Pi Durable's own events from =watchEvents()= unchanged. Request ids map to Durable =requestId=s namespaced by source, so a retried =submit= returns the same submission. Remote use is =ssh -t host june=, which needs no new authentication.

** Terminal client from pi-tui
The client uses =@earendil-works/pi-tui=. =src/transcript.ts= folds the snapshot and events into display items with no terminal dependency, so it is testable. June answers the terminal in Org; =src/org.ts= converts Org's own syntax to Markdown for the =Markdown= component, and replies to Telegram messages, already Markdown, render as they are.

** Models from Pi's models.json
pi-ai has no loader for Pi's =models.json=, so June reads the configured provider entry and builds it with =createProvider()=, keeping providers defined in one place. The entry's =apiKey= must name an environment variable. Keys are in the service environment and readable through the shell, so keeping them out of answers is an instruction in =AGENTS.md=, not a technical boundary.

** Queueing work through the dispatcher
June starts agents only through org-dispatch. =org_queue_task= writes a first-level =AUTO= heading with =:ID:=, =:AGENT:=, and =:HOST:= in its drawer, and a =:JUNE_REQUEST:= key built from the tool task's id and an instance id kept in the state directory, so a rerun after a restart finds the heading it wrote. It refuses =asana.org=, =inbox.org=, archives, Syncthing conflict copies, files outside the dispatcher's agenda, bodies with a first-level heading or property drawer, and hosts outside =dispatch.hosts=. It writes a temporary file and renames it only if the file's mtime has not changed. State changes on existing headings go through =org-edit= with an expected-state check.

Each queued or resumed heading gets a =june.follow= task: durable, background, owned by the conversation, and recorded by Org ID so a task is followed once. Every minute it finds the heading by =:ID:= and, while it is =PROG=, reads the agent's Herdr status from its =Sessions= link, with no model call. It reports each transition once as a =[follow]= input: not launched after seven minutes, blocked, =HOLD=, =EVAL=, =DONE=, or gone. =TODO= and seven days without an outcome end it silently. Each report's request id includes the check count, so a crash between submitting and committing cannot report twice.

Tasks the user dispatches are watched by =src/watch.ts=, an in-memory loop like the heartbeat rather than a durable task per heading, since it has no heading to start from: org-dispatch's per-run JSON records are the list of runs, keyed by host, ID, and start time so a resumed run is new. A ledger file in the state directory keeps each run's last signal and the news not yet told; a finished run whose signal has settled is not looked up again, so a minute's scan costs one Org lookup per live run. A run that June follows (a live =june.follow= task for its ID) is recorded but never raised, so nothing is reported twice. News is batched into one =[watch]= input and held to waking hours and a minimum gap, so a burst of finished audits is one message rather than ten. The ledger is written before the notice, so a crash can lose a notice but never repeat one.

** Shell and file tools, delegation by judgment
June has Pi Durable's =read=, =write=, =edit=, and =bash= on the daemon host and decides by her instructions whether to do work herself or queue it. No allowlist recreates a narrower limit; approval rules and the AUTO rules live in =AGENTS.md=. The tools are not replay-safe, so an interrupted call is reported as interrupted, never repeated. Org and Herdr read tools are =replay: "safe"=; =herdr_prompt_agent= is not, and is off unless =herdr.allowPrompt= is true. Herdr calls use argv arrays, and other hosts are reached with token-only arguments for reads.

** A background working context, and focus as her choice
The main conversation must stay reachable while June works. =work= follows Pi Durable's background subagent pattern: the replay-safe tool creates a =june.work= task with =background: true=, owned by the conversation, and returns at once. The task creates a child conversation it owns (found again on rerun through =scanConversations({ownerTaskId})=), configured without the work, memory, dispatch, Telegram, and patter extensions, submits the brief under a request id derived from the task, and waits. Its =report= phase posts the final text to the main thread as a =[work]= follow-up, once. A background task is a boundary: the main thread's Esc never reaches it, so =/stop= stops the run if there is one and otherwise aborts the tasks in =WorkDoc.active=. Display-only =june.work= entries let the client show "working in the background" across reconnects.

Where a report goes is decided in the commit that records it (=src/notify.ts=): if the user's latest message came from Telegram, it is handed to pi-durable-telegram's =tg.deliver=; otherwise it stays in the terminal. =[follow]= updates use the same path.

=focus= commits =configure()= on the calling conversation, which applies from the next request. The =mode= section renders from the request's resolved model. Focus is not persisted: startup and =/new= reconfigure the root to the chat model.

** Patter as a display-only side channel
Durable appends a write with only =kind= and =data= at once, even mid-run, and leaves it out of every model context, compaction, and memory review, so each patter line is a =june.patter= entry the client renders and a reconnect snapshot keeps. Chat and focus learn what was said only through a prompt section framed as performance. The loop polls =pi.live= and =WorkDoc= once a second, since it needs only "busy", the running tools, and the running briefs. It lives in memory: losing a line on restart costs nothing. A wait replays as one conversation with the patter model, the updates it heard as user turns and its lines as assistant turns; later updates carry only steps not yet reported, and tool calls go in without their results. On Telegram it edits one message per wait through its own grammY port, since the channel does not expose its client. =thinkingLevel= defaults to =medium=: with =none=, some models wrote their planning into the line.

** Nightly reflection
=src/reflect.ts= is an in-memory loop, not a durable task: once a minute it checks for the rhythm's sleep hours, an idle main thread, and a quiet user, then makes one =completeSimple()= request. A receipt file written after the files keeps it to once a night; a crash between the two reruns the pass on an already tidied day, which costs a request and changes little. The day's subtree and =MEMORY.org= are replaced by atomic compare-and-rename, after the old text is kept under =reflection/= in the state directory, since the data directory is not versioned. Compaction and reflection share one memory brief so both keep the same page.

The longer passes ride the same loop and receipt: once the night's day is done, each tick runs at most one period whose last closed end (=lastClosed()=) is past its receipt, in the order week, month, quarter, year, so a month reads the week and day written minutes earlier. Only the latest closed period is caught up, not every one missed. Each reads shorter digests rather than raw days, except a week, so the input stays small as the period grows, and writes no memory. Digests are ordinary entries that close a date-tree node; the journal's ordering puts later days before a "Month's end", since a title that is not a date sorts after dates.

** Configuration and identity outside the repository
The repository is code and templates and names no one. Machine plumbing (package, service, secrets, =JUNE_DAEMON_HOST=, =TELEGRAM_ALLOWED_USERS=) comes from the deployment; =config.json= and =AGENTS.md= are presets placed in the config directory; identity, memory, and journal are in the data directory. Code holds only harness mechanics that do not depend on the user's environment, such as source tags, where tools run, and side-effect honesty. Templates are filled in when copied rather than on each read, because June edits =MEMORY.org= and =HEARTBEAT.org= by quoting their text, which must match the file.

** Situation as atmosphere
=src/situation.ts= renders the =now= section. Pi Durable stores sections as positional system entries and resends only what changed, so the section is bucketed to the hour and leaves out the live temperature; exact values would add an entry every request. Calendars are Org files parsed for active timestamps on today and tomorrow, read on each render. Home Assistant's REST API is polled in the background for =sun.sun=, the configured =person.*= entities, and a daily forecast (=weather.get_forecasts=, since forecast attributes left the weather entity), so a slow or absent Home Assistant never delays a reply.

** Heartbeat in the main conversation
A heartbeat is a =june.input= with source =heartbeat= in the main conversation, so June judges with everything she knows, and nothing happens in a thread the user cannot see. Pi Durable has no hidden entry kind, so hiding is the client's job: =src/transcript.ts= enters a private mode at a heartbeat input and leaves it at the next input, showing only a final message that is not the quiet answer. Telegram's channel delivery shows typing and sends "(empty answer)" for silence, so =src/heartbeat.ts= waits for the answer itself and sends only a real message. It uses the chat model, since interrupting the user is a consequential call. The window, the cadence, whether the user is chatting, and what changed since the last look are worked out before the model sees anything; the model only judges. Quiet looks add two small entries an hour, which compaction folds away.

** Memory in ordinary Org files
The Durable transcript is short-term continuity; the user's Org records stay authoritative for tasks and schedules. =SOUL.org= and =MEMORY.org= are prompt sections cached by size and mtime, so an edit applies on the next turn. =JOURNAL.org= grows without bound and stays out of the prompt. =src/journal.ts= files entries into an Org date tree, replacing the file atomically only if unchanged, and skips an entry already present so replays write once. The =journal= tool lives in the memory extension, so working contexts never get it.

=src/memory.ts= installs the shared =CompactionTask.beforeCompact= hook for manual, threshold, background, and overflow compaction. One request returns JSON with a working summary and either the revised memory or null, plus dated journal entries the journal lacks. The summary is organized by topic thread, since one conversation holds everything. The response, baseline, proposal, and context range are durable task memos; replay recognizes a saved proposal, refuses a changed range, and counts usage once. Durable catches hook throws and would fall back to its built-in summary, so failures explicitly decline, keeping the old context. Output is capped at 8192 tokens, and there is no automatic pruning.

** Node 22
Pi Durable needs Node 22.19 or later for =node:sqlite=. Node 24 aborts when GC collects =node:sqlite= objects (nodejs/node#65446), so June builds with =nodejs_22=. Node strips TypeScript types itself, so the package ships =src/*.ts= with no build step beyond a typecheck.

** A user service, not a system account
June needs the user's Herdr socket, Org files, SSH agent, and Emacs config, which a separate account would need shared and Herdr does not support cleanly, so she runs as the user's lingering service. Hardening is limited to =NoNewPrivileges= and =UMask=0077=: in a user unit, =PrivateTmp= and =ProtectSystem= create a user namespace in which store-owned files appear owned by nobody, and ssh then refuses =~/.ssh/config=. With a shell as the user, her boundary is her instructions, not the tool list.

* Known risks

- Pi Durable and pi-durable-telegram are pre-1.0 in practice. The =tg.chats= routing relies on an internal document.
- The attach snapshot carries up to 200 entries; a long tool-heavy transcript makes attach slower.
- A Herdr prompt is at most once, not exactly once: a crash after Herdr accepted it reports the call as interrupted, and June must check before resending.
- A shell command interrupted by a restart may have partly run; June must check before repeating it.
- Org reads are not a parser. Unusual headings may be missed by =org_tasks=.
- Remote Herdr depends on an unlocked SSH agent and a reachable host.

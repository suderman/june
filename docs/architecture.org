* Decisions

** One daemon owns the database
Pi Durable has no cross-process locking, so only =june serve= opens =june.sqlite=. It takes pi-durable-telegram's data-directory lock before opening storage; a second daemon on the same state exits with the owner's pid. Clients never open the database.

** Pi Durable 1.2.0, pinned to match pi-durable-telegram
pi-durable-telegram 0.1.5, the newest on npm, depends on =@earendil-works/*= 1.2.0 exactly. Running 1.4.0 beside it would load two copies of pi-durable into one process, with task and document definitions split between them. June pins the whole family to 1.2.0 with npm =overrides=, and =npm ls= shows a single copy. Upgrade together when pi-durable-telegram moves.

** Telegram as a library, routed into the primary conversation
=createTelegramChannel()= is used as published, without its workspace tools, shell, prompt, or plugins. Its only tool is =telegram_send_file=. The channel keeps a chat-to-conversation map in the session document =tg.chats=; before =channel.start()=, June writes Jon's user id into that map pointing at the root conversation, so Telegram and the terminal share one conversation. This depends on two document kinds the library does not export (=tg.chats=, =tg.chat=); June redefines them with the same kind and version, and =test/daemon.test.ts= fails if that stops working.

Delivery is per admitted Telegram message: a =tg.deliver= task submits the message and sends its answer back. Answers to terminal input therefore stay in the terminal, while the TUI shows Telegram exchanges because it watches the conversation. Telegram's =/new= resets the shared conversation for every surface.

** Source tags instead of separate conversations
Terminal input is placed as a =june.input= entry with ={source, text}=, and the model sees it prefixed =[kitty]= or =[cli]=. Telegram input is a plain =pi.user= entry. The prompt tells June that untagged messages come from Telegram, so she can keep those answers compact.

** Transport: newline-delimited JSON over a Unix socket
The socket is =$XDG_RUNTIME_DIR/june/june.sock=, mode 0600 in a 0700 directory. There is no network listener. Requests are =status=, =attach=, =submit=, and =abort=. After =attach= the daemon sends a snapshot trimmed to the last 200 entries, then Pi Durable's own agent events from =watchEvents()= unchanged, so the wire format is the library's, not a new one. Request ids map to Durable =requestId=s namespaced by source, so a retried =submit= returns the same submission. Remote use is =ssh -t kit june= or =ssh kit june ask ...=; that needs no new authentication.

** Terminal client from pi-tui
The TUI uses =@earendil-works/pi-tui= (alt screen, =VStack=, =ScrollView=, =Editor=, =Markdown=), following dpi-tui's layout without importing durable-pi. =src/transcript.ts= folds the snapshot and events into display items and has no terminal dependency. Enter sends (a steer while June works), Alt+Enter queues a follow-up, Esc aborts the run, Ctrl+D detaches. The client reconnects with backoff and reloads from a fresh snapshot. Jon prefers Org where either markup works, so June answers terminal messages in Org; =src/org.ts= converts only Org's own syntax to Markdown for the =Markdown= component, and replies that answer a Telegram message (Markdown, which Telegram needs) render as they are.

** Models from Pi's models.json
pi-ai has no loader for Pi's =models.json=; that lives in pi-coding-agent. June reads the configured provider entry from =~/.pi/agent/models.json= and builds it with =createProvider()=, so codex-lb is defined in one place. The entry's =apiKey= must name an environment variable. Keys come from systemd =EnvironmentFile= or, in development, =envFiles= in June's config, and pass to pi-ai's auth context. They are also in the service environment and readable through the shell, so keeping them out of answers is an instruction in =AGENTS.md=, not a technical boundary.

Pi's =thinkingLevelMap= for gpt-6-luna maps =low= to =light=, which codex-lb rejects. June defaults to =medium=.

** Queueing work through the existing dispatcher
June can start work only through org-dispatch, never by launching agents herself. =org_queue_task= writes a new first-level =AUTO= heading with one host tag into an agenda file, newest first after the preamble, with an =:ID:= and a =:JUNE_REQUEST:= key. The key is the tool task's id plus an instance id kept in the state directory, and the tool is replay-safe: a rerun after a restart finds the heading it wrote. It refuses =asana.org=, =inbox.org=, archives, Syncthing conflict copies (and files with one beside them), files outside the dispatcher's agenda list, bodies containing a first-level heading or a property drawer, and hosts outside =dispatch.hosts=. It writes a temporary file and renames it, and only if the file's mtime has not changed since it read it. =org_dispatch_now= starts the =org-dispatch.service= unit the timer starts. The dispatcher's two-minute settle still applies. June does not change states on existing headings; that would need =org-edit= to accept AUTO.

Each queued heading gets a =june.follow= task: durable, background, and owned by the conversation, so it never makes June look busy. It is recorded by Org ID in the =june.follows= session document, so a task is followed once. Every minute it sleeps on the harness clock (the due time is in its checkpoint, so a restart keeps the schedule), finds the heading by =:ID:= with ripgrep, and, while the task is =PROG=, reads the agent's Herdr status from the heading's =Sessions= link. No model call is made. It reports each transition once as a =june.input= entry with source =follow=, which June answers: not launched seven minutes after queueing, the agent blocked, =HOLD=, =EVAL= or =DONE= (which end the follow), and the heading gone. =TODO= (Jon took it back) and seven days without an outcome end it silently. Each report's request id includes the check count, so a crash between submitting and committing cannot report twice. Reports reach the terminal; Telegram delivers only answers to Telegram messages, so they do not reach the phone yet.

** Shell and file tools, delegation by judgment
The first design gave June no shell, so every check went to a worker. Jon reversed that: June has Pi Durable's =read=, =write=, =edit=, and =bash= on the daemon host, with a 120-second default command timeout, and decides by her instructions whether to do work herself or queue it. No allowlist or permission layer recreates the old limit; approval rules, org-edit for task states and dates, and the AUTO rules stay in =AGENTS.md=. Commands start in the home directory. The tools are not replay-safe, so after a restart an interrupted call is reported as interrupted, not repeated. =/stop= aborts the task, which kills the command's process. The Org tools below are unchanged: ripgrep for search, heading lines for context, path checks that keep reads inside =~/org=, and =org-dispatch scan= for what AUTO would launch. Org writes go through =org-edit= and =org-dispatch=, which run Org in Emacs; her instructions keep her from editing Org task states and dates as text. Herdr tools call the herdr CLI with argv arrays. Other hosts are reached with =ssh host herdr ...= using token-only arguments, and only for reads. =herdr_prompt_agent= exists but is off unless =herdr.allowPrompt= is true. Every read tool is =replay: "safe"=; the prompt tool is not, so a restart never repeats it.

** A working context of her own, and focus as her choice
Jon wanted June's own busy work kept out of her main thread, and two efforts: everyday chat and careful heads-down work, which she manages herself rather than a setting he flips. June is Jon's one thread for everything, so she must stay reachable while she works. =work= follows Pi Durable's background subagent pattern: the replay-safe tool creates a =june.work= task with =background: true=, owned by the conversation, and returns at once (=WorkDoc.byCall= lets a rerun find the task). The task creates a conversation it owns (reused on rerun through =scanConversations({ownerTaskId})=), configured with June's =WORKER= instructions and without the =june-work=, memory, dispatch, Telegram, and patter extensions, submits the brief under a request id derived from the task, and waits. Its =report= phase posts the final assistant text to the main thread as a =[work]= follow-up input, so a report that lands while June is talking waits its turn. The report is its own phase so a restart sends it once. A background task is a boundary: the main thread's Esc and idle waits never reach it, so =/stop= stops the run if there is one and otherwise aborts the tasks in =WorkDoc.active=, telling June what was stopped. The report goes where Jon last spoke to June (=src/notify.ts=): the newest entries tell, since terminal input is a =june.input= entry and a Telegram message a plain user entry. For Telegram it is handed to pi-durable-telegram's own =tg.deliver= task, as its reminders plugin does, created in the commit that ends the task, so the answer reaches his chat; =[follow]= updates use the same path. The choice is made once, in the commit that records the report, so a restart cannot send it both ways. =june.work= display-only entries (started, finished, stopped) let the terminal client show "working in the background" and route Esc, and they survive a reconnect. The child's compactions use Durable's built-in summary, since memory review belongs to the main conversation. Jon's version was to keep work in the foreground until he types; always running it in the background feels the same to him and avoids handing a running child to a new owner mid-call.

=focus= commits =configure()= on the calling conversation, which applies from the next request, so she can tie her hair up and keep working in the same run. The =mode= section renders from the request's resolved model, so it changes only when the mode does. Focus is not persisted as a choice: startup reconfigures the root to the configured default model, and =/new= does the same. Relaxing otherwise relies on her instructions.

** Patter as a display-only side channel
The nightly reflection (=src/reflect.ts=) is an in-memory loop like patter, not a durable task: it checks once a minute whether the clock is inside =reflection.start= to =end=, the main thread is idle, and Jon's last own message is older than =quietMinutes=, then makes one =completeSimple()= request with the chat model. A receipt file in the state directory, written after the files, keeps it to once a night across restarts; a crash between the file writes and the receipt reruns the pass on an already tidied day, which costs a request and changes little. The day's subtree is replaced through the journal's atomic compare-and-rename, and =MEMORY.org= the same way; the replaced text is first kept under =reflection/= in the state directory, because =~/profile= has no Syncthing versioning to undo a bad rewrite. The prompt's memory section carries the last =reflection.recentDays= "Day's end" entries; they change only when a pass writes one, so the prompt stays stable through the day apart from the file's re-read. Compaction and reflection share one memory brief (=MEMORY_BRIEF=) so both keep the same page: Jon wanted memory to hold the facts of his life she must never get wrong, such as where he lives, which the old "lessons and corrections" brief left out, so it stayed nearly empty.

Patter must keep Jon company without touching the work. Durable appends a write with only =kind= and =data= at once, even mid-run, and leaves it out of every model context, compaction, and the memory review, which reads model messages only; so each line is a =june.patter= entry that the terminal client renders and a reconnect snapshot keeps. Chat and focus learn what was said only through a prompt section rendered from the last wait's lines, framed as performance. The loop polls =pi.live= and =WorkDoc= once a second rather than subscribing to events, because it needs only "busy", the running tools, and the running briefs with their child conversations. A wait belongs to the main thread's run, keyed by its first input, or, when the main thread is idle, to the newest brief running in the background. When Jon breaks in, the brief's wait is paused rather than ended: its lines become the note June sees, and once she has answered, patter resumes the same wait with its earlier lines, told that Jon broke in and the work kept going. It is in memory, not a durable task: losing a line on restart costs nothing. On Telegram, patter edits one message per wait rather than sending each line, because an edit is silent and Jon wanted a sign of life on the phone without a buzz every half minute; it has its own grammY port, since the channel does not expose its client. Requests go through =completeSimple()= with =model.patter.thinkingLevel=, =medium= by default: with =none=, gpt-6-luna sometimes wrote its planning into the line, and =medium= answered in about two seconds, no slower (=low= maps to the =light= that codex-lb rejects, and =minimal= is refused with the proxy's image tool). Only patter's output is kept apart; its input is the conversation, because a siloed patter repeated itself. The wait replays as one conversation with the patter model: each update it heard is a user turn and each line it wrote an assistant turn. The opener carries the last few exchanges (Jon's messages and June's final text, trimmed) and the brief; later updates carry only steps not yet reported, so a stall reads as "nothing new" rather than the same digest with a bigger number. Tool calls go in without their results, and elapsed time in rough words, so patter can react to real activity without announcing what the work found or counting seconds.

** Configuration and identity outside the repository
The repository is code only, and public; the code names none of Jon's paths. June uses XDG directories: config (=config.json=, =AGENTS.md=), data (=SOUL.org=, =MEMORY.org=, =JOURNAL.org=), and state. Jon keeps his configuration in two places with different lifetimes. The NixOS flake holds durable plumbing: binaries, services, persisted directories, secrets, and the two machine settings June takes from the environment, =JUNE_DAEMON_HOST= and =TELEGRAM_ALLOWED_USERS=. =~/.agents= holds the presets that change more often, which =agents apply= copies into each harness's real directory; June's =config.json= and =AGENTS.md= go to =~/.config/june= that way. Until 2026-10-28 June instead read =~/.agents/june=, =~/profile/june=, and =~/.config/june= in place as merged layers, which left live configuration in the agents checkout and personal settings in a synced folder; Jon wanted her configured like his other harnesses. The data directory is canonical; on his machines it is a link to the synced folder that holds the files. Harness mechanics that do not depend on Jon's environment (source tags, where the tools run, side-effect honesty) stay in code. =SOUL.org= is adapted from the Hermes June profile (=~/.local/share/hermes/profiles/june/SOUL.md=) with Hermes runtime directives removed. Skills are read in place from the configured =skillDirs= (=~/.agents/skills= and =~/profile/skills=) through =skill_read=, confined to each skill's directory. Bundled skills can become another root if June ever ships any.

Runtime state stays out of every synced or versioned tree: =~/.local/state/june= on kit, persisted by impermanence as storage. A SQLite database with a WAL must not be copied by Syncthing while open.

** Memory in ordinary Org files
The Durable transcript is short-term continuity. Task, schedule, and project facts belong in Jon's Org records. =MEMORY.org= beside =SOUL.org= preserves how June's understanding develops, including formative interactions and corrections, not just preferences. Entries separate Jon's words from June's interpretations and record what happened, what changed, and the resulting behavior. Both files are prompt sections cached by size and mtime, so an edit applies on the next model turn. =/reload= looks for the files again, so a =SOUL.org= or =AGENTS.md= made since startup is found. June can maintain them with her file tools; Hermes memories are reviewed in the Org project, not copied.

=JOURNAL.org= beside them is June's dated record of Jon and their days together, the diary half of being his one thread for everything. Memory holds what she learned and is in every prompt; the journal holds what happened and how he seemed, grows without bound, and stays out of the prompt, read on demand. =src/journal.ts= files entries into an Org date tree in the shape of Jon's own journal, replacing the file atomically only if it is unchanged, and skips an entry whose text is already there so replays write once. The =journal= tool lives in the memory extension so working contexts never get it.

=src/memory.ts= installs the shared =CompactionTask.beforeCompact= hook for manual, threshold, background, and overflow compaction. When a personal memory path is configured, one request returns JSON containing a working summary and either the complete revised memory or null for no change. It reviews the selected context prefix against current memory, identity, and operating instructions, without tools. Only =MEMORY.org= and =JOURNAL.org= can change; the review gets the journal's tail and the local time zone and may return dated entries the journal lacks. The summary still carries the working state; memory does not replace it. Because one conversation holds everything Jon brings, the summary is organized by topic thread, each with its state, personal threads included, and ends with how his day seems to be going.

The response, reviewed baseline, proposal, and context range are durable task memos. After validation, a same-directory temporary file is flushed, checked against the baseline, renamed atomically, and its directory flushed. Only then can the hook return the summary. Replay recognizes an already saved proposal, refuses a changed range or destination, and accounts model usage once per recorded response. A crash before recording the provider response may repeat that request. No separate memory database or service is added; receipts and review status use the existing unsynced SQLite database.

Durable catches hook throws and would continue with its built-in summary, so failures explicitly return decline. Malformed/truncated output, timeout, failed writes, concurrent edits, non-regular memory files, and Syncthing conflicts keep old context. Terminal =/compact= reports the cause; automatic failure status enters June's next prompt. A threshold decline may still allow the request to fit; an overflow decline fails it. There is no retry loop within the review. Output is limited to 8192 tokens, and oversized memory needs deliberate maintenance rather than automatic pruning. Checks and rename run without awaits, but external editors and Syncthing can race the final comparison: this is not a cross-host lock. SOUL.org changes remain deliberate, not an automatic compaction output.

** Node 22
Pi Durable needs Node 22.19 or later and uses =node:sqlite=. The NixOS repository pins Camofox to Node 22 because Node 24 aborts when GC collects =node:sqlite= objects (nodejs/node#65446). June builds with =nodejs_22=. Node 22.18 and later strip TypeScript types by default, so the package ships =src/*.ts= and has no build step beyond a typecheck.

** Deployment: a user service on kit
The Home Manager module lives in the NixOS repository (=programs.june=), which pins this flake as an input. Provider keys come from Pi's agenix-generated =~/.pi/agent/.env=, as Recall's nightly service already does, because June uses Pi's provider definitions. On other hosts the CLI runs the client commands on =daemonHost= over SSH.

kit runs Herdr's default session, org-dispatch, and most work, and is always on. June needs Jon's Herdr socket, his Org files, his SSH agent for other hosts, and the =org-dispatch= that loads his Emacs config. A dedicated system account would need all of that shared with it, which Herdr does not support cleanly, so June runs as Jon's lingering user service. Hardening is limited to =NoNewPrivileges= and =UMask=0077=: in a user unit =PrivateTmp= and =ProtectSystem= create a user namespace in which store-owned files appear owned by nobody, and ssh then refuses =~/.ssh/config=. June has a shell as Jon's user, so her boundary is her instructions, not the tool list.

* Verified behaviour

- Real codex-lb model through June's provider.
- =june ask= and the TUI share one conversation; a CLI message sent while the TUI's request ran was queued and answered after it.
- Ctrl+D detaches mid-run; the run finishes and a new TUI shows it.
- SIGKILL mid-answer, then restart: the run resumed, and resubmitting the same request id returned the same submission with one answer.
- SIGTERM with a TUI attached: the daemon exits, a new one starts, and the TUI reconnects.
- Esc aborts a run.
- Under systemd with the module's settings: Org search, =org-dispatch scan=, local Herdr, and SSH to lux.
- Tests (=npm test=, =nix flake check=): duplicate request ids, restart with unfinished work, attach snapshot and events, Telegram routing, redelivery dedupe and refusal of unknown users with a fake Bot API port, the data-directory lock, Org search and read without modification, Org path escapes, Herdr argv, target validation, Herdr error replies, direct shell and file tools with failure, timeout, =/stop=, and restart, memory kept across a correction and a restart, and pre-compaction learning with failed saves, concurrent edits, cancellation, reload, crash replay, stale ranges, and automatic threshold/background/overflow paths.

* Known risks

- Pi Durable and pi-durable-telegram are pre-1.0 in practice. The =tg.chats= routing relies on an internal document.
- The attach snapshot carries up to 200 entries; a long tool-heavy transcript makes attach slower. Compaction bounds what the model sees, not what storage keeps.
- A model-made Herdr prompt is at most once, not exactly once: a crash after Herdr accepted it reports the call as interrupted, and June must check before resending.
- A shell command interrupted by a restart may have partly run. June is told so and must check before repeating it; the tools never rerun it themselves.
- Org reads are not a parser. Unusual headings (inline tasks, odd keywords) may be missed by =org_tasks=.
- Remote Herdr depends on Jon's SSH agent being unlocked; cog is often asleep.
